Seven Rooms

A field guide to the Architect exam — seven weighted domains, the rules that decide questions, and two gauntlets tuned above typical practice-bank difficulty.

An exam is a building you walk through once, under time pressure, with no map. This guide is the map. The exam has seven rooms — seven blueprint domains, each with a weight on the door — and in every room the questions come dressed the same way: a long scenario, five doors, and only one that opens. The others are traps built from real techniques aimed at the wrong problem.

Three ways to use this guide. First pass: read the rooms in order — each teaches its decision rules with diagrams, then hands you a checkpoint. Drill pass: go straight to the two gauntlets at the end — thirty scenario items pitched deliberately above practice-bank difficulty. Night before: read the quick-revision annex and the option-triage method below, nothing else.

Every domain in this guide keeps reaching for the same instrument: the four properties of the model that architecture must design around instead of wishing it away. Questions across all seven rooms are ultimately asking whether you can see which property is surfacing.

Option triage: how to read five doors in ninety seconds

The gauntlets in this guide add a fifth option and a nastier species of wrong answer, pitched deliberately above practice-bank difficulty so the reflex is built before it is needed. Triage in this order:

  • Diagnose before you choose a remedy. Ask two separate questions of every option: is this technique sound? and is it the fix for this failure? The best distractors are excellent techniques bolted to the wrong diagnosis.
  • Category errors beat tuning errors. If one option changes the mechanism and the others tune parameters inside the wrong mechanism, the mechanism change usually wins. No amount of tuning fixes a wrong mechanism choice.
  • Know the silent-success signature. Confident wrong answers + no errors + normal latency means the architecture is answering a different question than the one being asked. Options that add alerting or retries to that signature are treating symptoms.
  • Spot the adversarial option. It reaches a right-sounding conclusion through broken reasoning, or it would be correct in an adjacent scenario — one detail different from the one in front of you. Re-read the stem's constraints before rewarding a familiar-sounding answer.
  • On multi-select, count independently. Each choice must survive on its own evidence; never pick a second answer because it "goes with" the first.
ROOM D1 · SOLUTION DESIGN & ARCHITECTURE

D1Solution Design & Architecture 17%

The first room asks one question in many costumes: who should own each piece of the work? Get ownership right and the pattern, the reference architecture, and the entry point mostly follow. Get it wrong and no downstream tuning will save you.

Decomposition: three owners, not one

Before any architecture exists, split the work into three piles: what the model owns, what existing systems own, and what humans own. The sorting tests are unglamorous and decisive. Language-shaped, judgment-tolerant, reversible work goes to the model. Anything a lookup table, a rules engine, or arithmetic can answer stays in code — the model may invoke that code as a tool, but it must never be the rules engine, because running a computable decision through a probabilistic component converts a guaranteed answer into a sampled one. And decisions that are irreversible, high-stakes, or accountability-laden keep existing logic plus a human signature.

The most common and expensive early mistake is over-assigning to the model — usually justified as "one agent end-to-end is cleaner." Tidiness is not an architecture property. The tasks in a workflow differ on exactly the axes that matter: reversibility, stakes, computability.

Pattern selection: autonomy is granted, not defaulted

Augmented call → workflow → agent is not a maturity ladder; it is a spectrum of autonomy granted, and autonomy is a cost you pay for a benefit you can name. Walk five factors in sequence — predictability, error cost, observability, latency, cost — and the first factor that rules a pattern out decides. A predictable procedure rules out the agent. A high error cost demands gates an agent's free path can't guarantee. An audit requirement demands a path you can replay.

The trap the exam sets over and over: input variability is not path variability. Messy, varied inputs feel like they need a flexible agent — but if every request takes the same procedure (extract → check → assemble), the messiness lives in the inputs, and a workflow with a deterministic validation gate handles it. Grant autonomy only when the path itself genuinely cannot be enumerated. Workflow sub-patterns — chaining, routing, parallelization, evaluator-optimizer — cover most "we need an agent" instincts; evaluator-optimizer in particular fits open-ended quality rather than procedural correctness a cheap gate can verify.

Reference architectures — and the one misapply that headlines them

Commit to a tested reference architecture before inventing one: retrieval-grounded chat, document pipelines, orchestrated multi-agent research, coding agents. The exam rarely rewards novelty; it rewards knowing what each shape guarantees and where each one breaks.

The headline misapply: retrieval asked to own transactional live state. An index is a snapshot; a balance, a plan tier, an order status is a fact that changes between snapshots. An indexed copy of live data always answers from the past — shortening the re-index interval narrows the staleness window but never closes it, because the mechanism is wrong, not the schedule. Live values come from a tool call to the system of record; retrieval serves the stable knowledge around them.

Silent-success signature

Retrieval-over-live-state presents as confident wrong answers, no errors, normal latency. Nothing is broken; the architecture is faithfully answering a different question — "what did the data say at index time?" When a stem shows that triad, look for the mechanism error before any tuning option.

Multi-agent systems: two failures that are not the same failure

An orchestrator decomposes work, fans out to scoped subagents, and synthesizes their returns. Its two failure classes differ in kind, and the exam probes whether you know which control goes where. Subagent failure is recoverable: the orchestrator survives it, so the fix is orchestrator-level completeness checking — every dispatched unit returns non-empty, or gets retried, reassigned, or explicitly flagged. Never silently synthesize around a gap; count what was dispatched, not what came back. Orchestrator failure is structural: the very component whose job is catching and repairing defects is the one that broke, and subagents cannot see a malformed plan from inside their own subtasks. Its mitigation must therefore sit outside — deterministic validation of the decomposition against the request, before fan-out.

Entry-point governance: constraints eliminate, then what survives is the answer

Choosing where the work meets the model — a consumer surface, an enterprise workspace, an API woven into your own platform, a developer tool — is not a scoring exercise. Regulatory and policy constraints eliminate options first; whatever survives the elimination is the decision. Residency requirements, retention-and-surveillance obligations, and prohibited capabilities each strike options from the list before cost or preference gets a vote. And prefer architectural controls over policy controls: a capability the integration never exposes cannot be misused, while a policy asking users to refrain is only a request the model can ignore.

ROOM D2 · MODELS, PROMPTING & CONTEXT

D2Models, Prompting & Context 13%

This room looks like a trivia room: tiers, token limits, cache flags. It grades like design. Every stem asks one thing: which property of the model is surfacing, and which mitigation belongs to it. Pair them correctly and the five doors collapse to one; mispair them and every distractor looks reasonable.

Four properties, read backwards

The front matter gave you the table. This room runs it in reverse: a validation finding never announces its property — you diagnose from the symptom. An output that flips when the prompt is reworded is next-token prediction surfacing; the cure for a must-be-exact value is a deterministic layer instead of a firmer sentence. Fabricated specifics — names, figures, citations — are knowledge meeting its boundary; ground through retrieval and tool calls, verify claims against sources. One entity's details drifting onto another mid-session is working memory degrading. An instruction honored on eight runs out of ten is steerability — instruction reduces deviation, never eliminates it — so the policy moves into an enforcement layer.

Two framings decide questions here. The properties are constitutive: not bugs awaiting a patch but what the component is, so any option promising to eliminate one is wrong on arrival. And confidence is not validity: fluency holds steady while accuracy varies, so tone carries zero diagnostic information — verification is built, never sensed. The classic distractor pairs a real mitigation with the wrong property: retrieval for a non-determinism finding, a sterner instruction for a knowledge gap.

Tier strategy: defaults are decisions

Route routine work to the balanced middle tier. Escalate a step only where an eval shows the quality bar unmet; drop to the small tier only where an eval confirms the loss is tolerable. "Step" matters — tier choices are per-stage, never per-system: a routing classifier and a final composition step rarely deserve the same model, and a stratified eval surfaces partial migrations (the two hard input types up, everything else down) that an averaged score would bury.

The non-negotiable: every model swap passes the eval suite before it ships. No exception for "newer and better," none for a version bump — the prompt-model pairing is the thing you actually ship. The mirror trap: declining to choose a tier is a choice that lands on the most expensive one; by the time the bill exposes it, the fix costs change management, not configuration. The same bar governs extended reasoning: a billed pass added per call, switched on by a measured accuracy gap, never by "it can't hurt."

A model swap is a release. Behavior moves along dimensions no changelog names — and only your eval suite is pointed at them.

Context strategies: four ways context reaches the model

Context is a degrading resource with a hard edge: attention quality slides well before the limit; at the limit, access simply ends. The window is a ceiling, not a target — budget the largest realistic session plus retrieval plus margin, never the maximum. Four strategies govern how context arrives. Monolithic loads everything up front: right for bounded inputs and stable prefixes that cache well; it dies in accumulating conversations. Progressive carries forward only what the next step needs: the production default for multi-turn and agent loops; it breaks when a decision hangs on a detail dropped three turns ago. Retrieval fetches slices on demand from a corpus too big to hold; it breaks on cross-document synthesis and adds a subsystem you now must evaluate. Compaction compresses the accumulated past; it breaks when the summary drops a critical identifier — and it is one-way. Production systems layer all four: a stable cached opening, a progressive working set, just-in-time fetches, a compaction checkpoint once early exploration stops paying rent.

Not an overflow

Long multi-entity sessions cross-attribute within limits: one customer's details migrate onto another at half the window, nothing truncated anywhere. A bigger window solves a capacity problem the stem doesn't have. The fix is structural — partition sessions per entity, or scope what enters so entities never share attention.

Prompt caching: prefix economics

Caches match on prefixes, token-for-token from position zero — that single mechanism generates every rule. Order blocks by how widely each is shared: system prompt and tool definitions first (all traffic), tenant configuration next (some traffic), the per-request document and user turn last (shared by none). Put dynamic content upstream and the prefix differs on every call: breakpoints set, cache never hits. An edit anywhere invalidates everything downstream regardless of breakpoints — a breakpoint marks where a match may end; it protects nothing that follows a change.

The boundary condition that silently kills the economics: the cache has a lifetime. When requests arrive spaced wider than that lifetime, every call pays the write premium and no call ever reads — caching becomes a surcharge wearing a discount's name. Model prefix size against call frequency inside the lifetime before switching it on.

RAG pipeline: two dials, two failure families

A retrieval pipeline has exactly two decisive dials. Chunking decides the unit that can be retrieved, chosen by the corpus's structure: fixed-size spans for uniform unstructured prose, semantic boundaries where a retrieved passage must stand alone to answer, hierarchical splits for sectioned material — contracts, manuals, policies — where the section is the meaning. A table travels with the paragraph that explains it, or retrieval forever serves numbers stripped of meaning. Indexing decides what "similar" means when a query arrives, chosen by the query pattern: dense embeddings for paraphrase and concept questions, sparse keyword matching for queries that hinge on exact tokens — error codes, clause numbers, part identifiers — and hybrid where real traffic mixes both, the two ranked lists merged with reciprocal rank fusion, the low-tuning default an architect can defend.

A classic move is crossing the axes. Chunking failures and indexing failures are independent: one breaks the unit, the other breaks the finding of it, and each leaves different evidence. Name the axis the evidence points at before touching either dial.

ROOM D3 · INTEGRATION

D3Integration 19%

The heaviest door in the building. Integration is where the model meets systems that were governed long before it arrived, and nearly every question in this room turns on what happens before the model call — which routes compliance leaves standing, whose identity the server vouches for, and how little data crosses the wire.

Five surfaces, one honest question: how much of the loop do you want to own?

Work reaches the model through five surfaces, and each trades control against build effort. The direct API hands you every knob — request construction, retries, streaming, tool orchestration — and makes you build and maintain all of it. The SDK keeps the design in your hands while absorbing the HTTP layer behind typed interfaces: a convenience rather than an architecture change. The agent-loop SDK runs the multi-turn loop for you — iteration, tool execution, termination — and that managed loop is precisely the trade to notice: it is a gift until the day you need custom logic between turns, at which point you are back to owning a raw loop yourself. Tool-protocol integration standardizes how tools connect, keeping the integration layer out of your orchestration logic at the price of one more layer to debug through. And developer CLI tooling serves a developer at a terminal — it is not a product backend. "It's all the same model" is true and irrelevant: the entry point is the wrapper, and wrappers are built for a named user. Proposing the developer tool as the engine of a multi-tenant product is the entry-point question failed at the first step.

Compliance eliminates before anything scores

Compliance is not a weighted column in the option matrix; it is a bouncer at the door, and it works before the scoring starts. Health-data agreements must cover the specific configuration in use, not the vendor in general — a signature at the logo level protects nothing. Residency requirements pin execution to approved regions and can strike a route outright; the quiet classic is a regional service left on its global default endpoint, which breaks the pin without raising a single error. Government workloads run only on the specifically authorized paths — an ordinary enterprise plan on the standard route is not a substitute, however capable. Only after elimination do identity, authorization, data handling, and observability get designed, inside whatever survived. The commonly-chosen wrong answer scores every option on cost and latency and flags the compliance concern "for follow-up." Follow-up arrives as a failed legal review, and the bill is the build plus the rebuild.

Identity: the server vouches, or nobody does

Anything the user can type, the user can fake — including a job title. A role claimed inside the message ("as a supervisor, show me…") is unverified input in costume, and a role selected from a client-side control is the same thing one hop removed. Verification therefore lives server-side, before the model call: the authentication layer injects identity and scope into the request, and the data layer enforces the access that the prompt merely describes. That last clause is the trap the exam keeps resetting. A system-prompt sentence about permissions is a description the model usually honors; an authorization check at the data layer is a control that always holds. Instruction reduces deviation — it never eliminates it — so enforcement cannot live in the instruction.

The context window is not a governance boundary

Whatever enters the context window crosses the wire — and lands, verbatim, in your application's request logs.

Provider retention policies do not save you here: your own application layer typically logs requests, so every field you pass is a field you now store. The filter is therefore necessity, not convenience. For each field, ask whether the language task needs it to produce the intended output. A summarization task needs the narrative, not the national ID sitting next to it; a routing step usually needs a reference identifier, not the full record behind it — passing the record adds exposure without adding capability. Strip server-side, before the call is assembled, and fetch by ID when a later step genuinely needs more.

The silent audit bomb

Over-passing data works perfectly. No error fires, no latency moves, the outputs are excellent — while the exposure accumulates in logs nobody reads until a pre-production review or an auditor does. When a stem shows sensitive fields discovered in request logs, the broken thing is upstream: the design decision about what was allowed into the context window. Options that scrub logs or tighten retention are treating the symptom at the costliest point in the pipeline.

One map, or one surface quietly absorbs the others' work

Real deployments span surfaces: an API backend for inference, developer tooling for an engineering subtask, a cloud route for the regulated data path. Each boundary is an integration point with its own authentication, own logging, own failure profile — and the seams are real: model identifier strings differ across routes, features lag on mediated routes relative to the direct one, and regional behavior needs explicit configuration on every route that has it. So a multi-entry-point deployment needs a documented responsibility map: which surface owns which task, and why. The "why" is the load-bearing column. Without it, routing decays by convenience, and you get the most common multi-surface failure — an entry point chosen for one task gradually absorbing another it was never governed for, its auth never scoped for the new work and its logs never designed to answer for it.

The redaction job still has to run once, over history — but as remediation, not as the control. The distractor to refuse is "disable provider retention": your own application layer wrote those logs, and it will keep writing them until the upstream filter exists.

ROOM D4 · EVALUATION, TESTING & OPTIMIZATION

D4Evaluation, Testing & Optimization 16%

The fourth room grades your grader. Every question here turns on one inversion: the eval suite is the acceptance criteria — written before the production code, consulted before every change, and refreshed as often as the system it claims to measure.

Write the suite before the code exists

A suite written first forces success into measurable terms while the design is still cheap to change, drags hidden assumptions into the open, and becomes the gate every future change must clear — model swap, prompt revision, retrieval reconfiguration, all of them. The contrapositive is a classic probe: a behavior you cannot write an eval for is a behavior you cannot verify — and neither is any change that touches it.

The nastier twist is the suite that has gone stale. A green run against a dataset that predates the change is not evidence; it measures the previous system wearing the current one's name. Checks present but outdated manufacture false confidence: a stale green certifies exactly the change it never tested, at the moment a regression is most likely to ship.

The grading ladder: cheapest reliable instrument first

Grade in code wherever the behavior is unambiguous — schema validity, exact match, length bounds, a lookup against authoritative data. Code checks cost nothing, return in milliseconds, and never drift. Climb to an LLM judge only where interpretation is genuinely required, and make the judging rigorous: a detailed rubric, a constrained verdict set rather than free-form scores, ideally a different model doing the judging than the one being judged (same-family self-evaluation is weaker, not disqualifying), and calibration against human-labeled examples before any verdict is trusted. An uncalibrated judge is worse than no judge: confident numbers with no known relationship to quality. Human review is the top rung and the last resort. And prefer volume: cheap checks running on every change catch more regressions than a handful of artisanal ones.

What the suite runs against decides what its scores mean. A golden dataset earns the name by matching the production input distribution — edge cases, malformed inputs, and adversarial ones included — and by being refreshed with every system change. A dataset assembled from the ten inputs the team knows best measures a different system than the one shipping; its scores predict the demo, not production.

The demo is a capability claim, not a systems model

A working demo proves the system can do the task — and hides four dimensions of doing it at volume. Cost: a bill from a few dozen daily requests is a sample, not a projection. The token tail: production token distributions are skewed — most requests are short, a long tail spends the budget — so a cost model built on averages misses by a factor of two or three. Latency: a demo runs one request at a time and shows you the median; SLA breaches live at p95 under concurrent load. Reliability: a demo has no retries, no fallback, no circuit breaker — the developer refreshing the page was the retry logic. The rule: model volume, token distribution, and tier against the budget ceiling before committing to an architecture, not after the first invoice.

Three controls, three layers — placement is the mechanism

Each reliability control answers a different failure and belongs at a different depth. Exponential backoff absorbs transient errors — rate limits, timeouts — and lives immediately around the API call, so a brief hiccup doesn't amplify into a retry storm. The circuit breaker watches a dependency's error rate and trips at the service boundary, failing fast instead of queuing timeouts. The fallback chain — alternate tier, cached response, graceful degradation — is a routing decision, so it belongs in orchestration. The wrong layer protects the wrong component; the classic distractor bundles all three controls into whichever layer the stem happens to mention.

Live split or shadow: exposure decides

A live A/B test is an experiment, and everything that makes it one is fixed before the split: a falsifiable hypothesis naming treatment and expected direction, random assignment kept consistent per session, one pre-specified primary metric, and a sample size computed in advance — larger than classical software needs, because output variance inflates n. Choose the metric after seeing the results and the experiment degenerates into outcome-shopping: with enough metrics, something always moved. An afternoon of fifty sessions per arm fails every test at once — that six-point "win" is the noise floor introducing itself.

Shadow testing is the other lane: mirror live traffic to the candidate, serve every user the current version, log the candidate's outputs, score them offline. No user ever sees an unvalidated answer — the only acceptable validation when exposure itself is impermissible, or when traffic is too thin to power a split in time. The price: nobody receives the candidate's output, so downstream behavioral signal — acceptance, follow-ups, abandonment — is lost; scoring falls back on rubrics and golden answers.

Classify before you fix

The failure class picks the fix, and the classes are not interchangeable. A prompt failure — ambiguous instruction, model fills the gap — is fixed in the prompt. A hallucination — fluent, confident content unmoored from any source — is fixed by grounding: retrieval, tool calls, verification. Sterner instruction does not repair it, because the model is not disobeying; it is generating. A model mismatch — the wrong tier for the task — is fixed by selection, gated through the suite. An orchestration failure needs a trace spanning orchestrator and workers before anything can be attributed. The same discipline governs a moving metric: model drift (behavior changed on stable inputs), data drift (the inputs changed), and version effects (the pinned model changed) carry three different fixes — misattribute, and you ship the wrong one with full confidence.

Fixed gates, moving distributions

A deterministic gate verifies exactly what it encodes, frozen on the day it was written — while the distribution it guards keeps moving. Read its metrics with suspicion in both directions: a rising rejection rate is loud, but a falling one can mean quality improved — or that the new input distribution simply stopped tripping the old tripwires. Silence from a fixed check is not evidence of health. The rule is permanent pairing: every deterministic gate ships with ongoing sampled review — human or eval — that inspects what the gate passed, not just what it caught. Not scaffolding to dismantle once the dashboard looks calm; the standing cost of freezing a check against a moving world.

The quiet-gate trap

A stem where a rejection or violation rate trends down after a model, prompt, or upstream data change is baiting you to read improvement. Ask first whether the distribution moved out from under the gate. The only way to know is to sample what the gate is waving through — which is why the pairing is permanent, not a launch-period courtesy.

Grade in code what code can grade; judge what needs judgment — and calibrate the judge before you believe it.

ROOM D5 · GOVERNANCE, SAFETY & RISK

D5Governance, Safety & Risk 14%

The governance room asks the question the other six rooms defer: who answers when the system is wrong? Every trap here has the same anatomy — a rule someone believed was enforced by training, by a filter, by a vendor, by a platform — that in fact lived in no layer at all, and failed while looking exactly like normal operation.

The safety stack: four layers, four blind spots

Safety is a stack, and each layer exists because the one below it cannot see something. Trained behavior — Anthropic's layer — suppresses broad classes of harm on every request with zero configuration; it has never seen your product's policy. System-prompt instruction aims the model at that policy, but instruction reduces deviation without eliminating it. Runtime screening inspects actual traffic. Authorization decides what an emitted action may actually do. The failure to watch for is the silent one: a payroll assistant refuses every hostile prompt in red-team review, so the team concludes the model also "covers" the rule that one employee's compensation is never shown to another. It doesn't. That rule appeared in no training set, no prompt, no classifier, and no permission check — so the day a polite, perfectly in-domain request asks for it, the system complies. A rule that lives in no layer is not a weak control. It is no control.

Three gates, three different questions

Input screening asks whether a request should reach the model at all. Output screening asks whether generated text is safe to return. Tool-call authorization asks whether this caller may take this action in this context — and because it guards the only irreversible event on the path, it runs before the tool does, and it is deterministic: allowlist plus identity plus scope, a decision you can prove and replay. The gates sit at different points and check different things, so one filter at one point covers nothing at the other two. Chain check types deliberately: a classifier catches phrasings no rule anticipated but can be argued around; a rule cannot be argued around but blocks only what it was written to block. Each covers the other's miss.

Failing open by accident is the trap

A screening service that errors and passes traffic looks healthy on every dashboard while doing none of its job: the appearance of protection without the function. Anthropic's built-in model safety is not yours to configure and does not fail open; the gates your team builds and hosts do whatever you chose when they break. If you never chose, you chose open: the surrounding code defaults to whatever keeps requests flowing. Fail closed is the default, not an absolute. Where blocking legitimate traffic is the greater harm (a critical-alert pipeline, or a medical-advice path where a silent block strands the patient with no answer), failing open on a degraded check can be the correct explicit choice, provided it raises an alert so the degradation is never invisible. Either way the behavior on error is chosen, never inherited.

Two ways instructions attack

Direct injection arrives in the user's own message, and the input gate exists to catch it. Indirect injection arrives inside content the system treats as trustworthy — a retrieved document, a tool's response — and reaches the model after the input gate has already passed the request. In enterprise deployments with retrieval or tool use, the indirect route is the dominant vector, and it demands its own control: run retrieved content and tool outputs through the same classifier you apply to user input, before any of it joins the context. An option that hardens the user-facing filter while documents flow in unscreened is guarding the door while the window stands open.

The risk catalog: walk the path, write it down

The risk assessment is a walk, not a brainstorm. Follow the request and data paths end to end — user input, retrieved content, tool outputs, model output, logs — and at each stop ask what an adversary could do there and which control stands in the way. The recurring catalog: both injection vectors, token-budget exhaustion (padded input that truncates work or inflates spend), tool and action abuse, and data exposure into contexts or logs where sensitive fields don't belong. The deliverable is written: each risk mapped to its component, a likelihood-and-impact judgment, a mitigation, an owner, and an evidence artifact. That document is what a security reviewer signs — a verbal tour of the diagram is not an assessment.

Fairness has an address

Unequal outcomes do not seep in from everywhere; they enter at four operator-owned doors. The retrieval corpus can over- or under-represent groups, skewing what the model reads. The prompt's framing can encode an assumption that leans outcomes one way. Few-shot examples carry whatever skew their source carried. And downstream routing can send some groups down a different path after a clean output exists. The vendor's fairness evaluation covered the model — and all four doors sit outside the model. A stem offering a vendor report as deployment fairness evidence is showing you a boundary drawn in the wrong place.

Decision logging: one record, three audiences

A decision log exists so that three very different readers can each get an answer. The affected user needs the reason in terms they can act on. The regulator needs proof that comparable cases were treated comparably — reconstructable on demand, from a durable, queryable record. Your own team needs the full trace to find why a flagged decision went wrong. Serving all three means capturing, per decision: the inputs, the retrieved context, the output, and the routing it took. And the log is itself governed data — in regulated contexts it holds exactly the sensitive fields the compliance register cares about, so minimization, retention limits, and access controls apply to the record too. Transparency and data protection want the same log, governed differently.

The log is the explanation. A decision you cannot reconstruct is a decision you cannot explain — to the user, the regulator, or yourself.

Routing to humans: stakes, never volume

Reviewer attention is a budget, and volume is the wrong way to spend it. Route on three variables: confidence (the system's calibrated estimate of how likely this output is wrong — useful only if calibration is verified), reversibility, and the cost of an uncorrected mistake. Low confidence plus irreversible or expensive goes to a person; confident, reversible, cheap flows through. Then place the human: pre-action approval when nothing irreversible may run unreviewed; post-action audit when throughput matters and errors can be unwound; sampled review to monitor system quality rather than guard individual outcomes. Finally, the reviewer's screen decides whether review happens at all. Without the inputs and the reason it was flagged, a queue is an approve button — and gating every step breeds consent fatigue, which is why mature designs review plans and exceptions instead of clicks.

The compliance register: outcome in, control + owner + evidence out

A regulation states an outcome and stops. You supply the other three-quarters: a technical control that achieves the outcome, a named owner accountable for it, and a living evidence artifact — a signed agreement, a configuration screen, a returned log query — revalidated on a cadence, because configurations drift and artifacts go stale. Choosing a compliant route was the prerequisite that got you into the room; it is not proof the rule is being followed, and a reviewer accepts a demonstration, not a design document. The trap is the ownerless control: nobody notices when it stops operating, and the gap surfaces at audit, the costliest place to find it.

Skills as supply chain

A skill bundle is code plus instructions, packaged and distributed — which makes it supply-chain surface, not conversation surface. Your prompt screens watch the dialogue; a malicious bundle was compromised upstream, before any dialogue existed, so the control moves earlier: audit before trust. Open the bundle and read for anomalous calls — network requests, shell execution, file-system access, credential reads — and for out-of-scope operations judged against the skill's stated purpose: a formatter that phones home is a finding. A clean audit can still miss code fetched at runtime, so pair the gate with a net: least privilege, sandboxed, sourced only from vetted registries or verified publishers. Close every audit with an explicit verdict — approve, reject, or remediate-then-re-audit — and never assume the platform screened the bundle for you; verify what its vetting actually covers.

ROOM D6 · STAKEHOLDER COMMS & LIFECYCLE

D6Stakeholder Comms & Lifecycle 14%

This room grades no code. It grades whether the people around the system — the sponsor, the auditor, the successor — could act on what you told them. Nearly every stem here shares one skeleton: the information existed, a structure failed to carry it, and someone made a reasonable decision that was wrong.

Discovery: four buckets, and the moment the questions stop

A discovery call is structured elicitation, not a conversation — listen, translate, write down. Force every stakeholder statement through four buckets: what the system must do, what it must not do, what it must cost, and what it must prove. Stakeholders volunteer the first bucket freely; the other three you must ask for — nobody offers boundaries, budget ceilings, or proof obligations unprompted. Experience words — "seamless," "instant," "careful" — are not requirements; they are flags that more discovery is needed. Ask what would make it feel not seamless, and the answers come back buildable: a latency budget, a no-re-entry rule, a failure state that routes quietly to a person.

The trap has a timestamp: the moment a plausible architecture forms mid-call. Sketching feels productive, the stakeholder nods, and the questions stop — with must-not-do and must-prove still empty, exactly where sign-off gates, protected-data handling, and retention rules live. And treat every "it's just a quick review" as a constraint to chase: throwaway review steps are how mandatory authorization gates get waved through.

Plausibility is the hazard

A stakeholder who hears a competent sketch assumes you had the facts to draw it — and stops supplying them. The unasked constraints resurface weeks later in compliance review, when redirection costs the most. Finish all four buckets before proposing anything.

The translation table: one row per item, reasoning intact

Every discovery item becomes one row with four cells: the statement as said, the constraint it implies, the architectural decision that constraint forces, and the assumption still awaiting confirmation. The row is a chain of custody from words to design — break it and the design inherits your guesses. A classic audit: three requirements trace to something the stakeholder said; one traces to nothing. The unsourced item is the dangerous one — an assumption nobody remembers deciding, so nobody defends it, revisits it, or notices when it breaks. Even sourced translations stay labeled: "instant" became your two-second figure — the number was yours until confirmed.

Tradeoffs: gain, give-up, and the panel people skip

Present every consequential choice in three parts: what we gain, what we give up, and what it costs to reverse the choice later. The third panel is the one presentations omit — the first two feel complete without it — and the one that changes decisions, because it converts "which option is technically better?" into "what if we are wrong?" The second discipline is scale: a per-call cost is accurate and useless — sponsors approve budgets, not unit prices. Quote it monthly at forecast volume, next to the cost of unwinding once the system depends on the choice. A yes without those two figures answers a different question than the one production will ask.

Approval of a direction is not approval of a bill.

The feedback loop: a decision layer, not a dashboard

Observability records — latency, error rates, eval scores, spend. Recording is not deciding. The feedback loop is the layer above the stack, written as a table before launch: every signal that matters maps to a trigger, an owner, and an action. Five stations run in sequence — signals, triage, decide, act, review — and the last feeds the rules back to the first. The failure that hides between the layers: quality eroding a little each week without ever crossing a hard alert threshold. That drift is invisible to dashboards by construction — thresholds see crossings, not slopes — and it surfaces as a user complaint months later unless a trend-shaped trigger with a named owner catches it. Monitoring is not a loop; a signal nothing has decided to act on is scenery.

Regulated deployments add a second trigger species: the calendar. A periodic output audit against the documentation standard, a scheduled confirmation that residency posture still holds — these fire on the date, independent of every metric, because clean-looking dashboards prove only that your thresholds were not crossed, never that the standard is met. A compliance checkpoint wired to metrics alone is a checkpoint the metrics can silence.

One document, three readers

One handoff document, three readers — and a document built for one is incomplete however thick. The inheriting engineer needs decisions plus rejected alternatives — without the options you turned down, they cannot tell which tradeoff a design resolves, so they reverse right decisions or defend wrong ones. The auditor needs, per obligation: control, owner, and the evidence artifact showing it operates — assertions do not survive review. The returning architect — usually you, months out — needs decisions dated, assumptions labeled as assumptions rather than smuggled in as facts, and open items with owners.

The completeness test is one sentence: can a competent architect who was not in the room make a safe change after reading it? A diagram alone always fails — it shows what, never why. The canonical postmortem: a successor hits a latency problem, swaps the context strategy the diagram showed but never justified, and reintroduces the residency violation that strategy existed to prevent. They reversed a load-bearing decision for an understandable wrong reason, because the rationale left the building with its author.

The outcome document: what changed, not what ran

Six fields close an engagement: the scope boundary, the business metric before, the same metric after — same definition, or the comparison is theater — the auditable control that makes the comparison credible, the measurement owner, and the reuse potential. The metric must be one a CFO will defend upward: cycle time cut, cost per case, rework avoided. Volume, latency, and uptime prove the system ran; they say nothing about what it changed — the metrics easiest to export are the ones that cannot justify expansion. And the before-figure is captured at the start or never: you cannot measure a departure point after leaving it.

ROOM D7 · DEVELOPER PRODUCTIVITY & ENABLEMENT

D7Developer Productivity & Enablement 7%

The lightest door on the corridor, and the easiest room to lose on instinct, because every wrong answer sounds like management common sense. Read it as engineering instead: enablement is an architecture whose components are people, channels, and defaults — and each component has a mechanism that controls something, plus a look-alike ritual that merely records the intention.

Four decisions before the first seat

A team environment is a shared artifact, not a pile of personal setups. Before anyone gets access, the architect settles four things: the shared environment — one baseline configuration holding the project instructions, the approved tool servers, and the permission defaults, reviewed and versioned once for everybody; the rollout shape; the skills-distribution channel; and the spend posture. None of them settles by itself; leave one open and drift decides it for you. And the baseline earns its keep only if it can move: a shared asset nobody can version or roll back is a liability from the day a second person depends on it, because one bad edit now propagates to every seat before anyone can stop it.

The champion batch: rollout is a learning system

The first cohort is not a courtesy pilot. Champions exist to manufacture the assets the rollout does not yet have: a baseline hardened by real use, the failure modes they hit converted into runbook entries, and — for every batch that follows — a nearby human who has already seen the sharp edges. Batching is the blast-radius control: whatever the first configuration got wrong lands on ten people with support standing beside them, not on three hundred at once. Expect the distractor "the tooling is mature elsewhere — enable everyone Monday." All-at-once does not skip the learning phase. It runs the identical learning phase in production, everywhere, simultaneously, with the architect as the only support surface.

Distribution: the channel is the governance posture

A skill can reach a team through four channels, and choosing among them is not logistics — each channel is a governance posture. Org-provisioned reaches every member with no opt-out: the only channel where the distribution itself is the control. A versioned plugin serves a defined group through deliberate pulls, one maintainer publishing releases, rollback riding the version history. A project-scoped skill lives in the repository, versions with it, and dies with the work — right for conventions that mean nothing outside one codebase. An API-consumed skill is called by a program, so its rollout follows software-release discipline, not people management. Matching the skill to the channel is the governance decision. The classic mismatch: a procedure required of everyone, shipped on an opt-in channel under a memo declaring it mandatory. The memo is a hope. Only the channel can be a control.

Governance rides the channel, not the announcement — a memo can declare an install mandatory; only a mechanism can make it so.

Spend posture: the default is the decision

The baseline also carries the money mechanics: a model default for routine work (the balanced middle tier, not the flagship), task-tier guidance naming when escalation is justified, caps on spend and rate, and an exception path for the work that genuinely needs more. Skip this and the posture still gets set — by inertia, seat by seat, usually at the expensive end — surfacing months later as an invoice, when the remedy is change management, not configuration. Spend posture is part of team setup, not an optimization to schedule after launch.

Inside the loop, not beside it

Where assistance sits decides what it can touch. Woven inside the loop the team already runs — the editor, the review queue, the CI gates, the test cycle — it operates on the surfaces where the leverage actually is, and the team's conventions become configuration the tooling applies on every pass. Parked beside the loop as a separate window, every use pays a round trip: copy the context out by hand, carry the answer back, re-fit it, re-check it. That tax caps usage at whatever friction each developer will tolerate, and it keeps assistance off the highest-leverage surfaces entirely. The metrics trap: high weekly-active counts can measure visits to the side window — logins, not leverage. Mandated adoption produces compliance; sticky adoption is the integrated path being genuinely easier than the manual one.

Verification: four boxes, each an action

AI assistance lowers the cost of producing code, which raises the volume arriving at review — so the quality bar must be an explicit gate, not a vibe. The checklist has four dimensions: correctness against the stated intent, edge cases included; security, including every dependency the change pulled in; maintainability against the team's conventions; and human comprehension — the person merging can explain what the code does and why. Each box names an action performed, never a field completed, and wherever a check is computable — tests, evals — it becomes an automatic gate. Scale review depth to blast radius: a copy tweak and a payment-path change are not peers. One finding is stop-the-line on its own: a dependency in the diff that nobody present can explain.

The ritual signature

Review medians of a few minutes with checklist compliance at 100 percent is not diligence — it is the form outliving the function. The checklist asks whether verification happened; the metric proves only that the box did. When a stem pairs perfect compliance with implausibly fast reviews, the right option restores the action — deeper review where blast radius is high, automation where checks are computable — never more paperwork.

Support: the symptom-to-cause map is the asset

A misbehaving deployment gets reported as what the team can see: quality slid, latency spiked, the assistant went vague. The architect's value is translation — connect the symptom to the architecture layer that owns it, then write the mapping down so the translation survives without you. The diagnostic that decides questions here: generic fallback answers plus healthy model metrics plus zero exceptions means a dependency the model calls — retrieval, a tool, an authorization — is failing politely while the model does exactly its job. Gradual quality decline with no code change points at the model, the prompt, or a drifting corpus; a latency spike points at grown context, a slowed tool, or a cache gone cold. Runbooks capture symptom → cause → first action so recurring issues resolve without the architect, and escalation paths route what remains to the team that owns the failing layer. Fixing the incident yourself is firefighting; the runbook entry is the support that lasts.

D1 · Solution Designsingle-select

An energy retailer serves 1.4 million households. Its support assistant answers from one RAG pipeline: a 9,000-document knowledge base (tariff explainers, moving-house guides, outage FAQs) and nightly exports of the billing and metering databases, all embedded into the same hybrid index. Four months after launch, agents report that the assistant sometimes states an account balance or current tariff that contradicts the billing screen the agent has open. Monitoring shows no errors, retrieval relevance scores are healthy, and latency is normal. The data-platform team proposes cutting the export cycle from nightly to hourly. What should the architect say?

  1. A

    Approve the hourly re-index and add freshness metadata so ranking prefers the newest chunk; balances will rarely be more than an hour stale, and the residual window can be disclosed to agents as a documented limitation while the pipeline stays unified.

    A real freshness technique bolted to the wrong diagnosis: hourly snapshots narrow the staleness window but never close it, and similarity ranking can still surface an older chunk. The mechanism is wrong rather than the schedule.

  2. B

    Correct: the stem hands over the rescue in one clause, the historical records still exist, so the missing “before” is reconstructable, and the document that results speaks in the CFO's decision units: what moved, provable how, measured by whom, going forward.

  4. D

    The funding case belongs to the sponsor; the architect owns technical truth. Deliver the metrics document as drafted, and offer a live dashboard walkthrough the week before the meeting so the sponsor can present the system's operational health with full confidence. Role separation also protects credibility: figures assembled by the team that built the system persuade precisely because they stay technical rather than promotional; an architect who over-claims business impact spends credibility the next engagement will need.

    The outcome document is precisely the architect's closing artifact, built for the sponsor's upward case, that is what closing an engagement means. Handing over operational health plus a walkthrough leaves the sponsor to answer “what changed” with numbers that structurally cannot say.

  5. E

    Commission an independent consultancy to run a post-engagement ROI study; a third-party figure carries more weight with a CFO than any comparison the team produces about its own system. Independent attribution also separates the assistant's contribution from seasonal submission-volume swings — the confound an internal comparison absorbs — and an external stamp survives due diligence if the expansion is later audited.

    Outsources what the engagement should produce, on a timeline a three-week deadline cannot absorb, and the consultancy inherits the same missing baseline, which it can only estimate less credibly than the archive's own timestamped records reconstruct it.

Answer & rationale

Correct: C.

The buried evidence is the stem's “complicating fact” that isn't one: the pre-deployment workflow records survive, timestamped, so the missing baseline is a reconstruction task rather than a lost cause, and reconstruction is what the three weeks are for. The draft's numbers are all of one species: uptime, volume, latency, accuracy, and unit cost prove the system operated, and an operating system is not what a CFO funds, a moved number in a metric finance already tracks is. The six fields exist to make that delta auditable: before and after on the same definition, a control that makes the comparison evidence rather than assertion, an owner so the number outlives the engagement. The adversarial option: B, gets closest, unit economics is real CFO language, and that is the trap: a baseline-free, ownerless cost comparison is still an assertion, and it measures the assistant's efficiency instead of the outcome the deployment targeted. A relabels, D abdicates, E rents the delay.
