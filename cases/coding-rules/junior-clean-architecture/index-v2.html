Clean Architecture for Juniors

A mentoring walkthrough with Silicon Sandwiches — franchise sandwich ordering as one modular monolith that screams its own business.

Junior, pretend you just cloned Silicon Sandwiches. You have never heard of the company. You open the top-level packages, and in the next thirty seconds the codebase will tell you what it worships. This post is about making sure the answer is sandwiches — not Spring, not SQL, not Stripe — and about the small set of disciplines that keep it that way as the system grows.

Everything below runs on one example: Silicon Sandwiches, a franchise sandwich-ordering business built as a modular monolith. The cast stays fixed — entities like Order and Offer, use cases like PlaceOrder, ports like OrderGateway, adapters like SqlOrderGateway — and every chapter-level idea gets grounded in it. The colours in the sticky key above are the honest map of the whole post:

Amber may depend on teal — never the reverse. The volatile outer ring plugs into the stable core through the violet boundary. Every rule in this post is a corollary of that one sentence.

PART ONE · THE HEART

01Open the project — what does it scream?

If the top level says controllers, services, repositories, the codebase screams Spring. That is the delivery mechanism talking, and the business — franchise sandwich ordering — is whispering underneath the stereotypes.

Screaming Architecture has a precise noun behind it, and it isn't "the domain" in general. Ivar Jacobson's old thesis is that an architecture is a structure that supports the use cases of the system — the things it lets people do. A house plan reveals foyer, kitchen, dining before it reveals brick versus cedar; a repository plan should surface PlaceOrder and ResolveOffer as load-bearing names before anyone meets a framework. And the claim is exclusive: you only get one organizing principle. If the structure is organized around Spring's stereotypes, it is — by definition — not organized around your use cases.

The true-believer trap

Why do junior repos come out framework-shaped? Because framework documentation is written by true believers, from a let-the-framework-do-everything posture. Follow the Spring getting-started guide faithfully and it will happily annotate everything down to the Order entity — that is precisely how a framework takes over an architecture. The prescribed stance is a skeptical eye and a two-part question you should ask of every framework and library:

Decision test — the framework pair

How should I use it — and how should I protect myself from it? For Silicon Sandwiches the protection strategy is nameable and auditable: Spring annotations are quarantined to SpringPlaceOrderController and the @Configuration composition root. PlaceOrder, ResolveOffer, Order, Offer, and FranchiseShop compile with zero Spring imports. Ask the same pair of any new receipt-printing or menu-templating library: which adapter wall keeps it away from the use cases?

The web is an I/O device

Here is a claim stronger than "frameworks are details": being delivered over the web at all is a detail. The web is a delivery mechanism — an I/O device — and the core should be ignorant of it. The litmus: SpringPlaceOrderController should be the only code that knows sandwiches are ordered over HTTP. The franchise could add an in-store kiosk, a phone-order console for shop staff, or a delivery-partner API tomorrow, and each would be just another driver invoking PlaceOrder with a request model and rendering the result through an OrderPresenter. If adding a kiosk would force changes inside PlaceOrder, the web has quietly become your architecture.

This is also the real purpose of the whole exercise: keeping options open. A use-case-centered structure lets you build and demo PlaceOrder and ResolveOffer against in-memory gateways while the database and payment-provider decisions are still open — the way a house architect proves the rooms are usable before the owner picks brick or cedar. A good architecture is the one that lets you change your mind late, cheaply.

New hire, day one "I've read the ordering and offer packages. I can explain how an order gets validated against today's offer, and how payment flows through a PaymentGateway. But… where are the controllers? Is this a website or an app?"

Mentor "You just passed the onboarding test. You know every use case and you still can't tell how the system is delivered — that's the scream working. The controllers are an outer-ring detail. You can meet them next week."

One last link, which we'll cash in properly in section 10: testability is the proof the scream is real. If the architecture is about use cases and the frameworks are at arm's length, then every use case is unit-testable with no web server running and no database connected. The contrapositive is the lie detector — if you need Spring booted to test a business rule, the scream is fake, whatever the folders say.

02Business rules come first

Before frameworks, before SQL, before JSON: the business. In Silicon Sandwiches the critical path is Place Order against a resolved offer for a franchise shop. But "business rules" is not one undifferentiated blob — the inner rings split it in two, and there is a test for which half a rule belongs to.

The abacus test — entities

A rule belongs to the enterprise core only if it would still make or save the business money with no computer at all — executed by hand, by a clerk with an abacus. Those are Critical Business Rules, and the data they can't work without is Critical Business Data. The two are inextricably bound, and binding them together in one module is exactly what an Entity is.

Run it on the cast: "an Order's total is the sum of its line items priced from the resolved Offer" still makes money if the franchise manager tallies it on a paper pad — entity. A FranchiseShop that doesn't deliver refuses delivery orders whether or not software exists — entity. Note what an entity is not: it isn't "a class," and it is emphatically not "a thing my ORM annotates." Any module that binds critical data to its critical rules qualifies, in any language.

The automation discriminator — use cases

What makes a rule application-specific instead? It makes or saves money only by defining how an automated system operates — it would be meaningless in a manual environment. Give PlaceOrder a gating rule of exactly that shape: the system will not accept payment until ResolveOffer has produced today's Offer for that shop, and the shop's delivery toggle has been checked against the customer's pickup-or-delivery choice. A paper-menu shop needs no such rule; it exists only because there is a screen flow to sequence. That's why it lives in PlaceOrder, not in Order.

The relationship between the two layers is choreography with one-way hearing: the use case decides how and when the entities' rules get invoked — it orchestrates, the entities embody — and the entities have zero knowledge of the use cases driving them. That's what makes them reusable: the same Order and Offer could serve a kiosk app, a catering bulk-order app, or a back-office tool tomorrow; PlaceOrder belongs only to the customer-ordering application.

Request and response models — and a subtler trap

Plain data crosses the use-case boundary: request and response models that are not your JPA rows and not your HTTP DTOs. The obvious mistake is deriving them from HttpRequest-shaped framework types. The subtler temptation is putting references to entities inside them, because the models and the entities share so much data. Resist it: they exist for different purposes and change for different reasons, and coupling them buys you tramp data — fields hauled through layers that never read them — and conditional sprawl. (Inside PlaceOrder, holding an Order and an Offer among its working data is fine. Handing them across the boundary is not.)

record PlaceOrderRequest(String shopId, List<LineItem> items,
                         boolean deliveryRequested) {}

record PlaceOrderResponse(String orderId, MoneyAmount total,
                          String readyTime) {}
// Plain fields only. Deliberately: no Order reference, no Spring import.
Decision test — delivery blindness

Hand someone PlaceOrder's spec and ask: web or kiosk? If they can tell, the use case is leaking. A well-formed use case names the data in and the data out and never describes how the system appears to the user — from its text you cannot tell whether the app ships on the web, a thick client, a console, or as a headless service.

03The rings and the Dependency Rule

Draw four concentric circles: entities in the center, use cases around them, interface adapters next, frameworks and drivers outside. Source-code dependencies point only inward, toward higher-level policy. (Four is a schematic, not a law — you may need more rings; the invariants are inward-pointing dependencies and rising abstraction toward the center.)

The rule is stricter than "arrows point inward." It is a rule about names: nothing in an inner circle may mention the name of anything declared in an outer circle — no function, no class, no variable. And it extends to data formats: the classic sin is the database row structure, the convenient object your persistence framework returns from a query. Pass that row inward and the use case silently knows about the database. The corollary decision test: data crosses a boundary in the form most convenient for the inner circle — OrderGateway accepts and returns order-shaped structures convenient to PlaceOrder, never a result row from the orders table.

The check is grep-able. Open PlaceOrder's imports: if SqlOrderGateway, StripePaymentAdapter, or any Spring or JDBC name appears, the rule is broken — regardless of how the diagram looks.

Level is distance from I/O — and the two graphs

"Policy and level" gets a measurable definition: a policy's level is its distance from the system's inputs and outputs. The farther from both, the higher the level; the policies that manage I/O are the lowest in the system. ResolveOffer's overlay of local price deltas onto the national menu baseline is the code farthest from any HTTP request or SQL row — the central transform of the sandwich business, the highest-level policy on the path.

Now the subtle part. Order data flows SpringPlaceOrderController → PlaceOrder → SqlOrderGateway, but the source arrows must not trace that pipeline. Data flow and source dependency are different graphs, and the art is decoupling dependencies from data flow and coupling them to level: both edges point into the use case. Code that "runs fine" with high-level policy directly calling the low-level read and write helpers is still wrong architecture — the arrows trace the data path downhill instead of pointing at the policy.

Why does level matter? Change asymmetry. Low-level policy near the I/O changes frequently, urgently, and for unimportant reasons — a Stripe API version bump, a Spring upgrade. High-level policy changes rarely, and only when the sandwich business itself changes. Architecture is grouping the things that change for the same reasons at the same times, then arranging the groups so every import statement points from lower level to higher. The payoff is containment: urgent churn at the edges never disturbs the important center.

DIP — what it actually targets

Crossing a boundary uses the Dependency Inversion Principle, and juniors routinely over-read it as "never depend on anything concrete." Unrealistic — every system leans on concrete platform facilities. DIP's real target is volatile concretions: the modules your team is actively developing and changing weekly. PlaceOrder may freely use BigDecimal for the total and java.time for the pickup window; it must never name SqlOrderGateway. Interfaces are the safe thing to point at because they are inherently less volatile than implementations — every interface change forces all implementations to change, but implementation changes usually leave the interface alone. A good port earns its keep by staying still: adding caching inside SqlOrderGateway should never ripple into the port that PlaceOrder sees.

In review, DIP compresses to four don'ts:

  • Don't refer to volatile concrete classes — point at interfaces.
  • Don't derive from them — in a statically typed language, inheritance is the strongest, most rigid source relationship there is.
  • Don't override concrete functions — you don't shed their dependencies, you inherit them. Implement PaymentGateway fresh rather than subclassing StripePaymentAdapter to tweak the charge path.
  • Don't new volatile concretes in inner code — creation is itself a source dependency on the concrete class, which is why factories and the composition root exist.

And a liberating footnote: DIP violations can never be fully eliminated, only swept into a small number of concrete components and kept apart from the rest. That dustpan has a name. We meet it in section 07.

The round trip — including the port the original post never drew

The persistence side is only half the story. The same inversion happens on the delivery side, where it is easier to get wrong: flow of control runs controller → use case → presenter, yet the use case is forbidden from naming the presenter. The fix is an output port — an output-boundary interface declared alongside the use case, which the presenter implements from outside:

// Owned by the use-case ring:
interface PlaceOrderOutputPort {
  void present(PlaceOrderResponse response);
}

class PlaceOrder {
  private final OrderGateway orders;
  private final PaymentGateway payments;
  private final PlaceOrderOutputPort output;   // never "OrderPresenter"

  void execute(PlaceOrderRequest request) {
    // ...direct the entities, load and save through the ports...
    output.present(response);
  }
}

What the rings buy you: five independences

Clean Architecture is the merger of a family — Hexagonal / Ports & Adapters, DCI, BCE — all pursuing separation of concerns by layers. Any system that honors the rings gets five verifiable properties, which turn "we use Clean Architecture" from a slogan into an acceptance test. For Silicon Sandwiches: could a staff-tablet UI replace the web UI without touching PlaceOrder? Could the relational store become a document store behind one new adapter? Can Order and Offer be exercised with no Spring context and no Stripe sandbox? Independent of frameworks, testable in isolation, independent of the UI, independent of the database, independent of any external agency. Five yeses mean the rings are real.

PART TWO · THE SEAMS

04Humble Objects — presenters, gateways, and friends

Some objects are hard to test: browsers, device views, JDBC drivers, Stripe's SDK. The Humble Object pattern says: keep those thin, and move the interesting branching and formatting next door where unit tests can reach it. But the pattern is bigger than a testing convenience — it was identified by unit testers (Meszaros' xUnit patterns), and the split they kept making turned out to land exactly on architectural boundaries. That gives you a detector, not just a pattern:

Wherever you find yourself carving out a hard-to-test lump, you have probably found an architectural boundary — and the traffic across it should be a simple data structure.

The view-model completeness test

When is the presenter done? When every single thing the application controls on screen appears in the view model as a string, a boolean, or an enum. Dates arrive as date objects and leave as formatted strings. Money arrives as a currency value and leaves as "$12.40". Button labels are strings; grayed-out states are booleans; tables of numbers become tables of pre-formatted strings. If the view has to compute, format, or decide anything — a color, a format, an enabled state — the presenter isn't finished.

class OrderViewModel {
  String totalText;             // "$12.40" — already formatted
  boolean discountApplied;      // highlight the Offer line?
  String placeOrderButtonLabel; // "Place order"
  boolean placeOrderEnabled;    // false when the FranchiseShop is closed
  List<String> lineItems;       // pre-formatted, one string per row
}

The view binds those fields to widgets and does nothing else. Test the presenter; baby-sit the view.

There is no such thing as an ORM

An object, from its user's point of view, is a set of operations with hidden data. A data structure is public data with no behavior. You cannot map what you cannot see — so Hibernate does not map objects. It loads data structures from relational tables; a better name would be data mapper. The consequence is placement: the mapper and its row-shaped classes belong in the database layer, behind the gateway, forming a second humble boundary. If SqlOrderGateway is built on Hibernate, the mapped row classes stay package-private beside the SQL; Order — the entity with behavior — is reconstructed from that data on the way in. PlaceOrder cannot tell whether Hibernate exists. The persistence framework never gets to define your domain model.

Gateways answer business questions, one method each

A gateway is not a generic data hatch. It is a polymorphic interface with one method per create, read, update, or delete operation the application actually performs — each named for the business question it answers, taking domain-typed arguments. Bad: findOrders(criteria), or anything taking a query string — that's the database sneaking back in through a hole in the wall. Good: ordersPlacedToday(shop), unpaidOrdersOlderThan(cutoff), offersActiveFor(shop, day). Each method exists because PlaceOrder or ResolveOffer asks that exact question; SqlOrderGateway turns each one into SQL out of sight. This is what "no SQL in the use cases" actually means in code.

Service boundaries get the same treatment — in both directions

The pattern extends to external services. Outbound, StripePaymentAdapter is the humble half: PlaceOrder produces a plain payment-request structure (amount, order reference, shop id) and the adapter alone knows how Stripe wants it serialized. Inbound is the half people forget: when Stripe calls back with a payment result, a service listener reduces that vendor payload to a plain payment-outcome structure before it reaches application code — so a change in Stripe's webhook format never ripples past the adapter layer.

Pitfall — the class that is neither

Every class should land in one of two buckets: humble and thin, or logic-bearing and unit-tested. (The interactor is emphatically not humble — it holds the application's rules — yet it stays fully testable because its gateways can be stubbed.) The failure mode is the class that is neither: SpringPlaceOrderController quietly growing an if-statement about whether delivery is allowed. That logic is now stranded on the humble side, invisible to the fast suite. Move it into PlaceOrder or OrderPresenter — whichever boundary it belongs to — one "tiny" if-statement before it becomes a habit.

05Boundaries multiply — and each one has a price tag

Clean Architecture is not "four rings and stop." As Silicon Sandwiches grows you may split streams — a web path, a staff-tablet path, a kitchen-ticket batch job, a future extraction of the offer-read cache. Each stream is its own boundary crossing with its own adapters, and the highest-level policy sits at the apex where the streams meet: PlaceOrder at the top, with the customer-conversation stream (SpringPlaceOrderController, OrderPresenter) on one side, the persistence stream (SqlOrderGateway) on another, and StripePaymentAdapter joining as a third.

But a full architectural boundary is expensive: reciprocal polymorphic interfaces, input/output data structures in both directions, independently compilable and deployable components on each side. So the chapter-grade question isn't "boundaries: yes or no?" — it's which strength of line, where, and when.

Anatomy: four strengths of the same line

At runtime, a boundary crossing is just a function on one side calling a function on the other and passing data. What a boundary actually manages is source-code dependencies — the things that force recompiles and redeploys. The strength ladder runs: source-level separation inside one executable (the monolith — invisible at deployment, fully real in the source tree), separately deployable components (jars), local processes, and services. Threads, note well, are not on the ladder: they schedule execution; they are not architectural boundaries.

Two corollaries of the ladder. First, design ports as if they might one day be promoted — a crossing that is chatty across a function call is fatal across a network. Second, high-level code must never contain the name, address, or URI of anything below it: locating Stripe is the business of StripePaymentAdapter and the composition root, never of PlaceOrder.

Partial boundaries — three named placeholders

When a full boundary costs too much, the answer isn't "no boundary." Three cheaper constructions hold the place, each one rung down in cost and in decay resistance:

  • Skip the last step. Do all the separation work — reciprocal interfaces, both-direction data structures — but compile and deploy both sides as one component. Full design cost, no release-management burden. This is "design the ordering module fully separable, ship one jar wired by the @Configuration root."
  • One-dimensional boundary. A Strategy-style interface inverting the dependency in one direction only. OrderGateway with its lone SqlOrderGateway is exactly this — the inversion is in place, but only discipline stops the adapter from reaching back into PlaceOrder's internals through a backchannel.
  • Facade. A class that lists the services as methods and forwards to hidden classes — sacrificing even the inversion. A PaymentGateway written as a mere facade over Stripe classes leaves PlaceOrder transitively recompiling whenever the Stripe SDK moves. That trap is what StripePaymentAdapter exists to avoid.
Honesty rule

A partial boundary is held shut by discipline, not by the compiler. That's an acceptable trade — if you say it out loud. Be honest about which side of the line is still porous, and re-check it whenever the team changes.

When to draw the line: the inflection point

A fully implemented boundary is expensive; a boundary you skipped is very expensive to add later, even with comprehensive tests and refactoring discipline. So the decision isn't YAGNI-versus-overengineering settled once at kickoff. You watch. You keep a list of boundaries-in-waiting — for us, the staff-tablet path and the kitchen-ticket batch job around PlaceOrder — and you look for the first friction caused by a line's absence: the day a FranchiseShop delivery-toggle change ripples through SpringPlaceOrderController and OrderPresenter together. That's the inflection point, where building the boundary becomes cheaper than continuing to live without it. Draw it then — not sooner, not much later — and re-weigh the list often.

The flip side is that an early line buys you a late decision. The famous version of this story is FitNesse's: a single data-access interface let the team run on stubs, then in-memory, then flat files, through more than a year of feature work — and the database decision eventually deferred itself into nonexistence, until the one customer who wanted a real RDBMS got a new derivative of the interface working in about a day. Our InMemoryOrderGateway is the same instrument: Silicon Sandwiches could build and demo the whole ordering flow before any schema exists, with SqlOrderGateway written the day the decision actually comes due.

The asymmetry test

What do boundaries actually buy? The plugin argument, in one question you can ask of any pair in the cast: who can break whom — and is that the direction you want? ReSharper's source depends on Visual Studio's, so nothing ReSharper's team ships can disturb Visual Studio, while Visual Studio could disable ReSharper at will. StripePaymentAdapter is ReSharper to PlaceOrder's Visual Studio: a Stripe SDK upgrade can never break the ordering rules, while a change to the PaymentGateway port rightly forces the adapter to adapt. Correct — because payment providers change for reasons that have nothing to do with how a sandwich is priced. Boundaries live where axes of change live: the Single Responsibility Principle, operating at architecture scale.

Two war stories — the premature boundary

Company P webified a desktop product with a three-tier topology built for server farms. Every domain object was instantiated in every tier, so adding one field meant touching three tiers, four message protocols, eight handlers, three executables — and every system they ever sold ran on one server, paying the marshaling tax for a farm that never existed. Company W's architect imposed enterprise SoA on a small fleet-management shop: adding a contact field meant registry lookups and message schemas, and testing anything meant booting a parade of services plus the bus. The shared lesson: coupling to premature decisions — ones driven by nothing in the use cases — multiplies human effort enormously. Three-tier is a topology, not an architecture. Hold this thought for section 09.

06Independence — the decoupling-mode ladder

Section 05 priced the boundary; this section decides how much to pay today. The rungs have proper names — decoupling modes — and they are rungs on one ladder, not competing religions:

Decoupling modes for Silicon Sandwiches
ModeComponents talk viaWhat changes for us
Source-level function calls, one address space Nothing — today's modular monolith. Ordering calls the offer module through OfferGateway as a plain method call.
Deployment-level function calls or IPC across deployable units The offer module ships as its own jar; the ResolveOffer side rebuilds without touching ordering.
Service-level data structures over the network OfferGateway backed by a networked adapter. PlaceOrder's source is identical in every row of this table.

The default stance is a concrete decision rule: decouple to the point where a service could be formed — then stay in one address space as long as you can. PaymentGateway and OfferGateway already pass only plain data structures, so a networked adapter can be swapped in behind the same port from the @Configuration root. That is "service-ready." Until lunch-rush read traffic on ResolveOffer actually outgrows the box, there is no network hop, no serialization, no distributed-debugging bill. Defaulting to service-level because the diagram looks modern fails on two counts: it is expensive in development time, and it paradoxically yields coarser decoupling — no matter how micro the services get, the boundaries are never fine-grained enough.

And the mode is reversible — in both directions, which almost nobody teaches. A good architecture lets a system be born a monolith in a single file, grow into independently deployable units, grow further into services, and slide back down when operational needs decline. If a national franchise expansion spikes traffic, Silicon Sandwiches promotes the offer module to a service by rewiring one adapter binding in the composition root; if the expansion fizzles, it slides back in-process the same way. Order, Offer, PlaceOrder, and ResolveOffer never learn which rung they are running on.

What one structure must support

Why all this ceremony? Because one component structure has to satisfy four masters at once: the system's use cases (make intent visible at the top level — the scream), its operation (lunch-rush ResolveOffer reads have a different load profile than steady PlaceOrder writes; isolation keeps the replicate-the-hot-path option open), its development (Conway's law — the ordering team and the offer team stop stepping on each other once the slices are decoupled), and its deployment (immediately runnable after build, with the @Configuration root as the master component that starts and wires everything — no ritual of hand-tweaked property files per shop).

True versus accidental duplication

Independence has a price juniors pay backwards: they unify things that merely look alike. The distinction: true duplication means every change to one copy necessitates the same change to the other. Accidental duplication is two things that resemble each other today but change at different rates, for different reasons — and unifying them couples them, which is far harder to undo than tolerating the resemblance. The place-order screen and a kitchen-ticket reprint screen may share a layout today; resist extracting the shared component, because menus and kitchen tickets evolve for different reasons. Horizontally: the row SqlOrderGateway reads looks a lot like the order-confirmation view, and the temptation is to pass it straight up. Instead OrderPresenter copies fields into an OrderViewModel — cheap insurance for layer decoupling.

Decision test

Before unifying two similar-looking pieces of code, ask: when one changes, must the other change with it, always? If the answer is anything but yes, the duplication is accidental — leave it alone.

Finally, use cases are the second axis of division: thin vertical slices cutting through the horizontal layers. PlaceOrder owns a slice — its controller, its use case, its presenter, its use of the gateways — and ResolveOffer owns its own slice; they share knowledge only through the entities. When a cancel-order or catering pre-order use case arrives, it lands as a new slice beside PlaceOrder, not as edits inside it. New features become additive, not surgical.

07Main is the dirty little secret

Someone has to create the concrete objects and plug them together. That someone is Main — in our story, the Spring @Configuration composition root. Main is allowed to know everything; the rest of the system is not. Remember section 03's footnote: DIP violations can't be eliminated, only swept into a small number of concrete components. Main is the dustpan — the dirtiest of the dirty components, and that is its job description, not an insult.

@Configuration
class SiliconSandwichesConfig {

  @Bean
  OrderGateway orderGateway(DataSource ds) {
    return new SqlOrderGateway(ds);
  }

  @Bean
  PaymentGateway paymentGateway(StripeClient stripe) {
    return new StripePaymentAdapter(stripe);
  }

  @Bean
  PlaceOrder placeOrder(OrderGateway orders,
                        PaymentGateway payments,
                        OfferGateway offers) {
    return new PlaceOrder(orders, payments, offers);
  }
}

Notice the direction: Main wires adapters into ports; PlaceOrder never constructs SqlOrderGateway itself. Now the parts the compact version leaves out.

Nothing depends on Main

Main has a precise structural definition: it is the lowest-level policy, the initial entry point, and nothing — other than the operating system — depends on it. Every source arrow points out of Main into the core; none point back. Its lifecycle is create everything, wire everything, hand control to the high-level policy, and get out of the way. A junior can verify this mechanically: search the codebase for references to the config class. The only caller should be the bootstrap itself.

The DI framework stops at Main's door

Here is the rule that turns the composition root from "the place where Spring lives" into "the fence that keeps Spring out of everywhere else": the Dependency-Injection framework is itself a detail, so its machinery operates only inside Main. The framework injects into Main; from there, dependencies are distributed normally — plain constructor arguments, no @Autowired, no @Component, no annotation of any kind on PlaceOrder, ResolveOffer, Order, or Offer. The proof-test: you can new PlaceOrder(fakeOrders, fakePayments, fakeOffers) in a plain unit test with no Spring context at all. If a use case can't be constructed without booting Spring, the framework has leaked past Main.

Main is a plugin — so have several

Because Main sits behind a boundary and nothing depends on it, Main behaves like a plugin to the application — and you can have as many as you have configurations. One for Dev, one for Test, one for Production; even one per country or jurisdiction, each setting its own initial conditions and standing offers while PlaceOrder and ResolveOffer stay byte-for-byte identical in every deployment. Seen this way, the configuration problem mostly dissolves: configuration is a swappable plugin, never a branch (if (env == PROD)) inside business code.

The keeper of the dirty strings

Raw literals, resource handles, and flavor data gather in Main and travel inward as constructed values. The bread and topping catalogs, the printable menu labels, the JDBC URL behind SqlOrderGateway, the API credentials behind StripePaymentAdapter — all loaded by the composition root and passed in. The audit question: could a franchise rename "hoagie roll" to "baguette" without touching a single core class? If not, a dirty string escaped Main. And for the single most volatile class in the system, Main can protect even itself: select the PaymentGateway implementation by name from a properties file, so a new payment adapter is a config edit rather than a recompile of the root.

Pitfall — plumbing yes, policy no

Main may legitimately own low-level plumbing: the HTTP listener, the raw-input dispatch, seeding the opening menu and standing offers at startup. What it must never own is anything policy-shaped — no pricing, no offer arithmetic, no delivery decisions. Main lays the table; PlaceOrder and ResolveOffer cook. And don't try to keep Main "clean" and abstract — abstracting Main just smears its dirt into the core.

PART THREE · THE DETAILS

08The database and the framework are details

The database is a detail. The web framework is a detail. Both belong at the edge, plugged into ports the business owns. But start with the distinction that keeps the slogan from being misread:

The data model is architecturally significant. The database is a doorknob.

The structure you give your data — the shape of an Order, how FranchiseShop variations attach to a menu item — is architecture, and PlaceOrder and ResolveOffer depend on it deeply. The database is merely the utility that shuttles that data on and off storage: necessary, replaceable, and not what the building is about. "The database is a detail" never meant schema design doesn't matter. It means Postgres versus MySQL versus a document store is a doorknob decision, made behind SqlOrderGateway.

Why do databases feel more important than that? Five decades of slow rotating disks, where a read cost a million processor cycles — forcing indexes, caches, and query languages, which is all a database is: machinery for moving data between disk and RAM. Run the thought experiment: if all data lived in RAM, would you organize it as tables queried by SQL? No — you'd use lists, trees, hash tables. And you already do: when PlaceOrder runs, it works with an Order holding a list of line items and a resolved Offer — in-memory structures. The tables behind SqlOrderGateway exist only because bits must survive between lunches. When the lunch-rush lookup gets slow, the fix is indexes or caching inside the gateway adapters; ResolveOffer's code does not change. Storage performance is legitimate — and fully encapsulable.

The asymmetric marriage

Framework adoption is a one-directional marriage: you make a huge, long-term commitment; the author makes none back. Framework authors solve their problems — Spring's authors have never heard of a turkey club — and their integration advice maximizes your coupling, because coupling costs them nothing and locks you in. Four named risks, worth reciting as a checklist: (1) the framework wants into your innermost circle — base classes and annotations on your entities; (2) your product matures past the framework's facilities and it starts fighting you; (3) the framework evolves in directions you don't need, and features you relied on vanish; (4) a better one appears and you can't switch.

The escape mechanism is concrete, not a vague ideal: when a framework asks you to derive your business objects from its base classes, refuse — derive proxies instead, and keep the proxies in components that plug in. If the ORM wants an annotated, framework-derived order class, the answer is a package-private row type inside SqlOrderGateway mapped to a plain Order:

// ✗ The anti-pattern — the framework in the innermost circle:
@Entity @Table(name = "orders")
class Order { @Id Long id; @OneToMany List<OrderLineRow> lines; ... }

// ✓ The proxy stays in the plugin; rows never travel:
class SqlOrderGateway implements OrderGateway {
  // package-private, invisible to the rest of the system
  @Entity @Table(name = "orders")
  static class OrderRow { @Id Long id; ... }

  public Order find(OrderId id) {
    OrderRow row = em.find(OrderRow.class, id.value());
    return toOrder(row);   // plain entity out; the row stays home
  }
}

"Rows and tables must not travel" is a named architectural error, not a style preference: let a row type escape SqlOrderGateway and a column rename becomes a change to PlaceOrder and possibly to what OrderPresenter formats. Knowledge of the tabular form of the data belongs in the lowest-level utilities of the outer circles, nowhere above.

War story — when the checkbox wins

Uncle Bob fought for years to keep an RDBMS out of a system that didn't need one — and lost, because customers simply expected a relational database as a checkbox item, driven by vendor marketing rather than any rational use. The lesson he drew isn't "fight harder." It's that irrational external forces — customer checklists, corporate mandates — are real, and the architecture win is not winning the technology fight but making the technology a side-plugin so the fight doesn't matter. If franchise corporate mandates an enterprise database because procurement says so, the mandate lands entirely inside SqlOrderGateway, and the core never learns which vendor won.

09Services are not an architecture

Drawing three boxes labeled Offer Service, Order Service, and Payment Service does not give you Clean Architecture. It gives you a network bill and a distributed-debugging hobby. The chapter's test is quotably precise: architecture is defined by boundaries that separate high-level policy from low-level detail and follow the Dependency Rule — a service that merely separates one behavior from another is an expensive function call, not an architectural element.

The decoupling fallacy, mechanically

"But services are strongly decoupled!" — at the level of individual variables, yes. They remain coupled by the data they exchange. Picture the naive split passing an order record between the three services, and corporate adds a gluten-free surcharge: a new field on that shared record. Every service touching the amount must change, and all three must agree whether the surcharge applies per line item or per order. Coupling to the record is indirect coupling to each other — one field, three coordinated releases, and the "independent" teams were never independent, just distributed. (The companion jab: a service interface is no more formal, and no better-defined, than a function interface. The OrderGateway signature is exactly as rigorous as a REST schema.)

The actual fix: component-based design

The Kitty lesson doesn't end at the diagnosis — there is a cure, and it's the Open-Closed Principle at deployment granularity. Keep the shared pricing logic in an abstract base; extract the feature-specific part into its own component that overrides it via Strategy or Template Method; let a factory — wired from the outer ring — instantiate the concrete classes. Shipping the surcharge then means adding a jar, not editing the fleet:

// The stable abstraction ResolveOffer prices against:
abstract class SurchargePolicy {
  abstract MoneyAmount surchargeFor(LineItem item, FranchiseShop shop);
}

// The new feature — its own component, dropped onto the load path:
class GlutenFreeSurcharge extends SurchargePolicy {
  MoneyAmount surchargeFor(LineItem item, FranchiseShop shop) { ... }
}

// Wired by a factory in the @Configuration root. PlaceOrder, OrderGateway,
// SqlOrderGateway, StripePaymentAdapter: untouched, un-redeployed.

Boundaries run through services, not between them

The chapter's punchline inversion: even when you do extract a service, the architectural boundary is not the HTTP hop. If Silicon Sandwiches one day extracts Payments, the boundary is still the PaymentGateway port that PlaceOrder depends on, with StripePaymentAdapter on the far side — the same line whether both sides share a JVM or sit in different pods. Services are deployment and communication units; the architecture lives in the component structure inside them. You can't outsource boundary-drawing to the network — the work is still waiting for you inside each box.

That yields a three-way grading scheme for the services you'll meet in the wild: (1) a single component wholly surrounded by an architectural boundary — a Payments extraction sitting entirely behind PaymentGateway; (2) a composite of several components separated by internal boundaries that obey the Dependency Rule — an Ordering service that keeps its controller, use case, gateway, and presenter properly layered inside; (3) a service so coupled to its clients — shared row shapes, shared interpretation — that it has no architectural significance at all. Type 3 is supposed to be rare. Experience says otherwise.

Pitfall — the org chart draws the boxes

The scalability pitch — one dev-ops team per service, scale by adding services — quietly converges on one microservice per programmer, because the org chart, not the domain, drew the boxes. Silicon Sandwiches with four developers does not need four services. Module ownership inside the monolith (one dev owns ordering, another owns offers) buys the same autonomy without betting the architecture on it — and without the surcharge forcing those "independent" teams into one coordinated release anyway.

PART FOUR · KEEPING IT HONEST

10The test boundary

Tests are not outside the system, watching. They are a first-class component of it — and architecturally they have a precise address: the outermost circle. Tests follow the Dependency Rule perfectly — always depending inward, maximally detailed and concrete, with nothing in the system depending on them. They are independently deployable (to CI, never to a live shop), and they are the most isolated component in the architecture. In a sense they are what SqlOrderGateway aspires to be: all arrows out, zero arrows in — the model of what every component should look like. And from this vantage the taxonomy wars dissolve: unit, integration, acceptance, Cucumber — architecturally, all tests are the same. A three-line TDD test of Order's surcharge math and a scenario reading "a franchisee orders a gluten-free BLT downtown" occupy the identical spot in the dependency graph. The dress code differs; the address is the same.

The Fragile Tests Problem makes the system rigid

Here is the full failure mechanism, not just the bruise. A suite that verifies business rules by driving the GUI — log in, navigate the menu screens, assert on the checkout page — is coupled to the most volatile thing in the system. Marketing asks to reorder the menu navigation for a promo, and a thousand tests about Offer pricing break, though no pricing rule changed. Then comes the perverse second-order effect: the team starts refusing reasonable changes to protect the suite. Tests that were meant to enable change end up vetoing it. And a suite too expensive to maintain eventually gets thrown away — taking your regression safety with it.

Structural coupling — the deepest form

The subtler variant: a test class for every production class, a test method for every production method. Any refactor of production structure now forces mass test edits. The deeper reason this is fatal: tests and production code need to evolve in opposite directions — tests grow ever more concrete and specific (more sandwich scenarios, more shop-by-shop variations), while production code grows ever more abstract and general. Structural coupling welds them together and blocks both evolutions.

The Testing API

The prescribed mechanism has a name the original post never used. Build a dedicated API that the tests use to verify every business rule — a superset of the interactors and adapters the real UI uses, with deliberate superpowers: skip security, bypass expensive resources like the database, force the system into particular testable states. Its purpose is to hide the structure of the application from the tests, so each side can evolve freely:

// ✗ Structurally coupled: mirrors PlaceOrder, breaks on refactor
@Test void execute_happyPath_callsGatewaySaveThenPresent() { ... }

// ✓ Through the ordering test API: states the rule, hides the structure
@Test
void turkeyClubIsPricedFromTuesdaysOffer() {
  testApi.seedOffer(Offer.sampleShopDay());     // no SQL, no SqlOrderGateway
  testApi.forcePaymentSettled();                // no Stripe sandbox

  var receipt = testApi.placeOrder("turkey club");

  assertEquals("$12.40", receipt.totalText());
}
Deployment rule — superpowers need their own boundary

An API that can skip security and mark payments settled must never ride along with production wiring. Keep the testing API and the dangerous parts of its implementation in a separate, independently deployable test-support component that the franchise build simply never contains — so there is no code path by which a live shop could mark an Order paid without going through StripePaymentAdapter.

The fake-gateway unit test from the original post still stands — it is the ground floor of this pattern, and, as promised in section 01, it is also the lie detector for the scream:

@Test
void placesOrderAgainstResolvedOffer() {
  var orders = new InMemoryOrderGateway();
  var payments = new FakePaymentGateway();
  var offers = new StubOfferGateway(Offer.sampleShopDay());
  var placeOrder = new PlaceOrder(orders, payments, offers);

  var result = placeOrder.execute(PlaceOrderRequest.turkeyClub());

  assertTrue(result.isOk());
  assertEquals(1, orders.saved().size());
}

No Spring context, no schema, no sandbox. The day this test needs the @Configuration root to boot, the architecture stopped screaming — whatever the folders say.

11Package by component — the payoff

Screaming folders were the trailer; packaging is the feature film. But before choosing a style, meet the forces. Which classes belong in one component is governed by three named principles in permanent tension: REP — what is reused together must be released together (a component deserves a version number and release notes, so consumers decide when to adopt); CCP — gather what changes for the same reasons at the same times, so one requirement means one redeploy (the SRP restated for components); and CRP — don't force dependents to inherit recompile-and-redeploy pain from classes they never use (the ISP for components — mostly telling you what not to group). REP and CCP grow components; CRP shrinks them. The right position moves with maturity: a young, single-team Silicon Sandwiches belongs at the CCP corner — optimize for develop-ability — sliding toward REP/CRP only when a second franchise product actually starts reusing the offer module.

Three more component principles police the arrows between them. ADP: keep the dependency graph acyclic — one cycle and the components on it fuse into a super-component that must build, test, and release in lockstep (the "morning-after syndrome": you leave working code at night and find it broken because someone upstream moved). Two named repairs: invert the offending edge with DIP — which is exactly what PaymentGateway does, a port owned by the ordering side with StripePaymentAdapter implementing from outside — or extract a new component both sides depend on, say shared money and menu-pricing types. SDP: depend in the direction of stability — and note that stability means hard to move (many inbound dependents), not "rarely changing." The signature violation: someone hangs a dependency on your deliberately flexible component and makes it rigid without touching a line of your code. SAP: stable components must be abstract, so stability doesn't harden into rigidity. SDP + SAP is DIP restated at component scale.

The packaging ladder — and the newcomer's shortcut

Chapter 34 walks the same Place Order use case through four styles. Package by layer: three big horizontal buckets, quick to start, endorsed by tutorials — and screaming nothing. Package by feature: vertical slices that scream the domain, better. Ports and adapters: the inside/outside split with domain names in the ubiquitous language. Package by component: one coarse business area's logic and persistence bundled behind one clean interface, UI kept outside. What separates them in practice is a war story: an eager new hire finds SqlOrderGateway already registered as a bean and wires it straight into SpringPlaceOrderController for a quick order-status page — skipping PlaceOrder and every rule it enforces about resolved offers. The dependency graph stays acyclic; every arrow still points "down"; and the business layer has been silently bypassed. That relaxed layered architecture is occasionally intended (CQRS does it deliberately) but is usually decay — typically discovered the first time a team visualizes its real dependency graph.

Organization versus encapsulation

Why does only the last row hold? Because of the sharpest argument in the chapter: if every type is public, packages are folders — an organization scheme, not encapsulation — and all four styles become syntactically identical: same types, same arrows, four costumes on the same layered architecture. The corrective is precise. In every style there is a small set of types that genuinely needs public — in package by component, just the component's interface: PlaceOrder, Order, OrderGateway. Everything else — SqlOrderGateway, SpringPlaceOrderController, OrderPresenter, the SQL mappers — goes package-private, and now the compiler, not a code review, guarantees nobody instantiates the innards. "Controllers never touch SQL adapters" stops being a review comment and becomes a compile error. Fewer public types, fewer possible dependencies. (The only escape hatch is reflection. Don't.)

That's the top tier of a three-tier enforcement ranking: discipline and code review (proudly claimed, erased by the first deadline), post-compile checks with rules like "types in **/web must not see **/data" (workable, but the feedback loop fires after the pressure has done its work), and the compiler itself — the author's preference for monoliths in one source tree. If you instead split into a two-tree domain/infrastructure build, watch for the named trap: the Périphérique anti-pattern — with all adapters in one infrastructure tree, one adapter can ring-road around the domain and call another adapter directly, like the Paris ring road skipping the city. SpringPlaceOrderController calling SqlOrderGateway, both living comfortably in the same tree, is exactly that road.

Mentor's aside — the map is earned, not drawn

One counterintuitive claim to close the loop: the component diagram cannot be designed top-down on day one. It says little about what the app does — it is a map of buildability, molded to isolate volatility so cosmetic churn never touches high-value policy. With no code, you know nothing about common closure or reuse, and a day-one decomposition would almost certainly produce cycles. The ordering/offer/payments map is earned: CCP co-locates what changes together, CRP starts to matter as reuse appears, ADP repairs cycles as they surface. The graph jitters and grows with the system — and this year's partitioning may be legitimately wrong next year. One more payoff, aligned with our monolith stance: well-defined components in a monolith are the stepping stone to services. If payments must someday become its own service, that is a change of decoupling mode — not a redesign.

12Monday morning checklist

Print this one. Each check traces back to a section above — and every one of them is falsifiable, not a vibe.

  1. The scream (01–02)
  2. Open the top-level packages. Do they scream Silicon Sandwiches — or Spring?
  3. Could a new hire learn every use case from the repo and still not know whether we ship web, kiosk, or console?
  4. Run the abacus test on a rule you touched this week: entity, use case, or presentation — and is it filed there?
  5. The rings (03)
  6. Grep PlaceOrder's imports. Any SQL, Stripe, or Spring names? Any framework-generated data formats (rows, request objects) crossing inward?
  7. Does the use case talk to the presenter through an output port it owns — or does it name OrderPresenter?
  8. Any new SqlOrderGateway(...) outside the composition root? Any subclassing of a volatile concrete class?
  9. The seams (04–07)
  10. Is every view-model field a string, boolean, or enum? Does the view decide anything?
  11. Do the gateways answer named business questions — or expose a generic findBy(criteria) hatch?
  12. For each partial boundary: do we know which side is porous, and what friction signal would trigger the upgrade?
  13. Could each port survive promotion to a process or service — or is it too chatty to ever leave the JVM?
  14. Is the @Configuration root the only place that news up adapters — and could you build a second Main for a new jurisdiction without touching the core?
  15. The details (08–09)
  16. Do any ORM row types travel above SqlOrderGateway? Do any entities extend framework base classes?
  17. Would a gluten-free surcharge ship as a new component wired in Main — or as three coordinated releases?
  18. Keeping it honest (10–11)
  19. Can you unit-test PlaceOrder with fakes and no Spring context? Do business-rule tests drive the GUI anywhere?
  20. Does the test suite mirror production structure class-for-class — or speak through a testing API?
  21. Is each domain module a package with a narrow public API, with adapters package-private — so the newcomer's shortcut does not compile?

If you can check those boxes, you are not "using Clean Architecture" as a slogan. You are keeping the sandwich business in charge of its own source code.

The business rules are the reason the system exists. Everything else — the web, the database, the framework, even the tests — plugs in.
