Chapter 1: Understanding AI Agents On AWS
1

Standard LLMs are powerful but come with limitations, such as knowledge cutoff and the inability to access private or real-time data. This raises the question of how we can provide LLMs with information they don't have, or enable them to interact with the real world. Two key approaches address this without fine-tuning or retraining the entire model: Retrieval Augmented Generation (RAG), which gives the LLM relevant context from your data, and AI agents, which provide the LLM with the ability to reason and use tools to achieve goals.

You may have built a RAG system that can answer questions about you or your organization's data, only to find that your users want more. For example, they want the AI to actually do the work—book a meeting, update a database, or coordinate a complex workflow. Transitioning from a passive "knowledge retriever" to an active "agent" is where many developers struggle. This chapter is important because it establishes the architectural blueprint you need to move past simple chat interfaces and start building "actor" systems that provide real value.

You might find yourself asking: What is the actual difference between a standard chatbot and an agent? How do I move beyond simple prompts to systems that can execute tasks reliably? This chapter addresses these questions by stripping away the hype and focusing on the core architectural components that make an agent functional. Understanding these fundamentals is crucial. Without a solid grasp of how agents think and act, it is impossible to build reliable systems that deliver real-world value.

The journey typically begins with basic LLM capabilities, progresses to handling single-prompt interactions, then evolves into dialogue-based systems such as chatbots, becomes more grounded with RAG-enabled conversations, and ultimately culminates in agents that can reason, use tools, and take action.

Our approach in this chapter is foundational and conceptual. What is RAG and how does it work?

Retrieval augmented generation (RAG) is a technique that enhances the capabilities of LLMs by combining them with an information retrieval system as follows:

Retrieve: The system searches an external knowledge base (e.g., a database, an API, or a document library) for information relevant to the user's query.
Augment: The relevant information (context) is added to the original query and passed to the LLM in a detailed prompt.
Generate: The LLM uses the provided context to generate a factual, accurate, and relevant answer.

Figure 1.1: How Retrieval Augmented Generation works

For example, consider the User Query from the preceding Figure 1.1, Who won the 2024 Nobel Prize in Physics? To answer this, a RAG-based system follows the same three-step process described above:

Retrieve: System queries a real-time news database for 2024 Nobel Prize Physics winner. It finds: The Nobel Prize in Physics 2024 was awarded to Dr. X....
Augment: The system augments or adds the retrieved context with the actual query asked to create a detailed prompt (Retrieved context + Query).
Generate: The LLM receives this fact and uses it to formulate the final, accurate response for the user.

Figure 1.2: RAG pipeline

Let's walk through the pipeline step by step:

Loading or ingesting data: In this step, you will load or ingest the documents you want to query
Chunking: Start by splitting your document or documents into smaller chunks of text. This is important because LLMs have a limited context window, so they cannot process very large documents all at once. Chunking also helps reduce the lost-in-the-middle effect, where important details buried in the middle of a long passage may be overlooked. For example, in a story, the model might miss a character introduced halfway through the text if the entire document is treated as one large block. By breaking content into smaller pieces, the system can retrieve the most relevant chunks and provide the model with focused context for answering the question.
Embedding: Generate an embedding vector for each individual text chunk. These embeddings are the numerical representations of the text's meaning. This is done by an embedding model, for example, the Amazon Titan model.
Storage: Store each text chunk together with its embedding vector in a vector database or vector store. These systems are designed to support similarity search, which helps retrieve content that is semantically related to the user's query. Common examples include Amazon OpenSearch Service, Pinecone, FAISS, Chroma, and PostgreSQL with pgvector. The best option depends on your application's scale, performance needs, and architecture.
Retrieval: When a user asks a question, the system converts the question into an embedding and uses it to search the vector database for the most relevant text chunks. It then retrieves the top k results, where k simply means the number of chunks selected, such as the top 3, top 5, or top 10 matches. These retrieved chunks are the pieces of text most similar in meaning to the user's query and are passed to the model as supporting context.
Filtering and Reranking: This is the process of selecting the most relevant information from a large set of documents to improve the quality of the generated output. Filtering and reranking enhance the quality of retrieved passages in RAG but are optional due to added complexity and computational costs.
Answer generation: After the most relevant documents or passages are identified from a knowledge base, they are passed to the language model, along with the original query. Answer generation is the final step where a language model crafts a coherent and relevant response based on the retrieved information.

What are agents?

The word agent simply refers to someone (or in this case, something) that performs a task on your behalf. AI agents are autonomous software systems that use artificial intelligence to reason, plan, and carry out tasks for humans or other systems. These tasks can range from compiling research and paying bills to planning a trip or managing enterprise applications.

Agents can make decisions, adapt to new information, and take action without needing explicit human instructions for every step. In many cases, they also use RAG as part of their workflow to retrieve and apply relevant information.

What truly makes agents powerful is their ability to think iteratively. They evaluate results, adjust their approach, and continue working toward a goal.

Agent capabilities

So far, we're aware of how RAG strengthens LLMs by adding a retrieval step that allows them to search a knowledge base and use the relevant context to generate more accurate answers. AI agents build on this foundation and take it much further. They make decisions and take actions on their own, even performing complex, multi-step tasks for humans. They achieve this by:

Planning: Breaking down high-level objectives into executable tasks.
Acting: Utilizing tools and information (knowledge bases) to accomplish these tasks.
Reasoning: Observing the results of their actions and updating their plans until the goal is achieved.
For instance, an AI agent could fully automate the process of scheduling a meeting, including checking calendars, sending invites, booking rooms, following up on declines, and updating the meeting details—a task that would typically require a human executive assistant.

Let's break down the key components that make up this architecture:

Tools: These are external functions or APIs that the Agent can leverage to interact with the outside world beyond its internal knowledge. This could include search engines, databases, calculators, code interpreters, weather APIs, RAG, or any other specialized service that can perform specific actions. We are going to cover this in detail in Chapter 2, Building Agents with Tools.
Memory: Stores past interactions over long and short term, which allows it to remember conversations so that the agent can build context and understand the bigger picture. We are going to cover this in Chapter 3, Agent Memory.
Planning: Agents analyze the problem, figure out the best sequence of actions to solve it, and decide which tools to use and when. It's not about random actions, but rather about strategic thinking and careful analysis to get the job done right.
LLM: This is the core intelligence or brain of the agent. An agent consults its LLM (brain) to understand the query, generate potential responses, or determine a course of action such as which tool to call. This is a crucial, bidirectional relationship.
With this view of how agents are structured and how their core components work together, let's see how these concepts map to real-world systems within the AWS ecosystem.

LLM + RAG
The next stage extends the LLM by grounding it in external knowledge through Retrieval Augmented Generation (RAG). Instead of relying only on the model's pretrained knowledge, the system first retrieves relevant information from external sources such as enterprise documents, knowledge bases, or databases, and then passes that information to the LLM as context. This helps the model generate responses that are more accurate, current, and relevant to your domain.

Example: A chatbot that answers employee questions using information retrieved from internal HR policy documents.

There are two common terms which you might hear with RAG: traditional RAG and agentic RAG. Let's understand the differences.

In a traditional RAG system, the flow is usually straightforward:

User query → retrieve relevant documents → send retrieved context to LLM → generate answer. For example, a user asks, "What is our company's leave policy?" The system retrieves the relevant HR policy chunks and passes them to the LLM, which then generates an answer.

Agentic RAG treats retrieval as one tool among many tools available inside an agentic system. Instead of following a fixed one-step retrieval flow, the agent can decide when to retrieve a RAG tool, refine searches, use multiple sources, combine retrieval with tools or APIs, and take actions based on the retrieved information.

Question → agent reasons → maybe call RAG tool → maybe call other tools → answer or act

In agentic RAG, the agent can call a RAG pipeline as a tool. The agent itself is the decision-making layer, and RAG becomes one capability it can use when needed.

Understanding agent protocols

Before we explore large-scale agentic systems, it is important to understand the communication challenges involved in making them work reliably in production. An agent often needs to call external tools, APIs, or databases to retrieve information or perform actions it cannot do on its own. For example, a travel agent asked to book a flight may need to access a flight API, customer profile, and payment service. As the number of tools and workflows increases, teams need a consistent way to connect agents to these external systems. This is the problem addressed by protocols such as Model Context Protocol (MCP), which standardize agent-to-tool interaction.

However, large-scale systems often involve multiple specialized agents rather than a single all-purpose one. A planner agent may delegate work to a booking agent, which may in turn coordinate with a compliance or payment agent. In these scenarios, the challenge is not only agent-to-tool communication but also Agent-to-Agent (A2A) communication.

Agent protocols like A2A and MCP are, hence, needed to standardize communication and interaction between agents, ensuring interoperability and efficient collaboration in multi-agent systems. Let's explore these protocols in detail.

Model Context Protocol

MCP is used for tool discovery in an agent architecture having multiple tools by providing a standard write-once, run-anywhere protocol.

Let's deep dive into the MCP architecture, developed by Anthropic as an open protocol, which provides a standardized way to connect AI models to virtually any data source or tool. Using a client-server architecture, MCP helps developers expose their data through lightweight MCP servers while building AI applications as MCP clients that connect to these servers. MCP uses a client-server architecture that contains the following components:

Host: An MCP host is a program or AI tool that requires access to data through the MCP protocol, such as Claude Desktop, an integrated development environment (IDE), or any other AI application.
Client: Protocol clients that maintain one-to-one connections with servers.
Server: Lightweight programs that expose capabilities through standardized MCP or act as tools.
Data sources: It can be local data sources such as databases and filesystems or external systems available over the internet through APIs (web APIs) that MCP servers can connect to.
Now let's understand the MCP workflow as shown in Figure 1.10 and how it interacts with the LLM to give you a response by using an example of the same travel agent but with a complex ask. You ask the agent to Book a 5‑day trip to Europe in January and we like warm weather. The host application (acting as an MCP client) identifies the need for external data and connects via the protocol to specialized MCP servers for flights, hotels, and weather information. These servers return the relevant data through MCP, which the host then integrates with the original prompt, providing enriched context to the large language model to generate a comprehensive, augmented response for the user.

Let's walk through the sequence of steps involved in this workflow:

A user's natural language request is sent to the MCP host.
The MCP host, using a large language model, understands the request and identifies the data needed (flights, hotel, weather).
The MCP host then uses the MCP protocol to communicate with the appropriate MCP servers, requesting the specific data.

The AI agents within the MCP host then process this aggregated information to fulfill the user's initial request.
This architecture demonstrates a distributed, agent-based approach where specialized agents (MCP servers) handle specific data access, coordinated by a central MCP host and powered by a large language model for understanding and planning.

Facilitates the creation of complex workflows involving multiple collaborating agents.

This diagram illustrates the Agentic Loop (or Agentic Workflow), a process where an AI Agent can take a high-level Prompt, use a Model (like an LLM) for reasoning, and Tools for specific actions, to ultimately deliver a Result.

Let's break down how it works with an example.

The user initiates the process by providing a prompt:

Write a short story about a robot who wants to be a painter.
This is the initial goal the agent needs to achieve:

Invoke agent: The prompt is sent to the Agent. The Agent is the central orchestrator here; its role is to understand the prompt, plan how to fulfill it, and manage the interaction with the Model and Tools.
Agentic loop (Inside the dashed box): This is where the iterative process of thinking and acting happens
Invoke model: The Agent first sends the prompt (or a refined version of it) to the Model. The Model, often an LLM represented by the brain icon, is responsible for:
Get a response: Generating text based on the input.
Reasoning: Understanding the prompt, breaking it down, and deciding on the next steps. For our prompt, the model might reason: To write a story, I need to generate characters, a setting, a plot, and a resolution. I might also need to look up artistic concepts or robot characteristics.
Tool selection: Deciding if any external tools are needed. For instance, if the prompt asked for a story with an image, the model might decide to use an Image Generation API.
Execute tool: If the Model determines that a tool is necessary (e.g., to find information, generate an image, or perform a calculation), it instructs the Agent to Execute tool. The Tools box, with the wrench icon, represents various external APIs or functionalities the Agent has access to (e.g., Image Generation API, Text-to-Speech, Search Engine).
For our story-writing prompt, the Model might initially decide it doesn't need an external tool for the core story generation. However, if the prompt were more complex (for example, Write a story about a robot painter and include an image of their first painting), the agent would use an Image Generation API here.

Return result (from Tool): The executed tool performs its function and sends its Return result back to the Agent
Get response, reasoning, tool selection (from Model): After the tool returns a result, or if no tool was needed, the Agent might invoke the Model again with the updated context or partial result. This forms a loop: the Agent asks the Model, the Model reasons/responds/selects tools, the Agent executes tools, and the results feed back into the Agent, which might then re-invoke the Model. This iterative process continues until the Agent determines the prompt has been fully addressed.
Return final response: Once the Agent has completed its task through multiple iterations of the Agentic Loop, it compiles all the information and the story generated by the Model
Result: The Agent delivers the result back to the user. For our example, this would be the complete short story about the robot who wants to be a painter.
In summary, Strands SDK had 3 core components: model, tools and prompt, and it has an agentic feedback loop which ensures that agents can adapt to dynamic environments, handle unexpected scenarios, and improve their performance over time.

Creating a simple agent

In this example, we import the Agent class from the strands module and interact with the agent by passing a message. The agent processes the input using the underlying LLM and returns a response.

This simple Python example shows how to interact with an Amazon Bedrock Agent using the strands library:

from strands import Agent
# Define the agent with a system prompt
agent = Agent()
# Interact with the agent
response = agent("Explain Amazon Bedrock Agents")
print(response)
The agent is created with a system prompt (or defaults) and then sent a question (in this case, Explain Amazon Bedrock Agents). The agent processes the query and returns a natural language response, which is printed out. This demonstrates how easily you can build conversational AI apps powered by Amazon Bedrock with minimal code.
