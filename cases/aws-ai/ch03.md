Agent Memory

In the previous chapter, you learned the fundamentals of AI agent tools and built an agent that could understand requests, generate intelligent responses, and use tools to complete tasks. That was an important first step: giving an agent the ability to reason and act. However, even a capable tool-using agent remains limited if it cannot remember previous conversations, retain user preferences, or build on past interactions over time. Without memory, every interaction starts from scratch, making the agent feel transactional rather than truly intelligent.

This is where agent memory becomes essential. Memory allows agents to move beyond one-off question answering and into more natural, personalized, and context-aware experiences. With memory, an agent can remember what a user asked earlier, preserve important facts across sessions, adapt responses based on preferences, and maintain continuity in long-running workflows. In practical terms, memory is what transforms an agent from a reactive assistant into a more reliable collaborator.

This chapter is a natural progression from the previous one. Once an agent can use tools, the next challenge is helping it retain and manage knowledge effectively. Using tools gives agents the ability to act, while memory gives them the ability to learn from interaction history and sustain context. Together, these capabilities form the foundation for building robust conversational and task-oriented agents that feel coherent, useful, and increasingly personalized over time.

What is agent memory

Agent memory is an agent's ability to retain past information for maintaining context and improving decision-making capabilities.

For example, let's consider a chat with a travel agent. So, when the user asks the question, what are good places to visit in NYC, the system replies, Times Square is a very common attraction. Similarly, when the user asks a follow-up question, What's the best time to visit it?, the chat agent understands the context that it refers to Times Square and responds back, the best time to visit Times Square is.... From this example, it's clear the agent memory context is giving the agent the ability to recall information and make the conversation seamless.

Why does memory matter?

The three key benefits of having the memory capability are:

Contextual Intelligence: It's not just about storing data; it's about understanding the why and how behind a request. By recognizing patterns in how you work or what you ask, the AI can give answers that are more accurate and relevant to your specific situation. It understands the big picture of your project rather than just treating every prompt as a random, isolated question.
User Preferences: The AI builds a profile of how you like to interact and creates a personalized experience. If you prefer a professional tone, specific formatting, or have previously discussed certain constraints, the AI remembers those details across many different sessions. You don't have to repeat your instructions (for example, always keep it under 100 words) every time you start a new chat.
Knowledge Retention: This is long-term, persistent memory that grows over time and allows for continuous learning. Instead of the AI being static, it becomes a more sophisticated problem-solver the more you use it. It retains information about complex problems you've solved together in the past, allowing it to act as a more knowledgeable partner in the future.
Types of agent memory

When building AI agents, memory becomes a core design consideration. Unlike traditional language models, which are largely stateless and depend on the current prompt and context window, agents often need mechanisms to retain and use information over time. A useful way to think about this is through cognitive architectures such as CoALA, which organize an agent around key functions such as reasoning, action, and memory. For this chapter, the most important idea is that memory is not a single thing. Agents may need short-term memory to track the current interaction, long-term memory to retain stable knowledge across sessions, and episodic memory to recall past interactions or experiences. Understanding these different memory types provides a practical foundation for designing agents that can behave more coherently, personalize responses, and handle multi-step tasks more effectively.

Short-term memory or working memory

This is the agent's short-term scratchpad. It contains whatever the AI is focusing on at this exact moment. This memory is the reason why a chatbot can feel like a natural conversation partner. Instead of treating every message you send as a completely new and isolated event, the AI uses its short-term memory to keep track of the context. For example, in a tool like ChatGPT, the system retains the history of your current session so it can provide answers that actually follow what has already been said. Without this, the AI would forget your previous question the moment you asked a follow-up.

Technically, this is managed through a context window or a rolling buffer. This is essentially a limited amount of space for data; as you continue to talk and new information comes in, the oldest information is eventually pushed out and overwritten to make room.

The main drawback is that this memory is designed to keep a single interaction smooth, but it doesn't save anything once the session is over. Because it resets frequently, short-term memory alone isn't enough for an AI to truly learn about you or remember your personal preferences over a long period of time.

Long term memory

Long-term memory moves the AI agent beyond simple conversations and turns it into a system that can remember your history, understand complex facts, and provide high-level expertise based on everything it has ever learned. It has two major capabilities:

Permanent Storage: Unlike short-term memory, which resets, long-term memory is built using databases or vector embeddings. This helps the AI understand how different pieces of information relate to each other and allows the AI to store massive amounts of history that can be accessed at any time.
Personalization and history: This memory is essential for AI assistants that need to know your background. For instance, a customer support agent with long-term memory can remember that you had a specific problem three months ago. Instead of asking you the same basic questions again, it can tailor its response based on your history, making the interaction personalized, much faster, and more helpful.
According to the CoALA framework, there are three types of long-term memory: Episodic, Semantic, and Procedural. Let's understand these:

Figure 3.3: Types of long-term memory

Episodic memory is what allows an AI agent to look back at its own personal history. It functions similar to human brains, remembering specific life events such as a specific meeting or a past conversation rather than just general facts. For example, memories of your trip to Paris or your birthday.

By recalling these individual experiences, the AI can engage in case-based reasoning. This means that when the AI faces a new challenge, it can look back at a similar situation from its past to see what actually happened. By analyzing whether its previous actions led to a success or a failure, the AI system learns to make much better decisions in the future.

To make this work, AI keeps a structured log of its lifecycle, recording:

What happened (the event)?
Why did it act that way (what was the reasoning)?
What did it do (the action)?
What the result was (the outcome)?
For example, an AI financial advisor uses episodic memory to remember a user's specific investment choices for several years in the past. It doesn't just know about the stock market in general; it remembers your history to provide better, more personalized recommendations.

Semantic memory serves as an AI agent's internal library of structured factual knowledge. While episodic memory focuses on personal experiences and events, semantic memory is dedicated to generalized information—things like facts, definitions, formulas, and universal rules.

In simple terms, episodic memory enables an AI system to remember a specific conversation it had with you, whereas semantic memory helps it know the actual definitions of the words used in that conversation.

To handle this, AI agents use specialized tools like knowledge bases, symbolic AI, or vector embeddings. These technologies allow the agent to organize vast amounts of data so it can understand relationships between concepts and retrieve the right information almost instantly when it needs to solve a problem.

This type of memory is essential for AI systems that require domain expertise. It is often found in high-level applications such as:

Medical tools: Recalling symptoms and drug interactions.
Business systems: Managing company-wide policies and data.
Legal assistants: Legal AI systems using semantic memory to search through thousands of past legal cases and precedents to provide accurate, fact-based advice.
Semantic memory provides AI with a stable foundation of world knowledge, allowing it to reason through complex tasks using facts and rules rather than just guessing based on patterns.

Procedural memory is long-term memory and represents an agent's ability to act, such as encoding skills, workflows, and action patterns (for example: tool usage, reasoning strategies, and step-by-step execution). It persists across sessions, improves with experience, and enables consistent behavior over time. Procedural memory is best understood through motor skills like riding a bike. When you first learn to ride, you consciously think about every step, such as balancing, pedaling, and steering. But over time, these actions become automatic. You no longer remember how to ride a bike, but you simply do it.

In essence, if semantic memory defines what the agent knows and episodic memory captures what it has experienced, procedural memory defines how the agent gets things done.

Challenges with implementing agent memory

Before implementing memory with agents, let's understand the key challenges of implementing memory.

In all, there are six major challenges involved:

Figure 3.4: Challenges with agent memory implementation
Figure 3.4: Challenges with agent memory implementation

Let's understand each challenge in more detail.

Storage scalability issues: As an AI agent interacts with users or performs tasks, the amount of data it generates grows exponentially. Storing millions of high-dimensional embeddings (mathematical representations of text) is expensive and computationally heavy. Developers must figure out how to scale these databases to handle massive amounts of information without the system slowing down or becoming prohibitively expensive.
Memory refresh: Information in the real world and in a user's life changes constantly. Agents need a way to update or overwrite old information with new facts. Deciding what to keep (long-term memory), what to discard (forgetting), and how to update outdated information without corrupting the rest of the memory is a complex balancing act.
Integration complexity: Building an AI agent requires stitching together many different technologies. Connecting a Large Language Model (LLM) to various vector databases, external APIs, and different layers of memory (short-term versus long-term) is technically difficult. Ensuring these systems talk to each other efficiently in real time is a major engineering hurdle.
Privacy and security concerns: Since agentic memory often stores personal or proprietary information, it becomes a high-value target for hackers. If an agent remembers your credit card number or private health data, that data must be encrypted and strictly controlled. There are also multi-tenancy risks, where information from one user's memory might accidentally leak into the responses given to another user.
Retrieval accuracy problems: Storing information is useless if the agent can't find the correct piece of information when needed. When an agent searches its memory, it often finds noisy or irrelevant data that is only tangentially related to the current task. Improving precision (finding exactly what is needed) and recall (not missing anything important) are among the most significant technical hurdles in AI development.
Observability: Observability refers to the ability to see and understand what is happening inside a complex system. It is often difficult for developers to understand why an agent remembered a specific fact or why it failed to retrieve a crucial piece of information. Without clear tools to monitor, trace, and visualize how memory is being used, debugging and improving the agent is very difficult.

Step 2: The agent accesses its immediate working memory or short-term memory to establish context. This includes recent conversational history, current task progress, and the immediate system state relevant to the active session.

Now, let's also try to explore each component shown in the preceding architecture.

AI agent/LLM

It receives inputs, reasons through problems, and decides which memory to access or what action is to be taken. In an AWS context, this would typically be models accessed via Amazon Bedrock (like Claude, Titan, or Llama) or any open-source model such as Meta Llama hosted in Amazon SageMaker.

Short-term memory (context)

This layer stores the immediate history of the current interaction (for example, the last 10 messages in a chat). It ensures the agent knows what was just discussed so it doesn't repeat itself. On AWS, this can be implemented in different ways:

Amazon DynamoDB: A fast NoSQL database used to store session states and recent chat transcripts.
Redis: An in-memory data store used for ultra-low latency retrieval of hot session data.
Amazon Bedrock AgentCore memory: Managed serverless service provided by the Bedrock API to help the model maintain a sense of the ongoing conversation.
Structured long-term memory

This provides the agent with access to factual, relational data stored in traditional formats. If an agent needs to check a customer's recent order or a company's inventory, it looks here. There several options on AWS to build a Structured long-term memory, including:

Amazon Aurora: A high-performance relational database (SQL) for complex, structured data relationships.
Amazon DynamoDB: Used here for massive-scale metadata or historical records that don't require complex joins.
Amazon Neptune: A graph database, used when the agent needs to understand relationships between entities (for example, Which employees have worked on Project X and also know Python?).
Semantic long-term memory (the RAG layer)

It stores general knowledge facts and concepts. This is arguably the most important for modern AI and uses Retrieval-Augmented Generation (RAG). It stores data as vectors (mathematical representations of meaning) so the agent can find information based on concepts rather than just keywords. Several options on AWS to choose your Semantic long-term memory are:

OpenSearch: A search suite used for vector database capabilities to find relevant document chunks.
PostgreSQL (with pgvector): A standard database with a specific extension that allows it to store and search AI embeddings.
Pinecone: A specialized, third-party vector database built specifically for high-speed AI memory and semantic search.
Amazon Bedrock Knowledge Bases: An option for a fully managed serverless option for storing semantic memory provided by Amazon Bedrock.
Durable storage

This is the Data Lake where the original, raw source files are kept before they are processed or indexed into the other memory types. This layer uses Amazon S3 which serves as the foundation for storing raw PDFs, text files, logs, and images that the agent might eventually need to reference or re-process.

Memory orchestration

This is the logic layer that acts as the connective tissue. It determines when to look in short-term memory versus when to query the semantic long-term memory. It consists of the following services:

AWS Lambda: Serverless code that executes specific tasks (for example, Go fetch the user's profile from Aurora).
AWS Step Functions: A workflow orchestrator that stitches multiple tasks together into a complex sequence or chain of thought.
Strands SDK: A specialized software development kit (a specific framework for managing threads of conversation and memory) used to simplify how developers build these agentic flows.
LangGraph: This is a framework for building stateful, multi-step AI agents using a graph-based execution model. It extends the LangChain ecosystem and allows developers to design agent workflows as nodes and edges in a graph rather than as a simple linear chain. In LangGraph, each node represents a step in the agent's reasoning process, such as calling an LLM, executing a tool, retrieving memory, or applying business logic. The edges define how control flows between these steps, including loops, conditional branches, and retries. This makes it well suited for complex, multi-turn agents that require planning, reflection, or structured decision-making. On AWS, LangGraph can be integrated with models hosted on Amazon Bedrock or Amazon SageMaker for inference, while using services such as DynamoDB or Redis for state management and memory. For deployment, LangGraph-based agents can run in AWS Lambda, containers such as Amazon ECS or Amazon EKS, or with Amazon Bedrock AgentCore, which provides managed capabilities for deploying and operating agentic applications.

Context management and memory optimization for agent memory

Effective agentic memory is built on three pillars: Context management, retrieval strategies, and memory optimization.

Context management involves deciding what information stays in the model's immediate context window (also called working memory) versus what is offloaded to external storage.

Just like a human executive, an AI agent can get overwhelmed. If you dump 1,000 pages of data into an AI's context window, it suffers from context rot. It becomes less focused, misses details, and makes mistakes.

The principle of context management is to treat context as a finite, precious resource. As models become smarter, they require less human hand-holding, but they still perform best when provided with a curated, high-signal information environment.

Figure 3.12 shows how an AI agent decides what information to include when responding. This process is known as context engineering:

Figure 3.12: Context window of agent
Figure 3.12: Context window of agent

From a large pool of possible inputs such as documents, tools, memory, and conversation history, the agent curates only the most relevant pieces into the model's limited context window. The model then produces a response or calls a tool, and the results can be stored, summarized, or reused in future interactions. Effective agents succeed not just by knowing everything, but by selecting the right context at the right time.

For developers, optimizing this context window typically depends on three core design pillars:

System prompts: These should strike the right balance—specific enough to guide the agent reliably, but not so rigid that they make the system brittle.
Tools: These should be token-efficient, self-contained, and minimally overlapping so the agent can choose among them without confusion.
Examples (few-shot prompting): These should consist of a small set of diverse, representative examples rather than a long laundry list of edge cases.
When a task is too large for a single context window, for example, migrating a massive codebase, you can use these specialized techniques:

Sliding window is the most common and basic form of context management. It works by keeping only a fixed window of the most recent tokens or messages. Imagine that your context window can hold 10 messages. When message 11 arrives, message 1 is deleted. When message 12 arrives, message 2 is deleted. So, the window of active memory slides forward, always keeping the N most recent interactions.
Compaction: Summarizing the conversation history and re-initiating a fresh context window with only the critical architectural decisions and recent state.
Structured note-taking: The agent writes to a persistent external file (like NOTES.md or a memory tool) to track progress across multiple sessions.
Sub-agent architectures: Using a lead agent to coordinate several specialized sub-agents. Each sub-agent does the heavy lifting in its own context and returns only a concise summary to the lead.
While Compaction tries to summarize the story of the conversation, Note-taking tracks the state of the project. For example, I have completed step 4, step 5 is pending, and the variable name is X.

Now that you have a strong understanding of the strategies and context management, let's see how to achieve memory optimization.

Memory optimization

LLMs have a context window, which is a finite limit on how much text they can process at once. Memory optimization ensures the agent provides the most valuable information without overflowing this window or incurring massive costs.

Intelligent memory management allows AI to behave less like a forgetful goldfish and more like a thoughtful, long-term companion by balancing what to keep, what to summarize, and what to forget.

Some of the strategies, such as sliding window and compaction, help with both context management as we covered in the previous section.

Let's look into some useful strategies for memory optimization:

Sequential (keep-it-all): Every message is fed back into the LLM. It's simple but quickly hits token limits and increases costs.
Sliding Window: Only the last N messages are kept. It maintains speed and relevance but forgets crucial details from earlier in the chat.
Summarization/compaction: This refers to periodically condensing the history into a brief summary and preserves the gist over long periods but can lose specific minor details.
Retrieval-based (RAG): History is stored in an external database such as vector databases. The agent searches for and retrieves only the most relevant past facts to answer a current query.
While many practical agent systems begin with simple memory techniques, advanced applications often require more sophisticated approaches. Memory must do more than simply store past conversations. It must also organize information, reduce redundancy, surface what matters most, and scale across long-running interactions. This has led to a range of more sophisticated memory designs in cutting-edge systems. Some of these approaches include:

Memory-augmented transformers, which use dedicated memory tokens or scratchpad spaces to retain key information.
Hierarchical memory systems organize memory into layers based on immediacy and importance.
Compression and consolidation, which reduce raw text into embeddings, summaries, or clusters of related memories.
Graph-based memory networks, which connect memories through entities and relationships rather than storing them only as a timeline,
Strategic forgetting removes low-value information while preserving the most useful knowledge.
For simple apps, prefer using sliding windows and for fact-heavy apps use retrieval-based (RAG) memory. Similarly, complex/long-term apps often work well with hierarchical or graph-based systems, and for production standard, go with hybrid approaches. For example, a sliding window for immediate flow combined with retrieval-based for long-term facts.

Architectural overview of Amazon Bedrock AgentCore Memory

In the hands-on section, Building a personalized agent with memory, where we built a personalized agent with memory, we used Mem0 to demonstrate how memory can make an agent more personalized and context-aware. Mem0 is a helpful way to introduce the basics of persistent memory because it is easy to integrate and clearly shows how agents can store and retrieve user preferences over time.

As we move toward more advanced and production-ready systems, memory management needs to be more structured, scalable, and secure. Agents must handle short-term context, long-term knowledge, memory extraction, and user isolation in a more systematic way. Amazon Bedrock AgentCore Memory addresses these needs by providing a managed memory architecture for stateful agents. Figure 3.14 shows how AgentCore Memory separates short-term and long-term memory and uses an extraction process to convert interaction events into durable memory records that the agent can reuse later:

The preceding figure illustrates how AgentCore Memory manages the full lifecycle of memory, from capturing raw interaction events to extracting and storing durable semantic memories that can be retrieved in future interactions. This architecture separates short-term working memory from long-term semantic memory, allowing the agent to handle immediate context while also building knowledge that persists over time.

The flow works in stages:

During an interaction, the agent produces raw events, such as user messages, tool calls, intermediate actions, or system responses. These events are first written to short-term memory, which acts as the agent's temporary working area. Short-term memory helps the system maintain continuity within the active session by keeping track of the most recent context, much like working memory in humans.
The next step is handled by the memory extraction module. Rather than copying everything directly into permanent storage, this module reviews the raw events and decides what is worth retaining. It identifies meaningful signals, such as user preferences, goals, important facts, or summaries of what happened, and transforms them into structured memory records. This step is important because it prevents long-term memory from becoming cluttered with low-value details.
Once extracted, these memory records are stored in long-term memory, which is typically implemented as a vector store to support semantic search and retrieval. This means the agent can later retrieve memories based on meaning and relevance, not just exact keyword matches. Over time, this gives the agent a growing body of useful knowledge that can inform future responses, improve personalization, and support more consistent decision-making across sessions.
This architecture addresses one of the most important challenges in agentic AI: state management. Without memory, an agent treats every interaction as independent, making it difficult to preserve context, maintain continuity, or build on prior exchanges. By contrast, this design allows the agent to capture granular activity as events, keep recent interactions in short-term memory, and ensure that runtime behavior remains aligned with stored state.

Understanding this high-level flow is important because it shows why memory is needed. The next step is to look more closely at how memory is structured in practice, starting with short-term memory.

Understanding Amazon Bedrock AgentCore short-term memory

Short-term memory is the part of the system that preserves immediate conversational context, tracks active interactions, and keeps different users and sessions isolated from one another.

To support this, Bedrock AgentCore organizes short-term memory around a few foundational concepts: events, actors, and sessions. Together, these components define who is interacting with the system, what happened during the interaction, and how those interactions are grouped over time.

In AgentCore Memory, each event is associated with an Actor, which identifies who the memory belongs to. An actor can represent a specific user or a user–agent combination. This ensures memories are properly separated, organized, and scoped to the correct identity, preventing cross-contamination of context across users.

In the middle, the agent creates events during the interaction, such as chat messages or other data in JSON form. Together, these components form a structured memory architecture where Events capture what happened, Actors define who it belongs to, sessions define when and within which conversation it occurred, and Short-Term Memory maintains the active working context that keeps the agent stateful and coherent.

To recap, AgentCore short-term memory keeps an agent's active conversations organized and consistent. By using actors, sessions, and events, it stores chat history, temporary state, and checkpoints, allowing the agent to preserve context, resume interrupted interactions, and maintain continuity across turns. Now, let's dive deep into Amazon Bedrock AgentCore long-term memory.

Memory strategies, namespaces, and long-term retrieval in AgentCore Memory

So far, we have focused on how AgentCore Memory captures and manages short-term conversational state. That explains how an agent keeps track of what is happening right now. However, short-term memory alone is not enough for agents that need to remember important facts, preferences, and outcomes across longer periods of time. To support this, AgentCore Memory provides a structured mechanism for extracting useful information from ongoing interactions and storing it as long-term memory.

This is where memory strategies and namespaces become important. Memory strategies determine what kinds of information should be remembered and how that information should be processed, while namespaces determine where that memory should be organized so it can be retrieved in the right context later. Together, they allow developers to move beyond storing raw conversations and instead build a memory system that is selective, structured, and searchable.

In the next section, we will cover the role of namespaces in organizing long-term memory, examine the three types of memory strategies supported by AgentCore Memory, and discuss how the memory extraction module converts raw interaction events into indexed, retrievable knowledge.

Namespaces

Namespaces allow developers to partition memory. For example, you might have one namespace for user preferences, another for past project details, and another for general facts. This ensures the agent doesn't get confused by mixing up different types of information.

The power of namespaces lies in their ability to zoom in or zoom out on data:

Global level (/): It stores universal knowledge, such as company-wide compliance rules or security protocols, that every agent must follow regardless of the user.
Strategy level (/strategy/{strategyId}): This stores domain expertise. For example, a medical agent would have a strategy namespace for anatomy facts. It is shared across many users but limited to a specific topic.
Actor level (/actor/{actorId}): It stores user preferences and recurring behavior patterns. When an agent queries this namespace, it remembers who you are and how you like to work.
Session level (/session/{sessionId}): It stores session summaries of specific conversations (for example, Ticket #456). This ensures the agent knows exactly what was discussed ten minutes ago versus ten months ago.
Memory strategies

When creating or updating an AgentCore Memory, developers can define one or more memory strategies to control how long-term memories are extracted and organized. These strategies determine what information is retained, how it is structured in namespaces, and how it is processed when events are added. If no strategy is configured, long-term memory is not extracted.

Amazon Bedrock AgentCore supports three strategy types:

Built-in strategies, which provide fully managed extraction for common use cases such as summaries, user preferences, and semantic knowledge.
Built-in overrides, which allow limited customization of built-in strategies while preserving the managed pipeline.
Self-managed strategies, which provide full control over the extraction and memory management process.
A single memory resource can use both built-in and custom strategies simultaneously, allowing flexible and tailored memory management.

Memory extraction module

The memory extraction module is responsible for turning raw short-term events into useful long-term memory. Based on the selected strategy, it runs asynchronously to extract important details, merge them with existing knowledge, and index the results for semantic search.

Now, let's see how the memory extracting module works per strategy (see Figure 3.16):

Figure 3.16: AgentCore Memory extraction between short-term and long-term
Figure 3.16: AgentCore Memory extraction between short-term and long-term

The system begins with short-term memory, where raw interaction events are continuously captured. Rather than immediately storing everything, a Memory Extraction Module runs asynchronously based on a strategy trigger, either every K messages (currently K=12) or after X seconds of inactivity (20 seconds if fewer than 12 events are received).

When triggered, the module performs Extraction, which identifies and pulls meaningful information from the raw interaction stream. The extracted information then moves to Consolidation, where it is merged with existing knowledge in AgentCore Memory. During consolidation, the system may add new information, update existing entries, or skip storage if the information is not meaningful or redundant. Unlike extraction, a session summary only performs consolidation because it operates on already structured content.

After consolidation, the memory is converted into embeddings and indexed, allowing it to be stored in long-term vector storage. The system can also retrieve similar memories during consolidation to prevent duplication and maintain coherence over time.

Overall, this design ensures that memory formation is structured, not duplicated, efficient, and balances real-time interaction capture with durable, searchable long-term memory.

Bringing it all together

To understand how AgentCore Memory builds useful long-term memory, it helps to see how three pieces fit together. Memory strategies specify the type of knowledge the system should preserve, the memory extraction module transforms raw short-term events into structured memory records, and namespaces organize those records so they can be stored and retrieved in the correct scope. Figure 3.17 shows how these components work together to move from short-term event capture to long-term semantic retrieval. It shows how memory flows through the system from short-term storage to long-term retrieval:

Figure 3.17: AgentCore Memory extraction module

Next, after a certain number of turns, automatic extraction runs and converts those raw events into a more compact semantic summary.
