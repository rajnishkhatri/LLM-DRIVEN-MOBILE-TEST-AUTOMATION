# mobile-test-automation-ash-capture — Tasks

**Status: PLAN-OK 2026-08-01** (gate closed with the plan; see `mobile-test-automation-ash-capture.plan.md` §7). The ASH repo is a **standalone Maven reactor + two Spring Boot deployables** (proposer co-located as a separate OS process over the localhost channel — plan-gate fork 1) consuming published `spine-contracts` and `screening` as versioned dependencies (owner decision 2026-08-01). Task IDs are `A01…A45` to keep the spine board (T01–T43) untouched.

**Order:** A01–A05b (WP-A0, strictly first — M18) → A06–A09 (WP-A1 contracts/config) → {A10–A18 (WP-A2 graph schema+writes) ∥ A19–A22 (WP-A3 screen-gate)} → {A23–A30 (WP-A4 arrival engine) ∥ A31–A38 (WP-A5 topology+credentials) ∥ A39–A45 (WP-A6 admission)} → gate.

**Critical path (plan-gate fork 2 — front-load the D-A/write core):** the sequenced spine is **WP-A0 → WP-A2 (schema+write) → WP-A4 (arrival) → the WP-A2 write path (A14–A18, A29)** — this chain delivers Lane-3 **S1** (the loop terminates on changed screens; the A30 changed-screen falsification) and unblocks the **S2 measurement spike** soonest. WP-A5 (topology/credentials) runs in **parallel off WP-A0** (disjoint surface), so front-loading the write core costs nothing there. WP-A3/WP-A6 follow their own dependencies. Do not chase topology ahead of the write core — S1 stays incomplete until the arrival verdicts can commit and replay.

Every task carries its file-level touchpoint, dependencies, a `[parallel]` marker where it runs concurrently with a sibling in another WP, the EARS criteria it satisfies **by name**, and an explicit pass/fail verification. Load-bearing verifications use the **T02 two-half method** (a named ArchUnit rule + a named runtime assertion, each proven by a deliberately-violating sample that fails the build and is then removed) for CS1–CS7, and Testcontainers proofs for the DB-enforced invariants.
