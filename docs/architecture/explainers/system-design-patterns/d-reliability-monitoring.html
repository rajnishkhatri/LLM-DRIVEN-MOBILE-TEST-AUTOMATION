System design patterns · Group D · Reliability & monitoring

Seeing Enough to Page

You cannot operate what you cannot see. First name the signals, then collect them on the device and on the server, join them across hops, and only then decide which burn rates deserve a page.

Audience Engineering & architecture Reading time ~14 min Status Explainer — catalog group D
How to read the colours: Verified mechanic / default Judgment / trade-off / when-not Operator or product decision Uncertain in the source

A checkout can return 200 while the user’s main thread is frozen. The load balancer can be green while the payment pool is queued. The Collector can drop the record of that night while the product stays up. Operating that system is not “having three stores.” It is four jobs, in order.

Name the signals so every card means the same thing by metric and trace. Collect them where the user sits and where the server works — those are different courts. Join one request across hops so the three signals are one investigation. Then decide, as policy, which spend of the leftover unreliability should wake a human.

You cannot operate what you cannot see: which signals exist, where they are collected, how they join across hops, and which burn rates deserve a page.

If you remember only that sequence, the rest of this piece is why each job is a different owner — and why collapsing them produces a dashboard that replaced the feedback loop.

PART ONE · FOUNDATIONS

01Name the signals first

Monitoring is collecting, processing, aggregating, and displaying real-time quantitative data. Observability is inferring internal behaviour from external outputs — a data-management problem first. Having three stores does not make a system observable. The quality attributes in play are diagnosability (you can name what broke and why), operability (pages are urgent, actionable, and user-visible), cost (cardinality is both the bill and the correctness bound), and reliability of the telemetry path itself.

This group’s first owner is vocabulary. A metric, a log, a trace, and a profile mean one thing from here on. Client RUM, server dashboards, trace propagation, and SLO math consume those definitions; they must not re-derive them. Breaker dashboards are placement of these signals — state, trip rate, not-permitted calls — not a fourth type.

OpenTelemetry’s word is signal, not pillar: system outputs that describe the underlying activity of the operating system and applications. Each signal is built on context propagation. Specification 1.60.0 (released 2026-08-07): tracing, metrics protocol, logging bridge, and baggage API/SDK are stable; the metrics SDK is mixed; profiles protocol is development. Semantic conventions are 1.44.0. OTLP 1.11.0 is stable for traces, metrics, and logs.

Three frameworks compose; they are complementary views of the same system, not competing scorecards. RED (Rate, Errors, Duration) is for every service — are users having a bad time? USE (utilization, saturation, errors) is for every resource — which pool is the bottleneck? The four golden signals — latency, traffic, errors, saturation — sit on a user-facing system. Wilkie treats them as RED plus saturation: user happiness joined to machine happiness. Golden saturation is the join — a service-level fullness measure that USE would have found per resource.

Semantics that later cards must keep

Latency is time to service a request — split successful versus failed, and never design around the mean. An average of 100 ms at 1 000 QPS can hide 1% at 5 s; that p99 becomes the median of a frontend that fans out. Collect counts bucketed by latency; never average percentiles. Traffic is demand in a system-specific unit. Errors are explicit (HTTP 500s), implicit (HTTP 200 with the wrong content), or by policy (a 1.2 s success against a one-second commitment). Load-balancer 5xx miss wrong-content 200s; classify 4xx / 5xx / 429 before counting — the same table the breaker already owns. Saturation is fullness of the most constrained resource; systems degrade before 100% utilization. p99 over a short window, and “the disk fills in 4 hours,” are leading indicators. Shed and 429 reject latency must not enter the success histogram; a degraded path needs its own RED. USE stays Gregg’s checklist: utilization is busy-time; saturation is extra work that cannot be serviced (any non-zero can be a problem); errors include recovered ones.

Cardinality is the correctness bound

Cost scales with unique attribute combinations, not request volume. The OpenTelemetry Metrics SDK default limit SHOULD be 2000. Overflow is not dropped: it folds into one point tagged otel.metric.overflow=true. Totals stay correct; filtered queries undercount. A counter labelled {url.path, success} that overflows will fold {url.path=/checkout, success=false} into that point — the error-rate alert goes silent while the total looks healthy. Put user ID, request ID, raw path, and build SHA on logs, traces, or exemplars. On metrics use method, route template, status class, service, instance. A 100% metrics series plus a 1% trace sample is a deliberate fidelity split; D4 owns the sampler.

Verified mechanic · when a page is justified

D5 owns SLI/SLO documents, error budgets, and multiwindow burn-rate math. D1 owns when a page is justified, so D5 does not invent a different paging philosophy. A page detects an otherwise undetected condition that is urgent, actionable, and actively or imminently user-visible. Every page requires intelligence — a robotic response should be automated. Symptom over cause: “what’s broken” versus “why.” Causes belong on dashboards and in traces. Black-box paging forces discipline; white-box catches imminent saturation and failures masked by retries. Email alerts are alert spam. Keep the paging path simple — limited success with deep dependency hierarchies and “magic” threshold learners.

Signals without trigger, owner, and action are a dashboard that replaced the feedback loop. Start with RED histograms, USE on the bottleneck resource, and a Watchdog. You do not need every OpenTelemetry signal before the first dashboard.

The pipeline is a dependency

A Collector that drops on overflow is fail-closed for telemetry and fail-open for the product: the request succeeds, the record does not. Decide that explicitly. Documented defaults: queue 1000 (requests, not spans), 10 consumers, drop on overflow; retry 5 s → 30 s at 1.5×, max_elapsed_time 300 s. Self-metrics scraped only on localhost never reach the Prometheus that pages you; the legacy collector health endpoint is documented as not working as expected. Watch accepted versus sent and enqueue-failed. Sustained refused means the client was told no. The Watchdog is an alert that is always firing, routed to an external heartbeat: its absence is the only reliable signal that the paging path has died.

PART TWO · THE TWO COURTS

02The device is a different court

Server metrics tell you the backend survived. Client-side monitoring tells you whether the user device did: the page painted, the tap painted, the process stayed alive. A 200 from checkout and a frozen main thread are compatible facts. This is first-party observation of browser and mobile experience — RUM, Core Web Vitals, JavaScript exceptions, crash, ANR, hang — so a release that is green on the server can still be red where the user sits.

It is not a capacity control. A RUM snippet does not shed load, trip a breaker, isolate a pool, or flip a kill switch. Those act. This card sees. D1 still owns the taxonomy: the client only instantiates those types. A browser p75 is not a server p99. Session-to-trace correlation is D4; burn-rate math is D5. p75 CWV and Play 28-day DAU rates are candidate SLIs, not a paging policy.

Field measurement has two populations that must not be treated as interchangeable. CrUX is eligible Chrome users who opted into usage statistics, on publicly discoverable and “sufficiently popular” origins, over a rolling 28 days, about two days behind. It tells you whether a public URL or origin passes Core Web Vitals at p75 — not why. First-party RUM is whoever your snippet reaches, minus consent, blockers, and sampling; it can attribute which element, which interaction, which navigation, which session. Lab (Lighthouse, DevTools, WebPageTest) has no real user, so INP is not measurable there — Total Blocking Time is the documented proxy. Lab cannot stand in for field INP or lifespan CLS.

A page or origin passes Core Web Vitals only if all three meet “good” at p75, reported mobile and desktop separately. INP replaced FID on 2024-03-12. CLS is the worst session window, not a lifetime sum. Finalize INP and CLS on visibilitychange; mobile often skips unload, so a keepalive beacon is the transport. Soft navigations are off unless opted in — they diverge first-party RUM from Search. Two JavaScript OpenTelemetry stacks do not emit the same signals: legacy auto-web is spans only (no CWV, no exceptions, no sessions); the newer browser SDK emits browser.web_vital and exception events — metrics are out of scope. Do not average two CWV implementations. Do not treat CrUX green as a reason to skip first-party RUM.

Play’s user-perceived ANR is input-dispatch of 5 seconds. OpenTelemetry Android’s device.anr is a foreground 1 s × 5 poll — not that definition. Prefer crash-free sessions on a fixed post-release window; crash-free users shrink as the window lengthens by construction. Opt-in-only collection makes the charts optimistic or near zero — a monitoring failure, not an app-quality signal.

Judgment · client-shaped alerts

Alert on field p75 or Play’s 28-day DAU rate — never a single pageview or a Lighthouse score. Tight “N of M minutes” burns mis-fire because client series are sparse, consent-biased, and finalized late. A RUM-volume drop with stable server traffic is a monitor outage, not a quality win. Consent and sample-rate changes are deploys: they move the denominator. Burn-rate and paging policy stay in D5.

03Four stacked views of one server

The complementary question on the server is: what is the distribution of user-visible work, and is a human needed? A probe is a binary routing or restart decision. A golden-signal pipeline is histograms, counters, saturation, and paging. Crossing them produces the two classic failures already on the health-check card: a shallow TCP check that black-holes traffic onto empty 200s, and a deep dependency check in the load-balancer path that takes the fleet out when one shared backend blinks.

Treat a production instance as layers. Host, process, and runtime take USE. Inbound RPC takes RED — the inbound histogram, not host CPU. Saturation is not utilization: any queued extra work is already a problem, and five-minute CPU averages at or below 80% can hide 100% bursts. Wilkie’s shape is one duration histogram, but status as a label multiplies buckets × codes × routes. Prefer a route template and an explicit error predicate — status_code!~"2.." pages on 401/404/422. Prometheus DefBuckets top out at 10 s and omit the extra OpenTelemetry HTTP boundaries; put a bucket on the SLO threshold or interpolation lies.

Prometheus’s software default scrape is 1 minute (timeout 10 s), not the tutorial’s 15 s. Alert for: defaults to 0 s — first-evaluation fire. Alertmanager: 30 s / 5 m / 4 h. Data more than four to five minutes stale “might significantly impact” incident response. After a failed scrape, series go stale — blank, not flat. up is scrape reachability, not correctness: a process can export up=1 while every request is 500. Page one global error-rate or latency page, not one per node; inhibit children when the dependency is already firing. Saturation is the exception: page when a signal is nearly problematic, because black-box users have not broken yet.

Verified mechanic · the cut with D5

This section may cite workbook mechanics so an implementer can wire rules. It does not pick the objective. Multi-window AND, short window ≈ 1/12 of long, page at 14.4× and 6×, ticket at 1× — those numbers are D5’s to accept or reject. Wiring the shape without accepting the thresholds is unfinished work, not a default.

PART THREE · THE JOIN

04One request, one forest

Metrics tell you that p99 moved. A sampled trace tells you which hop. Correlation is joining logs — and exemplars — onto the same trace_id so the three signals are one investigation, not three timestamp-matching sessions. Traces diagnose a page; they are not the SLO. Timeouts bound the call and propagate remaining time; this card only records the remaining budget as a custom low-cardinality duration attribute. There is no standard OpenTelemetry name for “deadline” in semantic conventions 1.44.0.

A trace is a forest of spans that share one 128-bit trace-id. A span is one unit of work: name, immutable SpanContext, parent, kind, start/end, attributes, events, links, status. Status is UNSET, OK, or ERROR. Kinds: CLIENT, SERVER, PRODUCER, CONSUMER, INTERNAL. Attributes present at creation are the only ones a sampler is guaranteed to see. HTTP span names should be {method} {target} when the target is a low-cardinality route template; instrumentation must not default to the raw URI path. Raw /user/123 names are a spanmetrics outage waiting for a deploy.

The interoperable default is W3C Trace Context Level 1: fixed-length traceparent plus tracestate. The sampled flag is a recommendation, not a mandate. Default OpenTelemetry propagators: tracecontext,baggage. A fleet that only configures W3C drops context at an OpenCensus gRPC peer still speaking grpc-trace-bin. Baggage is a separate header — the only standard way to carry tenant, debug, or canary bits without putting them on every span, and a PII channel. Prefer a short allow-list; never user identifiers; clear it at trust boundaries.

Head sampling is cheap and complete-or-absent — and biased against rare 5xx because the decision is made before status exists. Wrap ratio samplers in ParentBased; bare TraceIdRatioBased is deprecated for ProbabilitySampler. Health-check and /metrics roots should be AlwaysOff. There is no SDK TailSampler: the contrib processor (beta) waits 30 s, caps 50 000 traces, and requires every span on the same collector instance. Head-sampled-away errors never reach the tail policy. Logs SDK trace_based=true silently drops debug logs on unsampled requests. Collector span.processed is hand-off, not persist success.

Tool-neutral defaults: W3C headers on every hop that can carry them; baggage only for a short allow-list; ParentBased plus ProbabilitySampler at roots; inject context on every queue message; put trace_id/span_id on every log line; record remaining deadline as a duration. The 128-attribute count limit does not fix high-cardinality values.

When not to install the forest

A single process with local logs; a batch job whose unit of work is not a request; hops that cannot carry headers and will not be changed; a compliance boundary that forbids request-scoped identifiers from leaving a trust zone. Then D1 metrics plus D3 logs are enough. Do not install AlwaysOn plus tail sampling “just in case” on a latency-critical path without a budget. Default parentbased_always_on at high QPS saturates the backend, then operators disable tracing — Dapper’s original fear. If you derive RED from spans, treat it as a sampled estimate.

PART FOUR · POLICY

05Which burn rates deserve a page

An SLO is a target on a carefully defined SLI. The error budget is the leftover unreliability. Alerting policy is how you notice spend while budget remains. An SLA is the same idea with consequences; if nothing happens on a miss, it is an SLO. D3 wires the path; this card picks the objective. Breakers and retries feed the SLI — they are not the SLO. 429s are a product choice for the denominator; shedding and degradation are how you spend budget on purpose.

Preferred SLI: good events / total events. Example: 99.9% over four weeks and 3 000 000 requests → 3 000 allowed errors; a 1 500-error hole spends 50%. The specification is the user outcome; the implementation (logs vs probers vs in-page JS) changes quality and coverage. Server logs miss never-arrived requests; in-page JS is closest to the user and gives telemetry its own reliability requirement. Start with five or fewer SLI types and a four-week rolling window. Count well-formed requests only: 5xx, timeout, connect fail, UNAVAILABLE / DEADLINE_EXCEEDED are bad; 4xx, 401/403, and caller cancel are not. Start with the Workbook’s 5xx-only — do not silently adopt 5xx|429. An HTTP 200 LLM refusal is a quality SLI, not availability. Traffic is not an SLO you choose. Golden signals are not a fifth SLO.

Low traffic breaks the math: 10 requests/hour, one failure = 1 000× burn versus 99.9%. Options: synthetics, combine services, change the product, or lower the SLO. Do not invent per-microservice windows — bucket request classes. NO_SLO is sourced for dark launches and alpha. Yield can spend the same budget as a four-hour hole, four one-hour holes, or a 0.5% drip — different happiness. The extra-9 thumb-rule: unique critical deps one nine tighter; count each once. If a dep cannot meet it, cache, queue, or degrade. Do not overachieve — Chubby synthesizes a controlled outage in any quarter that has not naturally spent the budget.

Operator decision · the teeth

Without an approved freeze policy the SLO is “another KPI.” Appendix B: four-week budget exhausted → halt all changes except P0 / security until back in SLO. One incident over 20% of four-week budget → postmortem with a P0 action. Write the shared-fate exceptions down before the first freeze (company-wide network, another team’s frozen dependency, out-of-scope load, miscategorized errors with no user impact). Table 2-5 is how you learn the number is wrong: met + low satisfaction → tighten; missed + high satisfaction → loosen. Do not copy current performance without that review loop. Do not set an SLO you cannot win a priority argument with. Do not page to defend five nines. Do not set 100%.

OpenTelemetry is instrumentation — raw material, no SLO resource. OpenSLO v1 is a policy object, not an instrumentation standard. Neither is the other. Fail-open guardrails still look healthy: they burn a safety or quality budget while availability stays green. Fail-closed burns the product budget on purpose. Instrument both. Do not fold a synchronous judge into the user latency SLO unless it is on the path. Metamonitoring: prefer an end-to-end “alert was delivered” black-box over per-component causes. The metrics pipeline is a critical dependency; without an extra nine and a Watchdog, you learn from Twitter.

Failure modes of monitoring itself

The monitor is another production system. The Concepts name the ways it lies, in the same sequence as the story:

  • Cardinality overflow hides the page. Totals stay correct; filtered labels undercount. Detect otel.metric.overflow=true.
  • Mean latency / unsplit success+error latency. Fast 500s make the service look faster as it gets worse.
  • Implicit and policy errors invisible to the load balancer. HTTP 200 + wrong body; SLO-late successes.
  • Population bias and denominator clash. CrUX ≠ RUM ≠ Play DAU ≠ Crashlytics session. Play’s 100% versus 33% example is the trap.
  • Beacon loss and next-start crash reports. A silent collector 429 looks like a perfect release. Pair volume with server traffic.
  • Alert fatigue. Bigtable SRE paged on synthetic mean plus email as the SLO approached and missed user-visible failures. Gmail paged on every de-scheduled task; the durable fix was automating the rote poke.
  • Pipeline drop = silent product success. Default Collector queue drops at 1000 in-flight requests. No Watchdog → you will not be paged when Prometheus dies.
  • Head sampling the tail away and tail policies that keep only errors (the stored corpus looks like the system is always on fire).
  • Three-store hop without correlation IDs. Metric with no exemplar, log with no span_id.
  • Event-ratio blindness to outage shape and nines arithmetic on correlated deps. Same spend, different pain. Shared fate breaks the product.
  • Guardrail fail-open. Availability stays green; safety should have burned.
  • Observability that replaced the feedback loop. Signals without trigger, owner, and action.
◆ Uncertain in the source — do not treat as defaults

07Parked, not decided

Everything above this line is a claim the five Concepts actually make. What follows is marked Uncertain, development, or not-yet-Recommendation in those same sources. Do not promote any of it to a fleet SLO or a paging default.

◆ Uncertain · D1

Profiles. The Profiles format is development as of 2026-09-13 (pprof-based; OTLP path /v1development/profiles). Events as a log subtype are under development or proposal. Do not treat either as equivalent to traces, metrics, or logs.

◆ Uncertain · D1 / D4

W3C Baggage is a Candidate Recommendation Snapshot, 2024-05-30 — not a Recommendation. OpenTelemetry’s own line: “Baggage is not an observability tool”; there is no OTLP component. Trace Context Level 2 (random-trace-id flag, 56-bit randomness that ProbabilitySampler depends on) is still a Candidate Recommendation Draft (2024-03-28).

◆ Uncertain · D4

Messaging semantic conventions are Development as of v1.44.0 — do not freeze create/send/process structure as stable. Mesh default header sets were not re-fetched; do not assume one. The tail sampler itself is beta.

◆ Uncertain · D2

OTel browser-sdk 0.4.0 is experimental; metrics are out of scope; default OTLP is localhost. Android instrumentation remains alpha (agent API stable since 1.0.0). The iOS OpenTelemetry Swift crash/hang emit list was not verified from a README — use MetricKit. WWDC26 session 222 claims iOS 27 MetricKit diagnostics are delivered immediately; older guidance was ~24 h delay.

◆ Uncertain · D5

OpenSLO v1 AlertPolicy allows one condition (issue #218) and cannot express Workbook iteration-6 AND/OR without an extension. Burn-rate 14.4 / 6 are not in that spec. Sloth generated sloth_version dev on the fetched page — no release version claimed. No numeric eval-score threshold is sourced.

Name the signals. Collect them on the device and on the server. Join one request. Then decide — as policy, with teeth — which burn rates deserve a page.

Health checks decide whether this instance receives work. Golden signals decide whether a human is needed. Traces decide which hop to open. The SLO decides how much unreliability you are allowed to ship. Do not collapse the four.
