§01Module Introduction

Concept§01 · Screen 1

Four decisions before you build

Designing a Claude solution is not "pick a model and start coding." The module's whole argument is that four decisions come first, and everything you build inherits them. One: what part of the work should Claude own — as opposed to an existing system or a human? Two: what shape is the work — a person being helped mid-task, a workflow with known steps, or an agent that decides its own path? Three: which reference architecture are you committing to — named up front, so you don't pay for an expensive pivot later? Four: where does the work touch Claude — which entry point, model tier, and context strategy?

The course threads one scenario through all of it: an enterprise partner in a regulated industry, where the design that demos flawlessly is the same one whose misroutes an audit digs up a quarter later. The skill being trained is not memorizing stages — it's recognizing which decision is in front of you, because each one rewards a different move.

  • Worth memorizing
  • The most common and most expensive early mistake is over-assigning work to Claude.
  • An eval is the stage-gate before any model swap.
  • Governance can rule out a delivery route before any cost or latency tradeoff applies.
  • This module teaches the decisions above the code — it never asks you to write production code.

For the exam: given a scenario, first name which of the four decisions it is testing. The move that wins decomposition (splitting ownership) is not the move that wins entry-point selection (following constraints in order).

§02How Claude Behaves

Concept§02 · Screen 2

The four properties architects design around

Before deciding what Claude should do, you need to know how it behaves. The course names four properties — next-token prediction, knowledge, working memory, and steerability — and insists on one framing: each is a capability paired with a limitation, and neither half goes away. You design around them the way a structural engineer designs around the properties of building materials. Nothing here is a flaw to fix.

Each property carries a design consequence that later sections pick up. Non-determinism means the same input can produce different outputs — which is exactly why evaluation frameworks exist. Context is a finite resource with a hard token budget, so what goes in, in what order, is a design decision. Confidence is not validity: wrong answers arrive in the same assured tone as right ones, so verification and human checkpoints are architecture, not afterthoughts. And knowledge has boundaries: reliable on the common, recent, and consistent; unreliable on the rare, private, and fast-changing — where an external source of truth takes over.

The screen closes with a story: a demo ran cleanly five times, so the team shipped a financial reconciliation pipeline with no checks. In week two of production, the same statement re-processed into a different categorization — found only because an analyst happened to re-run a batch. The lesson is about the architecture, not the model: five clean runs prove nothing about determinism.

  • Worth memorizing
  • The four properties by name: next-token prediction, knowledge, working memory, steerability.
  • Hallucination risk concentrates on names, dates, citations, and statistics — route those through tools or authoritative sources.
  • You cannot certify behavior you observed once. (Five clean demo runs ≠ determinism.)
  • Reliable on common / recent / consistent topics; unreliable on rare / private / fast-changing ones.
  • Mitigation kit for precision failures: citations, uncertainty signaling, generator-verifier loops, tool calls.

For the exam: recognize each property by name and pair it with its consequence. An unacknowledged property produces no error message — the system drifts quietly and the gap surfaces in an audit, not in monitoring.

§03Platform Map & Primitives

ConceptReconstructed§03 · Screen 3

Entry points, build-time interfaces, and delivery routes

Reconstructed — this course screen wasn't captured in the source notes. Rebuilt from: the layer tables preserved in the §10 entry-point notes, plus the layer-sorting checkpoint.

One map, three layers — and each layer answers a different question. Entry points are what a person interacts with: the Claude.ai apps (web, mobile, desktop), Claude Code, Cowork, Claude in Chrome, and Claude for Excel. Build-time interfaces are what an engineer programs against: the direct API, the SDKs, MCP, and the Agent SDK. Delivery routes are where API traffic terminates: Anthropic's own endpoint, AWS Bedrock, Google Vertex AI, or Microsoft Foundry. The mnemonic that survives: who interacts, how code reaches Claude, where the request runs.

Collapsing the layers is the classic architecture error. "We'll use Bedrock" sounds like a design, but it only answers where — it says nothing about which surface the user touches or what the team codes against. Likewise MCP is not a product a person opens, and Claude Code — developer-flavored as it is — belongs with the entry points, because a person drives it. The model behaves identically on every route; a route changes the billing account, the identity system, and the region, never the intelligence.

The layers also stack inside a single request: a user works in an entry point, the code behind that surface speaks a build-time interface, and the resulting traffic terminates on exactly one route. Keep the three questions separate and most platform scenarios answer themselves.

  • Worth memorizing
  • Entry points (person interacts): Claude.ai apps, Claude Code, Cowork, Claude in Chrome, Claude for Excel.
  • Build-time interfaces (engineer programs against): direct API, SDKs, MCP, Agent SDK — they layer on one another; they are not always alternatives.
  • Delivery routes (traffic terminates): direct Anthropic API, AWS Bedrock, Google Vertex AI, Microsoft Foundry.
  • A route changes billing account, identity system (Anthropic key / IAM / Google credentials / Entra ID), and region — never model behavior.
  • CSP-mediated routes (Bedrock, Vertex, Foundry) lag the first-party API on new features by weeks, sometimes longer.
  • Layer test: who interacts / how code reaches Claude / where the request runs.

For the exam: tag every platform noun in a scenario with its layer before weighing tradeoffs. Distractors often pair a plausible tradeoff with a piece from the wrong layer — a delivery route offered as an answer to a "who interacts" question, or MCP offered as a product.

Concept§03 · Screen 5

Seven AI primitives an architect assembles

Before the course shows you any pattern, it hands you the parts bin: seven primitives, each with a job you can say in a word. Tools act — a function the model can call to do something or fetch a result. MCP connects — one tool server reachable from many Claude clients. Subagents isolate and parallelize — a scoped sub-task moved into its own context. Hooks guarantee — deterministic code on defined events that the model cannot skip. Skills package a procedure — a versioned, reusable unit of instructions plus optional scripts. Agent Teams coordinate peers, each owning part of a larger goal. Dynamic Workflows compose steps at runtime instead of fixing them in advance. Those last two are the newest vocabulary, extending "single agent" and "fixed workflow."

Why inventory the parts now: every later pattern is an assembly, not a new idea. A workflow is steps wired in your own code, usually through tools. An agent is Claude picking its own next tool call as it goes. A multi-agent system is one orchestrator handing scoped units to subagents.

The vocabulary is a risk control, not pedantry. In one architecture review, "we'll use an agent" meant five different systems to five listeners — a single tool-using model, a multi-step workflow, a team of subagents, Claude Code, a chatbot — and the meeting stalled for twenty minutes before anyone noticed. The cost lens is just as blunt: a heavier primitive than the job needs is paid for in latency, tokens, and operational surface on every request. Use the fewest primitives that meet the requirement.

  • Worth memorizing
  • Exactly seven primitives: Tools, MCP, Subagents, Hooks, Skills, Agent Teams, Dynamic Workflows.
  • The jobs: ACT, CONNECT, ISOLATE/PARALLELIZE, GUARANTEE, PACKAGE A PROCEDURE, COORDINATE PEERS, COMPOSE AT RUNTIME.
  • Agent Teams and Dynamic Workflows are the two newest terms; many running systems predate them.
  • Cost example: a team of agents where one tool call would do — the overweight choice is paid on every request.
  • Discipline: the fewest primitives that meet the requirement; each one added is a part to build, observe, and govern.
  • Pattern map: workflow = steps in your code (often tools); agent = model chooses its tool sequence; multi-agent = orchestrator delegating to subagents.

For the exam: scenario questions name a requirement and expect the primitive whose one-word job matches it — a rule that must never be skipped is a hook, not a prompt; a procedure reused across requests is a skill. Also expect the "agent means five things" disambiguation: know which assembly a speaker actually means.

§04Decomposition

Concept§04 · Screen 7

Decomposition: Claude vs. systems vs. humans

Architecting for a partner already involves three calls: what the ask is, which systems are available, and where human judgment belongs. This module adds a fourth — where Claude fits — and it is the one architects most often get wrong. Decomposition answers it by splitting the request into three ownership buckets: what Claude does (work that leans on language understanding, summarization, planning, drafting, or acting through tools), what existing systems do (anything the partner already paid to make reliable — the rules table, the policy engine, the database of record), and what humans do (judgment calls, exceptions, approvals — where being right beats being fast).

The classic early mistake is over-assignment: collapsing all three buckets into "what Claude does." It almost always makes the solution more expensive, slower, and harder to run. The counter-discipline is delegation — deciding for each step not whether Claude can do it but whether it should own it. The output is a delegation map, and every assignment must survive three questions: reversibility (could a wrong call be undone?), stakes (what would a wrong call cost?), accountability (who answers for it?).

The claims-triage scenario shows the lens at work. "Read the claim" is pattern-rich language work — Claude's. "Decide priority" sounds like language but is a deterministic rule the partner's rule engine already owns. "Look up coverage" must come from the live system of record, reached through tool use or an MCP server. "Email the adjuster" splits three ways: Claude drafts, the email system sends, a human approves above a value threshold. The framing shift the module builds toward: not "where can Claude help?" but "where do the four properties argue for Claude over the system that already does the job right?"

  • Worth memorizing
  • Three buckets: what Claude does / what existing systems do / what humans do — every step gets exactly one owner.
  • Delegation-justification triad: reversibility, stakes, accountability.
  • Delegation is the first of the four AI Fluency competencies; the four behavior properties were taught in the foundations section and get applied here.
  • Claims-triage steps: read the claim / decide priority / look up coverage / email the adjuster — only the first belongs wholly to Claude.
  • Live coverage data is retrieved through tool use or an MCP server, never recalled from training data.
  • Over-assignment penalty triad: cost (LLM prices for database work), complexity (untraceable errors), risk (authoritative answers drift silently).

For the exam: given a scenario step, name its bucket and the justification. The favorite distractor is a step that sounds like language ("decide priority") but is really a deterministic rule — the right answer usually has Claude calling the existing system, not replacing it.

Watch-out§04 · Screen 8

When the deterministic check quietly drifted

The setup is deliberately sympathetic. A partner has a hard rule — any claim over £5,000 must reach a senior adjuster — enforced today by an SQL check against the claims table. On a scoping call the architect folds it into Claude: prompt the model to extract the amount and route if it tops 5K. One component, no second system, easier to demo. The partner agrees; in the moment it reads as a clean win.

What was actually traded: a deterministic rule, which must be correct on every execution, was handed to a probabilistic system, which is right most of the time. Three months into production an audit found 41 of 14,000 claims misrouted — roughly 0.3% — and every one failed the same way: the amount was buried in prose such as "damages estimated around five thousand pounds," and the model read "around five thousand" as a loose estimate, not a trigger for senior review. The rule was precise; the inputs were not; the model honored the letter of the rule over its intent.

The drift stayed invisible twice over. Nobody wrote test cases — routing was filed as "something the model handles," not a rule the business counts on. And standard observability never fired: logging that would catch a broken SQL check never records what a model chooses inside a single request. The fix: keep the hard check deterministic — code or SQL, outside the model — with Claude working around it, even at the cost of one extra integration.

What broke

A rule that must be right every time was moved inside a system that is right most of the time — the failure mode of deterministic drift. The threshold never changed; only its enforcement did, so nothing looked different while the misses accumulated.

  • Worth memorizing
  • The rule: claims over £5,000 require a senior adjuster; original enforcement was an SQL check against the claims table.
  • Outcome: 41 of 14,000 claims misrouted (~0.3%), all through amounts written as fuzzy prose.
  • Surfaced three months after go-live, in an audit — not in the system's own monitoring.
  • A rule that must be right every time cannot be delegated to a system that is right most of the time.
  • A rule the business counts on gets tests, monitoring, and a human owner; a rule you assume the model handles is left alone until it breaks.
  • SQL-style logging does not capture decisions made inside a single model call — clean demo cases hide the residual error rate.

For the exam: spot the moment a deterministic business rule is about to be absorbed into a probabilistic component — the tell is "one step instead of two, way simpler." The correct design keeps the check in code or SQL with Claude around it, and expects failures to hide in fuzzy inputs and surface in audits, not dashboards.

§05Pattern Selection

Concept§05 · Screen 11

Augmented call, workflow, or agent

Ownership decomposition told you which pieces of the task Claude holds. The next decision is structural: what shape does Claude's involvement take? Three patterns, plotted on two axes — how predictable the path through the work is, and how much autonomy you hand the model. An augmented LLM is one bounded call: your code does all the wiring, and control flow never branches on what the model decides. A workflow keeps the path in your code while the model exercises contained judgment inside individual steps, with deterministic guards between them. An agent owns its trajectory — the model's choices are the control flow.

To choose, walk five factors in a fixed sequence: predictability (can you enumerate the steps in advance?), error cost (does a wrong answer cost a retry, an audit, or a lawsuit?), observability, latency budget, and token cost. For each factor, ask which pattern it rules out — the first factor that eliminates a pattern is the deciding one. Agents carry the highest exposure on every factor: non-deterministic failures concentrate there because there is no code boundary where a guard can sit.

Choosing "workflow" still leaves a design decision: four sub-patterns — chaining, routing, parallelization, evaluator-optimizer — each encode a different assumption about how steps relate, and most production systems combine them. Take the simplest that meets your error tolerance and observability needs, and escalate only when production measurement shows it falling short. When prompting feels unreliable, fine-tuning is the last move, not the first: optimize the prompt, add tool use or retrieval, escalate to a stronger pattern — only then consider fine-tuning.

  • Worth memorizing
  • Two axes: path predictability × model autonomy. Five factors, in order: predictability, error cost, observability, latency budget, cost.
  • Claude Code is the course's production-proven example of the agent pattern — it scripts nothing in advance.
  • Fine-tuning earns its place in exactly three cases: very high volume where inference cost is the constraint; latency-critical work where a smaller specialized model beats a prompted general one; a consistent output format prompting hasn't achieved. Access is limited — confirm with the Anthropic account team first.
  • Cost nuance: a badly built workflow can out-cost a well-built agent — the design, not the pattern label, drives the bill.
  • Agent latency: budget for the worst case, not the median. Agent risk: keep the tool entry point as narrow as the task allows.
  • Packaging is a separate spectrum: prompt-only → direct tool use → a Skills-based architecture (versioned, reusable, governed unit).

For the exam: scenario questions hand you constraints and expect the elimination walk run in order — a regulated audit requirement kills the agent at observability before latency or cost is ever asked. Also expect sub-pattern identification (a classifier picking among coded paths is routing, not an agent) and the fine-tuning progression: prompt first, fine-tune last.

Watch-outReconstructed§05 · Screen 12

When the team wanted flexibility and got non-determinism

Reconstructed — this course screen wasn't captured in the source notes. Rebuilt from: the concept's own summary line and the pattern-selection screen's notes.

A team chose the agent pattern because they could not predict what users would eventually need — autonomy felt like insurance against an unknown future. Months later, production traces told a different story: virtually every run followed one of four enumerable paths. The work had a predictable shape all along. Nobody had measured it before picking the pattern.

The autonomy they paid for became the thing they answered for. With the model's trajectory as the control flow, there was no code boundary where guards or step-level logs could sit — so when compliance asked to reconstruct why a run did what it did, the answer was a transcript, not an audit trail. A routing workflow — a classifier steering each request down one of four coded paths — would have covered every observed case, with deterministic guards between steps and every path testable and loggable.

The lesson generalizes: flexibility you cannot name a concrete need for is just non-determinism you will be held accountable for. Predictability is the first of the five selection factors, and it is measured, not guessed. If the paths are enumerable, build a workflow. Reserve agents for work where enumerating the steps in advance is itself the expensive part.

What broke

  • Predictability was assumed low, never measured — the very first selection factor was skipped, and the traces later showed just four paths.
  • The autonomy bought no capability: the agent reached the same four destinations a workflow would have, minus the step boundaries where guards and logs live.
  • The gap surfaced as compliance debt: an agent trajectory reads like a transcript, and standard observability tooling could neither reconstruct it as steps nor alert on it.
  • Worth memorizing
  • Production traces showed four enumerable paths — the signature of a routing workflow, not an agent.
  • Predictability is factor one of five; this failure is a factor-one miss that no later factor can repair.
  • Workflow steps log like ordinary code; an agent's trajectory reads like a transcript that most current observability tooling isn't built to alert on.
  • Reach for an agent only when enumerating the steps in advance is the expensive part of the problem.
  • The Delegation lens: autonomy is justified by the stakes and reversibility of the actions — never by hoped-for flexibility.

For the exam: when a scenario says a team wants an agent "to stay flexible," the tested move is to ask whether the paths are enumerable. If they are, the answer is a workflow — usually routing — and choosing the agent is scored as taking on non-determinism, cost, and audit risk for autonomy the work never needed.

Concept§05 · Screen 13

Multi-agent systems and orchestration

Some work is too large or too varied for one agent's context. The design then moves to two roles — exactly two. The orchestrator holds the goal: it decomposes the work, chooses what to hand off, and synthesizes whatever comes back into one answer. It never does sub-task work itself; keeping goal ownership separate from unit execution is what makes the structure hold. Subagents each own one scoped piece, run it in a context of their own, and hand back a result. The most common shape is fan-out — split a big item into independent units, dispatch one subagent per unit, run them in parallel, synthesize. The win is twofold: each subagent gets a clean context sized to its unit, and independent units run concurrently.

The key architectural question is where each failure is recoverable — and the answer is asymmetric. A subagent failure usually is: the orchestrator can retry the unit, route it elsewhere, or drop it and flag the gap while the rest proceeds. An orchestrator failure usually is not: lose the goal or the synthesis state and the whole run dies, stranding partial work. So design for the asymmetry — make subagent work idempotent and retryable, and protect and checkpoint the orchestrator's state so a failed run resumes instead of restarting.

Three things are designed, never assumed: how work decomposes into units, how each result is structured so the orchestrator can combine it, and how conflicts or gaps get resolved. And because many actions can happen before a human sees anything, human-in-the-loop checkpoints belong inside the orchestration design — a gate before any irreversible or high-stakes action, sampling for the low-stakes rest, placed by risk and reversibility.

  • Worth memorizing
  • Worked fan-out scales: a 400-file codebase audit, a 200-document corpus summary, a regulatory filing checked against fifty rules.
  • Malformed or empty subagent result → validate every return; retry or re-route; record the gap rather than failing the run.
  • Two subagents conflict → an explicit conflict-resolution rule in the orchestrator, or escalate to a human.
  • Orchestrator loses goal or synthesis state → protect and checkpoint state so runs resume, not restart.
  • Traces fragment across agents → propagate one shared trace identifier so a run is reconstructable end to end.
  • Discipline: the fewest agents that meet the requirement — token spend multiplies, since every subagent carries its own context.

For the exam: given a failure vignette, name where it lands — subagent boundary, synthesis, orchestrator, or observability — and give the matched design response. Two reliable distractors: an orchestrator that "helps out" with unit work (role violation), and gating every action instead of placing gates by risk and reversibility.

Watch-out§05 · Screens 14–15

When fan-out hid a dropped unit

A compliance team used a fan-out to check a 50-section vendor contract against an internal policy checklist: one subagent per section, each returning a pass or flag verdict. The synthesis came back clean — “48 sections reviewed, 3 flagged” — and was circulated to the legal lead. But 50 were dispatched. One subagent timed out and returned nothing; another hit a scanned page and returned an empty result. The orchestrator counted what came back, and no rule said returns must equal dispatches.

Both failures were the recoverable kind — recoverable only if some component owns the subagent boundary and retries or flags the miss. Nothing did, so both passed silently, and the summary's fluency did the rest: confident synthesis over incomplete work is the most dangerous multi-agent failure precisely because polish hides the hole. The fix is a coverage check at synthesis: reconcile the return count against the dispatch count, and flag any shortfall before a human reads the report.

What broke

  • The count was never reconciled — synthesis summed the verdicts it received, so 48 returns became “48 reviewed” instead of “two are missing.”
  • No component owned the subagent boundary — a timeout and an empty parse are the recoverable case, but only when something retries the unit or flags the gap. Nothing was watching.
  • The output read as complete — fluent, well-formed, and exactly wrong. Three gaps had to line up for the miss to reach a reader.
  • Worth memorizing
  • 50 units dispatched, 48 returned; the report read “48 sections reviewed, 3 flagged” and reached the legal lead before anyone noticed.
  • Two silent modes: a timeout that returned nothing, and a scanned page that parsed to an empty result — neither raised an error the pipeline acted on.
  • The rule: returned must reconcile against dispatched — any shortfall is flagged before the summary circulates.
  • Three gaps lined up: an unreconciled count, an unwatched boundary, and fluent output masking the hole.
  • Checkpoint pattern: defects cluster wherever a failure or high-stakes action crosses a boundary unobserved.

For the exam: expect a draft architecture with named components and a select-N ask. Sort each component by one test — does anything observe what crosses this boundary? Completeness is verified, never assumed: an orchestrator reporting only on results received is trusting its fan-out implicitly, and that is the flaw the question wants named.

Self-test: critique the fan-out design

1. A draft fan-out lists six components: (1) the orchestrator decomposes the corpus into per-document units; (2) subagents run in parallel, each returning a verdict; (3) synthesis sums returned verdicts into a report; (4) an irreversible auto-archive runs with no human gate; (5) failed subagents get no retry and no gap flag; (6) a shared trace ID reaches every subagent. Which three carry a control or failure-boundary defect?

Reveal answer

Components 3, 4, and 5. Sum-only synthesis never reconciles returned against dispatched, so a dropped unit vanishes into a confident report. The ungated auto-archive lets an irreversible action cross a boundary with no human review. And with no retry or gap flag, a recoverable subagent failure becomes a silent one. What the three share: at each one, a failure or a high-stakes action slips over a boundary with nothing watching — exactly where multi-agent designs break.

2. Why is the shared trace ID (component 6) a distractor rather than a defect?

Reveal answer

It is the observability plumbing a healthy design includes: one identifier propagated to every subagent makes a run reconstructable end to end. It carries no control defect — the exercise plants it to test whether you can tell sound plumbing from unwatched boundaries.

§06Reference Architectures

Concept§06 · Screens 16–18

Reference architectures, and retrieval vs. live state

Screen 16's claim is simple: a pattern gives your solution its shape; a reference architecture gives it the wiring — how that shape connects to everything around it. Five are already proven in the Claude ecosystem: Agent, RAG, document processing pipeline (evaluator-optimizer), customer-service / ticket triage (routing), and coding agent — agentic exploration paired with deterministic edit/test/review steps. They are references to adapt, not blueprints to implement as drawn. Reach for a second pattern only when two parts of your problem break in different ways worth managing separately: composing two roughly doubles the surface area you maintain, and each brings its own eval contract.

The watch-out is the most common misapply in the field: retrieval asked to own live transactional state that a tool call to the system of record should own. In the worked trace, an electronics retailer's assistant answers "Where's my order?" by merging two stale index chunks into a confident "shipped June 12" — while the real order sat at a depot with a damaged label, a state recorded in neither chunk, and a live order-status tool in the partner's API went uncalled.

The retrieval principle names the boundary: retrieval answers "what does the corpus say"; live state answers "what is true right now." Conflate them and the failure hides — normal latency, no errors, nothing to alert on — until a customer notices the answer contradicts reality.

What broke

Four diagnoses, in order of depth. A category error: retrieval suits knowledge (FAQs, policies, manuals), not transactional state. A data-architecture failure: live state was indexed as text, so the system searched past snapshots instead of querying the system of record. Similarity is not truth: 0.78 beat 0.74, but a higher score only means wording closer to the query, not a more current fact. And the fix is a tool call plus a data split — knowledge base keeps the FAQ content, transactional database keeps the orders. Not a better chunker, embedding model, refresh interval, or similarity threshold.

  • Worth memorizing
  • Five reference architectures: Agent; RAG; document processing pipeline → evaluator-optimizer; customer-service / ticket triage → routing; coding agent (agentic exploration + deterministic edit/test/review).
  • Composing two architectures roughly doubles the surface area you maintain — when in doubt, pick one.
  • A composed system needs separate eval sets per architecture; top-level health can mask a failing component.
  • Trace numbers: order #88412; chunk at 0.78 says shipped June 12 (tracking AB123); chunk at 0.74 says still processing; the truth — returned to depot, damaged label — appeared in neither.
  • Symptoms of retrieval-on-live-state: stale chunks, results that shift with each index refresh, answers that contradict the database.
  • Non-fixes: better embeddings, better chunker, shorter refresh interval, higher similarity threshold. The fix: a tool call to the system of record.

For the exam: when a stem shows a retrieval-backed assistant giving confident answers that contradict the database — or answers that shift after each index refresh — name the mechanism error and pick the tool call to the system of record. Better embeddings, shorter refresh intervals, and higher similarity thresholds are all distractors.

Self-test: critique the draft routing diagram

1. A partner's draft routing design for a customer-service assistant has six components: (1) intent-classifier Claude call, (2) retrieval over an "Order Status Index", (3) retrieval over a "Product Manual Corpus", (4) an agent loop exposing refund / cancel / update-address tools, (5) no escalation path to a human agent, (6) response-composer Claude call. Which three are misapplied?

Reveal answer

2, 4, and 5. Order status is live transactional state, so an index over it is retrieval standing in for a tool call. The refund/cancel/update-address loop takes high-consequence actions with no guard. And a routing design must be able to hand off to a human. These are the three failures that most often sink routing designs.

2. Why is retrieval over the product-manual corpus fine when retrieval over order status is not?

Reveal answer

Manuals are stable knowledge — true yesterday, true tomorrow, refreshed on a schedule an index can tolerate. Order status is owned by a system of record and changes independently of any index built over it. Same mechanism, different data properties.

§07RAG Pipeline Design

ConceptReconstructed§07 · Screens 19–20

RAG pipeline: chunking, indexing, and hybrid retrieval

Reconstructed — this course screen wasn't captured in the source notes. Rebuilt from: the concept's own summary line and the certification study guide's RAG pipeline design section.

The reference-architecture card settled whether retrieval should own the data — the retrieval principle: stable knowledge only. This screen designs the pipeline itself, and every choice follows one instruction: match it to the corpus and the queries, never to habit. Chunking comes first. Split documents by the corpus's structure — fixed-size when text is uniform, semantic when natural boundaries exist (policy clauses, sections), hierarchical when documents nest. The tradeoff is size versus precision: too-large chunks retrieve imprecisely and squander the finite context; too-small chunks lose the surrounding meaning that made them worth retrieving. Add overlap wherever continuity across a boundary matters.

Indexing embeds chunks for similarity search, and the embedding model must match the query and content domain — a mismatch degrades retrieval quietly, with no error surfacing anywhere. Retrieval strategy then follows the query pattern. Dense (semantic) search finds meaning-similar text even when wording differs; sparse (keyword) search wins when exact terms must match — policy IDs, part numbers, error codes. Hybrid runs both and merges the two ranked lists, and reciprocal rank fusion is the defensible default for that merge. Re-ranking then sharpens precision, and metadata filters scope results to the right applicant or document set before anything reaches the model.

One operational rule outweighs the rest: confident-but-wrong answers that begin right after a document refresh, with model and latency unchanged, point at the index — a broken re-index or mismatched embeddings — not the model. Diagnose by mapping the symptom to the component that changed.

  • Worth memorizing
  • Three chunking strategies: fixed-size (uniform text), semantic (natural boundaries like policy clauses), hierarchical (nested documents) — with overlap where continuity matters.
  • Chunk-size tradeoff: too large = imprecise retrieval and wasted context; too small = meaning stripped from the chunk.
  • Sparse/keyword retrieval for exact identifiers (policy IDs, part numbers); dense/semantic for paraphrased meaning; hybrid when queries mix both.
  • Reciprocal rank fusion (RRF) is the defensible default for merging the dense and sparse ranked lists.
  • Re-ranking buys precision on the merged set; metadata filtering scopes to the right applicant or document set.
  • Diagnosis rule: confident-but-wrong after a doc refresh, model and latency unchanged → check re-index integrity and embedding match first.

For the exam: stems hand you a symptom plus the one thing that changed, then ask where to investigate first. "Wrong policy answers after the monthly document refresh" is a retrieval/indexing answer every time — model weights, temperature, and context-window size are the distractors. Also expect "exact policy-ID lookups keep missing" → add sparse/keyword search, and "results bleed across applicants" → metadata filtering.

§08Model & Context Strategy

Concept§08 · Screens 21–23

Model, context window, and context strategy

A pattern plus a reference architecture is not yet a shippable system. Three decisions remain — which model, how much of the context window to actually plan around, and whether context arrives progressively or all at once — and each multiplies across every request at production volume. The model family is Opus, Sonnet, and Haiku; Sonnet is the default starting point. Move up to Opus only when an eval shows Sonnet missing your quality bar; move down to Haiku only when an eval confirms the quality tradeoff is acceptable. Model moves are measured, never reflexive.

Conflating four terms produces reference-architecture mistakes. The context window is the model's active attention space — anything outside it does not exist to the model, and it resets between calls. Retrieval is external knowledge fetched at query time; it augments the window, never replaces it, and the model sees only what the retriever surfaces. Persistent application state — order status, user records, balances — belongs to your system, and the model reaches it only through a tool call. Summaries and memory layers are continuity your application manages, because the model has no native memory between calls. The window's edge is the working-memory cliff: failure is abrupt, not gradual. So budget the window as a ceiling, not a target, and measure tokens from the API's usage field instead of estimating.

Context strategy is a spectrum. Monolithic loads everything at once; progressive stages context just-in-time and is the right default for most production workloads; RAG and compaction sit between the poles. Real systems layer all four — the module's coding agent runs a cached monolithic prefix, progressive accumulation, just-in-time retrieval, and compaction. And every model change ships through an eval whose pass threshold is fixed before the results come in.

What broke

Running Opus everywhere "because it's the most capable." A model choice multiplies across every request, so an unmeasured move up is a cost and latency surcharge with no evidence it helps. The discipline runs both ways: Opus must earn its place with an eval showing Sonnet misses the bar; Haiku with an eval showing the quality loss is acceptable. No eval set means no rollback signal — the regression ships, and the user finds it first.

  • Worth memorizing
  • Model family: Opus (most capable) · Sonnet (default starting point) · Haiku (fastest, cheapest) — change tiers only on eval evidence.
  • Window budget formula: largest realistic conversation + retrieved context + system prompt + working scratch + margin for growth.
  • Cost example: a conversation opening at a 4,000-token prompt can be carrying 80,000 tokens by turn 30 — no visible signal until billing.
  • Extended thinking is a billed reasoning pass: thinking tokens bill as output tokens and add latency. Enable it only for a measured accuracy gap, never because "it can't hurt."
  • Eval gate minimum: curated test set covering the real work distribution + a grading function + a delta threshold set before the run.
  • Worked case: 250 stratified documents; Sonnet 0.94 vs Haiku 0.86 average; two types at 0.71 and 0.74; pre-set rule "reject if any type < 0.85" killed the full swap — salvage: those two types stay on Sonnet, the rest move to Haiku.

For the exam: scenario questions apply budget or quality pressure and test whether you demand the eval gate — threshold fixed in advance — before any model move. Watch the four-term trap: 'the model remembers the order status' really means a tool call into persistent application state.

Self-test: cost and latency checkpoint

1. A support conversation opened with a 4,000-token prompt. By turn 30 each call costs many times more, yet no code changed. What happened, and which strategy is implicated?

Reveal answer

Monolithic accumulation: the full history rides into every call — about 80,000 tokens by turn 30 in the course's example, with no signal until billing while the window fills toward the cliff. The fix is progressive staging plus compaction of early turns.

2. Accuracy is below target. When is switching on extended thinking the right move?

Reveal answer

Only when evals without it, plus work on the prompt itself, still leave a measured accuracy gap. It is a billed reasoning pass — thinking tokens are charged as output tokens and add latency on every call — so "it can't hurt" is exactly the wrong justification.

3. Under budget pressure a team wants to swap Sonnet for Haiku. What must exist before the eval runs, and why did it save the worked case?

Reveal answer

The rollback criterion, set in advance — reject if any document type scores below 0.85. Because it pre-existed the data, there was no self-negotiation when two types came in at 0.71 and 0.74. Stratification then surfaced the partial migration — two weak types to Sonnet, the rest to Haiku — that a single overall average would have hidden.

§09Prompting as Architecture

Concept§09 · Screens 24–27

System prompts, templates, and guardrails

At enterprise scale a prompt stops being something you type and becomes an asset you engineer. A system prompt that hundreds of requests a day depend on is a different artifact from a one-off chat prompt, so it gets structure: a statement of role and scope, the constraints the model must hold — what it must never do, what it must always do — and an output contract naming the exact shape of the response. Reused at that volume, ambiguity is a defect multiplied across every request.

A template is that system prompt with parameterized slots inside fixed scaffolding — and the scaffolding is where safety lives. The design goal: filling a slot can never delete a constraint, so whoever supplies the variable content inherits the guardrails without re-authoring them. The safe path becomes the default path. The failure mode to hunt is underspecification: wherever the prompt is silent, the model improvises, differently each time — and an underspecified guardrail is worse than a missing one, because it gives the appearance of a control without the substance. The Description competency supplies the checklist — scope, format, constraints: for each requirement, does the prompt state it or merely hope for it?

Technique selection is an architecture decision, made by task complexity, never habit. Start zero-shot (instruction only); escalate to few-shot only when the format or judgment is easier to show than describe; reach for chain-of-thought only when the reasoning path itself decides the answer — each step up costs tokens and latency on every call. And because a more capable model needs less scaffolding, the prompt-model pairing is what you actually ship: a model swap is a release, gated by an eval.

  • Worth memorizing
  • Enterprise system-prompt anatomy: role and scope + constraints + output contract.
  • Template rule: the fixed scaffolding carries the safety and consistency guarantees — slot-filling must not be able to remove a constraint.
  • Description (one of the four AI Fluency competencies) names three things: the scope, the format, the constraints.
  • Escalation order: zero-shot, then few-shot, then chain-of-thought — every step up adds tokens and latency on every call, so reach for the lightest technique that meets the requirement.
  • Three bias sources in prompts: leading phrasing, unbalanced few-shot sets, assumptions baked into the instruction — invisible in any single output, visible only in aggregate.
  • Few-shot examples are maintained content: as the task evolves, stale examples quietly steer the model wrong.

For the exam: expect a template scenario where a fill-in slot can override a constraint — the diagnosis is safety living in the slot instead of the scaffolding. On technique questions the justification is graded as much as the pick: choose the lightest technique that meets the requirement, and say why the heavier one isn't earned.

Self-test: pick the technique for each task

1. Route incoming support tickets into one of five fixed buckets: billing, technical, returns, account, or general. Which technique?

Reveal answer

Zero-shot. The task is fully specified and the categories are enumerated — classification like this is something the model handles reliably without examples, so few-shot would just add tokens for nothing.

2. Pull the date, vendor, and amount out of expense receipts whose layouts vary wildly. Which technique?

Reveal answer

Few-shot. With heavy layout variation, the target extraction format is easier to demonstrate with a handful of input/output examples than to pin down in instructions — this is the show-don't-tell case.

3. Decide whether a contract clause creates a liability when three interacting conditions apply. Which technique?

Reveal answer

Chain-of-thought. The answer hangs on a sequence of conditional logic steps, and asking for explicit step-by-step reasoning lowers the odds the model skips an interaction between the conditions.

4. Compress a 400-word product description into two sentences. Which technique?

Reveal answer

Zero-shot. Standard summarization of a well-bounded input — examples or explicit reasoning would add tokens and latency with no quality gain. The general rule underneath all four: match the technique to the task's demands, not to habit.

§10Entry Points & Governance

Concept§10 · Screens 28–30

Entry point, route, and governance selection

You've chosen the model and the shape of the work; now: how the partner consumes Claude. Three decisions, in a fixed order. First: which entry point fits the work and the user — the wrapper deciding who can talk to Claude, what it can touch, and how much engineering it takes to get there. Second: which build-time interface the team programs against — the direct API, a language SDK, MCP, or the Agent SDK; layers that stack rather than compete. Third: which delivery route the traffic terminates on — first-party Anthropic, AWS Bedrock, GCP Vertex AI, or Microsoft Foundry. The model is identical on all four; only billing, identity, region, and existing procurement paper differ.

One screen runs before cost or latency gets a vote: governance. Privilege, HIPAA, GDPR, FedRAMP, and internal residency policy rule routes out before preference is heard. Claude.ai takes this hit most; the API or SDK behind a partner-approved gateway — logging, retention, and identity in the partner's own infrastructure — survives most regulated reviews. Name the governing constraint, let it eliminate options first, then let cost and latency pick among survivors. The entry point should follow the work, not precede it.

What broke

A regional bank proposed an operations assistant for branch staff: Claude Code on branch laptops with per-branch CLAUDE.md, MCP servers for the customer database, appointments, and policy corpus, and subagents running compliance. Three failures: the entry point was chosen before the user was named — branch staff do not run terminals; MCP was carried forward from a prior project, with no other clients to justify it; and compliance, the highest-consequence path, sat on the surface with the weakest deterministic guarantees. The fix: a custom web app calling the API directly, compliance in deterministic server-side code, an SSO banking UI, tool calls audited at the server boundary.

  • Worth memorizing
  • Three decisions in strict order: entry point → build-time interface → delivery route.
  • Interface rule: one request/one response → API or SDK; tools reused across clients → MCP; multi-turn agent in the partner's product → Agent SDK.
  • Six permission modes: default, acceptEdits, plan, auto, dontAsk, bypassPermissions (containers or CI only).
  • CSP routes (Bedrock, Vertex, Foundry) lag the first-party API on new features by weeks, sometimes longer.
  • HIPAA: a BAA covers one specific configuration only; beta features are generally excluded unless explicitly listed.
  • FedRAMP map: Claude for Government = FedRAMP High civilian; Bedrock GovCloud = High + DoD IL4/5; Vertex Assured Workloads = High + IL2 — all on a model lag.

For the exam: answers must pair the right entry point or route with the right deciding tradeoff — the correct destination for the wrong reason scores wrong. Classic distractor: the right route with the wrong category — Bedrock "for residency" when the real reason is BAA coverage.

Self-test: six scenarios — name the entry point and the deciding tradeoff

1. A non-engineering operations team wants a chat assistant over approved internal docs.

Reveal answer

Claude.ai with a Project — audience decides. A non-technical team needs a ready-made product surface, not a build-time interface; the Project supplies the shared context.

2. A bank on AWS with an enterprise agreement wants a loan-officer assistant pulling live core-banking data.

Reveal answer

AWS Bedrock — integration depth. A chat product cannot retrieve core-banking data, and the AWS commitment rules out the direct API: the route follows the procurement context.

3. A law firm's general counsel requires all AI touching privileged documents to run behind the firm's own audit infrastructure.

Reveal answer

API or SDK behind the firm's own app and gateway — governance/control. Privilege turns on owning the audit trail: Claude.ai Enterprise logs live in Anthropic's infrastructure; residency (Bedrock) is the wrong category.

4. Non-technical warehouse staff on shared tablets need shift-handoff notes and equipment checklists.

Reveal answer

Claude.ai with a Project — audience. Staff need zero-setup access; nothing demands a custom build, and Claude Code is a developer terminal tool with nothing to offer here.

5. A healthcare network holds an AWS BAA confirmed to cover Bedrock; a rival bid proposes the direct API under a separate BAA.

Reveal answer

Bedrock — governance/control: the existing BAA covers this exact configuration. Not residency: HIPAA turns on BAA coverage of the configuration in use, not geography. A fresh BAA adds procurement delay for zero gain.

6. A financial firm on GCP must produce a natural-language summary of each trade within 400 milliseconds.

Reveal answer

Vertex AI — latency plus existing cloud. Staying inside the firm's GCP environment minimizes round-trip; the direct API or cross-cloud Bedrock adds overhead a 400 ms budget cannot absorb (and Bedrock lacks a procurement case).

§11Assembly & Recap

Concept§11 · Screens 31–33

Cumulative assembly: the law-firm brief

The capstone commits you to all five decisions on one brief: entry point, pattern, split of work, model and context, human-in-the-loop. A 180-lawyer firm wants contract review faster — senior associates spend 12–18 hours a week checking 35-page contracts against the firm's standard playbook. Documents live in iManage, a CIO-approved private LLM gateway exists, attorney-client privilege rules out consumer-grade tools, and the target is a 60% cut in associate time with the senior associate still the final reviewer.

Three of the four candidates collapse on a named decision. Option A builds on Claude.ai Projects — the privilege failure: a consumer-grade entry point the brief excludes, made easy to miss because everything downstream in A is reasonable. Option B freezes the full playbook into the system prompt on every call — the knowledge-limitation failure: the copy goes stale and every request pays to reprocess it. Option C breaks twice: an open-ended agent on work that splits cleanly by section (the "we want flexibility" failure) plus Opus on every call (the bill-arrived failure).

Option D holds: API or SDK behind SSO and the approved gateway, a parallelized workflow with a schema-enforcing evaluator pass, the playbook versioned in firm systems and retrieved per clause, Sonnet with progressive context and eval-gated extended thinking, and senior-associate sign-off with low-confidence clauses flagged. Each decision constrains the next — the architecture passes because all five hold together.

  • Worth memorizing
  • Takeaway 1 — decomposition comes before architecture: split the work into three buckets (Claude / existing systems / humans), driven by how the model behaves on each piece.
  • Takeaway 2 — choosing a pattern is choosing how much autonomy to grant: five factors (predictability, error cost, observability, latency, cost), and the tightest constraint decides.
  • Takeaway 3 — reach for the five tested reference architectures (Agent, RAG, Document processing pipeline / Evaluator-optimizer, Routing, Coding agent) before inventing your own; never use retrieval as a stand-in for live state.
  • Takeaway 4 — Sonnet is the default; every model swap is a release: an eval set that defines "better" plus a rollback criterion set before the swap. Progressive context outlasts monolithic.
  • Takeaway 5 — pick the entry point by the work it must do and say the tradeoff out loud; the named tradeoff is what later tells you when to switch.

For the exam: given a full candidate architecture, find the one decision that sinks it — a sound downstream stack never rescues a broken upstream call (Option A's trap). Map each named failure to its decision: privilege → entry point, knowledge-limitation → split of work, "we want flexibility" → pattern, bill-arrived → model. Only C fails twice.

Self-test: the capstone — judge the four candidates

1. Draft your own one-paragraph architecture for the brief, committing to all five decisions, then reveal and compare.

Reveal answer

The model answer is Option D: direct API or SDK in a thin SSO web app through the approved gateway; a parallelized section-by-section workflow with a schema-enforcing evaluator pass; Claude does extraction, playbook classification, and draft redlines; iManage fetches documents; the playbook stays versioned in firm systems, retrieved per clause; Sonnet with progressive context, extended thinking only where an eval set justifies it; senior-associate sign-off, low-confidence clauses flagged. Every constraint in the brief maps to a decision.

2. A reviewer skims Option A and sees a parallelized workflow, Sonnet with progressive context, and a human gate — all correct. What did they miss, and why is it easy to miss?

Reveal answer

The entry point. Claude.ai is a consumer-grade tool and the privilege requirement excludes it — the design is dead before any downstream choice matters. Easy to miss because every downstream decision is sound: correctness below camouflages the fatal call above.

3. Option B ships the entire playbook in the system prompt "so the model always has the standard." Name the failure and the fix.

Reveal answer

The knowledge-limitation failure, on the split of work. A copy frozen in the prompt goes stale when the playbook changes, and every request pays to reprocess it. Fix: keep the playbook versioned in the firm's systems as the source of truth and retrieve only the relevant sections per clause.

4. Option C's defenders argue "an agent gives us flexibility" and "Opus gives maximum accuracy." Which two decisions break, and what rule answers each defense?

Reveal answer

Pattern: the work splits cleanly into independent sections, so a parallelized workflow fits — the agent's autonomy costs money and predictability and is never used. Model: Sonnet is the default tier; escalate to Opus only when an eval set proves you must, with a rollback criterion set before the swap. C is the only candidate failing on two decisions at once.

5. What makes D "the one that holds," beyond each decision being individually defensible?

Reveal answer

The five decisions reinforce each other: SSO plus the approved gateway satisfies privilege, the workflow shape matches how the work decomposes, per-clause retrieval keeps the playbook current and the context progressive, Sonnet holds the cost line as volume grows, and the sign-off gate keeps the senior associate the final reviewer. An architecture passes when all five hold together — not when each looks fine in isolation.
