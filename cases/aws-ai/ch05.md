Together, these protocols provide the foundation for building modular, extensible, and interoperable agentic applications.

Model Context Protocol

As you build more sophisticated agents, you'll quickly encounter a challenge: managing dozens or hundreds of tools becomes complex. What if you could discover and use tools dynamically, without hardcoding each one into your agent? What if tools built by other teams or organizations could be seamlessly integrated into your agents? This is where the MCP comes in.

Why is a standardized protocol needed for tools?

AI models and agents need to interact with many external tools, including APIs, databases, and developer platforms. Without a standardized protocol, each model must build custom integrations for each tool, which quickly becomes complex, costly, and difficult to maintain. Having a standardized protocol provides a common interface for tool use, reducing integration overhead, improving interoperability, and making it easier to scale AI systems as new tools and models are introduced.

Figure 5.1 shows a comparison between the traditional integration and the MCP approaches for connecting AI models to external tools and systems. As shown in the diagram, the model connects with three tools: DynamoDB, Glue, and GitHub.

Figure 5.1: Traditional integration versus MCP
Figure 5.1: Traditional integration versus MCP

In the traditional model, each AI model must directly integrate with every tool or service—such as Amazon DynamoDB, AWS Glue, and GitHub—resulting in N × M connections, where N is the number of models and M is the number of tools. This creates many integrations that are difficult to build and maintain as the system grows. In contrast, the Model Context Protocol introduces a central layer that acts as a standardized interface between models and tools. Each model connects to MCP once, and each tool also connects to MCP once, reducing the integrations to N + M connections. This architecture simplifies development, reduces maintenance, and allows new models or tools to be added easily without creating multiple new integrations.

This many-to-many integration pattern is exactly the problem MCP is designed to address, providing a shared interface that replaces fragmented, one-off tool connections with a more scalable and maintainable approach.

What problem does MCP solve?

Imagine you're building an enterprise agent that needs to interact with multiple systems: your company's CRM, inventory database, email system, calendar, document storage, and more. Traditionally, you'd need to write custom integration code for each system, maintain that code as systems change, and handle authentication and authorization for every individual system. On top of that, you'd have to deal with different API formats and conventions and update your agent code every time a new system is added. This repetitive, siloed approach is exactly what leads to fragmented app development, where every integration is built from scratch with no shared standard, making the entire system harder to scale, maintain, and manage over time.

For example, as shown in Figure 5.2, each AI app (App 1, 2, and 3) has to independently build its own entire stack: each app writes its own core AI integration from scratch, each app manages its own way of structuring and handling prompts, each app defines its own methods for invoking external tools, and each app builds its own connectors to reach data sources. If App 1 solves a data access problem, Apps 2 and 3 can't benefit. Bugs and updates must be fixed separately in each app. Also, each app may behave differently even for the same underlying task.

This approach doesn't scale. It's time-consuming, error-prone, and creates tight coupling between your agent and the systems it integrates with.

MCP addresses this by providing a single, standardized layer that all AI apps can share, so instead of each app reinventing the wheel, they all plug into a common protocol for tool calls and data access.

Using MCP offers several advantages that make agent development easier and more scalable:

Dynamic tool discovery: Your agent automatically sees all available tools from connected servers
No integration code: It connects to new tool sources without writing custom adapters
Automatic updates: When a server adds new tools or updates existing ones, your agent sees the changes immediately
Unified interface: Whether tools come from AWS, GitHub, or your internal systems, your agent interacts with them the same way
Flexible deployment: MCP servers can run locally on your machine or remotely in the cloud
MCP provides a universal adapter for AI agents, such as USB, for example. Through MCP, AI models can connect to a wide range of external tools and systems, including databases (Amazon DynamoDB), CRM systems, calendars, code repositories (GitHub), messaging platforms (e.g., Slack), and document storage systems (Google Drive). Understanding MCP in action

MCP establishes a standard protocol between your agent and tool providers, similar to how USB created a universal standard for connecting devices to computers.

Figure 5.4: Long-term memory
Figure 5.4: Long-term memory

Key components of MCP:

Host: The Host is the AI application or agent that needs to perform tasks, such as answering questions, retrieving information, or interacting with tools. Instead of directly connecting to external systems, the host communicates with an MCP Client.
MCP Client (tool consumer): Built into your agent, this component connects to MCP servers, discovers available tools, and handles the communication protocol. When your agent needs a tool, the client queries the appropriate server and executes the tool with the required parameters.
MCP Server (tool provider): A service that exposes a catalog of tools with their descriptions, parameters, and capabilities. For example, AWS Labs provides an MCP server (https://github.com/awslabs/mcp) that exposes AWS documentation tools, GitHub provides servers for repository operations, and you can build custom servers for your internal systems.
Data sources: Finally, the MCP Server connects to the actual data sources, such as databases, APIs, files, or enterprise systems. It then retrieves the required information and sends the results back through the MCP Client to the Host. This layered design allows AI applications to access many different tools and data sources through a consistent and reusable interface, making integrations easier to build, maintain, and scale.
These components work together through a standardized communication layer, which is the core idea behind MCP. Instead of each host and tool provider inventing its own integration pattern, MCP defines a common protocol for how clients and servers discover capabilities, exchange requests, and return results. This shared protocol is what makes MCP scalable, reusable, and easier to maintain across many tools and systems.

Now that you have a solid understanding of the key components of MCP, let's look at the difference between the host and the MCP Client.

Differnce between host and MCP client

When building an MCP client, the client itself does not operate independently. Instead, it is instantiated and managed by a host application, such as a code editor, AI assistant interface, or browser extension. The host application is responsible for the overall user experience, including managing the user interface, maintaining session memory, and orchestrating prompts. It can also coordinate multiple MCP clients simultaneously, with each client connected to a different server.

In contrast, each MCP client functions as a protocol-level component that maintains a one-to-one connection with a single MCP server. Its responsibilities include discovering the tools, resources, and prompts exposed by that server, gathering and organizing relevant context for the model, and prompting the user for any missing information when needed. Understanding this distinction is important: the host is the layer users interact with, while the client enables the host to communicate with specific servers through MCP. Figure 5.5 gives a high-level overview of the relation and integration between the host and MCP client:

Figure 5.5: Relation between MCP host, MCP client and MCP Server

The MCP Host can contain multiple MCP clients (one-to-many), each interacting with different MCP servers, and collectively enabling the agent to access multiple tools. This design keeps individual connections simple and modular while allowing the overall system to scale across many external services. Each MCP client in the MCP Host connects to a single MCP server (1:1 relationship) through the transport layer, ensuring a clear and isolated communication channel. In turn, each MCP server connects to a specific external system (1:1 relationship).

The MCP Host is the application layer (UI, workflows, user interaction), while the Client is the integration layer within the host that implements the MCP protocol, allowing multiple clients to connect to different MCP servers.

The Host orchestrates, but each client communicates with one server only, maintaining a clean and modular protocol connection.

Each MCP client communicates with its corresponding MCP server through a transport layer, which is responsible for carrying protocol messages between the two. MCP uses JSON-RPC as its message format, and these messages must be UTF-8 encoded. In other words, while the client and server define what is being communicated, the transport layer defines how those messages move between them.

MCP currently supports several standard transport mechanisms for client-server communication. These transport options should be viewed together because they serve the same purpose, but are designed for different deployment scenarios:

Stdio (Standard Input/Output): Best suited for local integrations where the client and server run on the same machine. It is simple, direct, and lightweight, much like communication between local command-line processes. This is a common choice when running an AI agent locally on your computer.
SSE (Server-Sent Events) or Streamable HTTP: Best suited for web-based or remote communication. It uses HTTP-based streaming so that data can be delivered incrementally in real time, rather than as a single response. This is useful for scenarios such as a live chatbot receiving updates as they happen.
Custom transports: Developers can implement their own transport mechanisms when the built-in options do not fit their requirements. For example, an enterprise team might use gRPC for high-performance, low-latency communication. In the next section, we'll see how the lifecycle of a client–server connection is managed to ensure smooth communication and proper state handling.
Together, these transport options give MCP the flexibility to support local, remote, and enterprise deployment patterns while preserving the same client-server protocol model. Managing lifecycle between client and server

Lifecycle management describes how an MCP client and server start, maintain, and end a connection. It ensures that both sides agree on protocol versions, understand each other's capabilities, and manage session state correctly. It includes three stages: Initialization, where the MCP client and server agree on protocol versions and capabilities; Operation, where normal protocol communication occurs; and Shutdown, where the connection is gracefully terminated by the client.

Example Consider an AI agent that connects to an MCP server to access a company's database. During Initialization, the MCP client and server perform a handshake, agreeing on the protocol version and capabilities (for example, the server confirms it supports query execution). In the Operation phase, the agent sends requests such as retrieving customer records and the server processes them and returns structured responses. Finally, during Shutdown, the client gracefully closes the connection, ensuring any ongoing operations are completed and resources are properly released.

Let's understand how the connection is secured.

MCP provides an authorization framework to be used with HTTP. Implementations using an HTTP-based transport should conform to this specification, whereas implementations using STDIO transport should not follow this specification, and instead retrieve credentials from the environment. Additionally, clients, and servers may negotiate their own custom authentication and authorization strategies.

Understanding MCP server features

The MCP Server exposes three main categories of capabilities to the client: Tools, Resources, and Prompt templates.

Figure 5.6: MCP Server features tools, resources and prompt template

Tools: These are functions the Agent can execute to perform actions in external systems. Examples include retrieving/searching data, sending messages, or updating database records.
Resources: These represent data or content the agent can read. Resources represent read-only, persistent data that your server exposes to clients. Unlike tools, resources don't perform actions. Instead, they make information available for browsing, searching, and referencing. Resources are essential for enabling models to look up facts or structured information without triggering an operation. Examples include files, database records, or API responses that provide context for the Agent.
Prompt Templates: These are predefined prompts exposed by the MCP server that the agent can use through the MCP client to guide how it interacts with data or performs a task. They provide reusable instructions for common interaction patterns, such as document question answering, transcript summarization, or generating output in a structured format like JSON.

Because tools were already covered in Chapter 2, Building Agents with Tools, we will briefly review their role in MCP and then focus more closely on resources and prompt templates

Tools

You are already familiar with tools, as they were covered in Chapter 2. In the context of MCP, tools are specific actions your MCP server exposes to a client, like built-in functions or APIs that an LLM can call during a conversation. When a user asks for something that requires action (fetching data, triggering an operation, or performing a calculation), the model chooses the appropriate tool to handle it. Each tool execution requires explicit user approval, thus making sure that users maintain control at all times. An MCP server supports two methods per protocol:

tools/list: To discover available tools, clients send a tools/list request. You can find the available tools that the server supports. It returns an array of tool definitions with schemas.
tools/call: This is used to execute a specific tool. The method returns the tool's execution result.
You can read more about tools and their specifications at: https://modelcontextprotocol.io/specification/draft/server/tools.

Resources

Each MCP server defines collections or documents as resources. These can also be organized into categories (called Roots) for easier navigation. The MCP clients can fetch, filter, or search these resources on demand. To discover available resources, clients send a resources/list request and to retrieve resource contents, clients send a resources/read request.

More information on Resources can be found at: https://modelcontextprotocol.io/specification/draft/server/resources

Resource template

Resource templates allow servers to expose parameterized resources using URI templates. Each resource is identified by a unique Uniform Resource Identifier (URI) (for example, file:///path/to/document.md) and declares a MIME type, which is a standard label that tells the client what kind of content the resource contains and how it should be handled. For example, a resource might be identified as Markdown, JSON, or PDF, allowing clients to process different content formats correctly.

For example, an MCP server can share a course directory as shown in the following code:

{
  "uri": "file:///data/student-directory.json",
  "name": " courseDirectory ",
  "title": " Course Directory ",
  "description": "List of courses and instructors in a program",
  "mimeType": "application/json"
}
Clients can substitute variables in the URI to query specific data. For example, a template such as travel://activities/{city}/{category} can provide access to activities of several categories for various cities, for example: travel://activities/barcelona/museums.

Prompt templates

Prompts in MCP are predefined instruction templates that an MCP server exposes to clients. They help standardize recurring interactions and save developers from rewriting the same instructions for common tasks. Each prompt can include variables, which the MCP client fills in dynamically at runtime. The MCP client retrieves the selected prompt from the server and then passes the completed prompt to the model as part of the inference request.

Prompts can be versioned and updated centrally without changing client code. They are explicitly invoked by the user or client, they don't run automatically. They can also be context-aware, dynamically referencing available resources and tools to build more complete and efficient workflows.

      "name": "examDate",

Understanding MCP client features

When building an MCP client, you're creating the component that connects directly to an MCP server. But clients don't exist on their own; they are instantiated by a host application, like a code editor or a browser extension.

The next sections show how to use features such as Sampling, Roots, and Elicitation:

Sampling: Letting MCP servers use your AI model safely
Roots: Defining filesystem boundaries
Elicitation: Request user input at runtime
These features help optimize context, organize data, and manage interactive flows. Let's understand each one of them in detail.

Sampling

Sampling lets an MCP server temporarily use the AI model and permissions already available on the client side, instead of calling its own model directly. This is valuable because it reverses the usual client-to-server request pattern: rather than the client only asking the server for data or actions, the server can ask the client to perform an AI task on its behalf. This is especially useful for complex, collaborative workflows where the server has the domain data or business logic, but the client has access to the model, the user's permissions, and the user interface. As a result, the client and server can work together on a task while still keeping the user in control of model usage, approvals, and final outputs. Figure 5.11 shows how sampling works in the MCP using a travel planning example:

Figure 5.11: How sampling works between client and user for approval
Figure 5.11: How sampling works between client and user for approval

A travel server retrieves many Rome activities but lacks AI logic to rank them. It sends a sampling request to the MCP client asking an AI model such as Claude 3.5 Sonnet to select the top five activities for someone interested in history, art, and food. The client asks the user for approval, runs the AI analysis, and shows the results to the user. After the user reviews and approves the recommendations, the client sends the final AI-generated results back to the server.

Roots

MCP provides a standardized way for clients to expose filesystem roots to servers. Roots define the boundaries of where servers can operate within the filesystem, allowing them to understand which directories and files they have access to. Servers can request the list of roots from supporting clients and receive notifications when that list changes. Figure 5.12 shows how Roots work in the MCP to control file access:

Figure 5.12: How MCP client uses roots to manage access to files
Figure 5.12: How MCP client uses roots to manage access to files

An event planner uses an MCP-powered assistant to manage conferences. The root

file:///Users/planner/conference‑2025 is the main workspace for current event.

The MCP client defines these as roots:

[
  {
    "uri": "file:///Users/planner/conference-2025",
    "name": "2025 Conference Workspace"
  }
]
With these boundaries, the MCP server can save updated attendee lists to conference-2025. However, it cannot access unrelated files outside these roots, such as personal documents or other projects. This limitation is intentional, as the server can access only the files and folders explicitly exposed through the configured roots, not unrelated content such as personal documents or other projects. When users switch projects or folders, clients can update the roots list and notify the server, ensuring access remains tightly scoped.

Elicitation

MCP elicitation allows a server to request missing information during an active session instead of assuming it in advance. In practice, the server detects that required context is missing or ambiguous and sends an elicitation request. The client then asks the user for the needed information, allows them to review, edit, reject, or cancel the request, and returns the response to the server. The server can then continue processing with the newly supplied context.

MCP supports two elicitation modes: form mode and URL mode.

For example, in form mode, a travel-booking server can ask the client to collect structured fields such as passport number and date of birth before completing a reservation. In URL mode, a payroll server can direct the user to a secure external HR portal to enter sensitive tax or banking details that should not pass through the client. In both cases, the client remains in control of the interaction, while the server receives only the information or completion signal needed to continue safely.

Building and using MCP servers

This section explains how to work with MCP servers in practice, either by using existing servers or by building your own for custom integrations.

You can either build your own MCP server or use an existing MCP server provided by Anthropic, the open-source community, or AWS through the Official MCP Servers for AWS repository.

Using pre-built MCP servers

You have options to directly connect to an MCP server, for example, GitHub MCP Server (https://github.com/github/github-mcp-server) or Slack MCP Server (https://github.com/korotovsky/slack-mcp-server), to your existing MCP host such as Claude code IDE, VS Code or Kiro. These servers expose functionality as MCP tools that any MCP-compatible agent can use.

To make this more concrete, consider the AWS Documentation MCP Server. This server exposes tools for searching and retrieving information from official AWS documentation. In the following example, the code launches the MCP server as a local process using uvx, creates an MCP client that communicates with it over standard input and output, retrieves the list of available tools from the server, and then passes those tools to a Strands agent. Once connected, the agent can answer AWS-related questions by calling the documentation tools exposed through the MCP server rather than relying only on its own built-in knowledge

from mcp import stdio_client, StdioServerParameters
from strands import Agent
from strands.tools.mcp import MCPClient
# Create MCP client
mcp_client = MCPClient(lambda: stdio_client(
    StdioServerParameters(
        command="uvx",
        args=["awslabs.aws-documentation-mcp-server@latest"]
    )
))
# Use with agent
with mcp_client:
    tools = mcp_client.list_tools_sync()
    agent = Agent(tools=tools)
    response = agent("What is AWS Lambda?")
This pattern is powerful because you do not need to write custom integration logic for AWS documentation yourself. The MCP server packages that capability as reusable tools, and the agent simply discovers and uses them through the MCP interface.

Building your own or custom MCP Server

You can build custom MCP servers to expose your organization's tools and data sources. Building an MCP server involves using an SDK to define tools (actions the AI can perform) and resources (data the AI can read), and then running the server with a chosen transport method.

The SDK used to build MCP servers officially supports Python and TypeScript, making them the recommended languages for development.

FastMCP versus FastAPI

There are two ways to build MCP servers in Python: FastMCP (https://gofastmcp.com/getting-started/welcome) and FastAPI (https://fastapi.tiangolo.com/). Although both can be used in MCP-based systems, they serve different purposes and operate at different levels of abstraction.

FastMCP is designed specifically for MCP. It provides MCP-native abstractions for defining tools, resources, and prompts, so it is usually the simplest option when your main goal is to build an MCP server quickly. Developers should choose FastMCP when they want a straightforward, MCP-focused development experience with less boilerplate and when the service is primarily intended to expose MCP capabilities.

FastAPI, by contrast, is a general-purpose web framework. It is a better fit when MCP functionality needs to be part of a broader application that also exposes REST APIs, custom authentication flows, health checks, dashboards, or other web service endpoints. Developers should choose FastAPI when they need more flexibility and tighter integration with a larger service architecture, even if that means writing more of the MCP integration logic themselves.

In short, FastMCP is usually the better choice for building a dedicated MCP server quickly, while FastAPI is better when MCP is only one part of a larger web service.

Using MCP with Agent Frameworks

Frameworks such as Strands and LangChain can act as MCP clients or adapters, allowing agents to discover and invoke tools exposed by MCP servers. Their role is not to define the MCP server itself, but to help agents consume MCP-compatible capabilities as part of a larger reasoning and orchestration workflow.

Strands Orchestrator

Strands agent includes Anthropic's MCP Python library, which includes the FastMCP library for MCP implementation using Strands orchestrator. You can use Strands for creating the autonomous agent, managing tool discovery, and connecting to AWS services (like SageMaker), and FastMCP to create the underlying, fast-responding tools that the agent calls.

LangChain

LangChain has native support for the MCP through specialized libraries, allowing agents and chains to connect with Anthropic's MCP servers (https://modelcontextprotocol.io/). Using langchain‑mcp‑adapters, developers can convert MCP tools into standard LangChain tools, enabling seamless access to external data and APIs.

Server.py code

First of all, we import libraries:

from mcp.server.fastmcp import FastMCP
FastMCP is the high-level API from the MCP Python SDK. It handles all the protocol details for you, such as JSON-RPC messaging, capability negotiation, and schema generation.

Step 1: Create the server

mcp = FastMCP("WeatherServer")
Step 2: Add the Tool: get_weather

The following code shows how to add a simple MCP tool named get_weather using the @mcp.tool() decorator.

@mcp.tool()
def get_weather(city: str) -> str:
    """Get the current weather for a given city."""
    # Fake data for demo purposes
    fake_weather = {
        "london": "15°C, cloudy",
        "paris": "18°C, sunny",
        "tokyo": "22°C, humid",
        "new york": "12°C, windy",
    }
    result = fake_weather.get(city.lower())
    if result:
        return f"Weather in {city}: {result}"
    return f"Sorry, no weather data available for '{city}'."
Step 3: Next, define the Resource.

Resources are read-only data endpoints like GET requests in a REST API. The URI template greeting://{name} means a client can read greeting://Alice and the {name} parameter gets passed as Alice to the function.

@mcp.resource("greeting://{name}")
def get_greeting(name: str) -> str:
    """Return a personalized greeting."""
    return f"Hello, {name}! Welcome to the WeatherServer."
Step 4: Define prompt (weather_report)

Prompts are reusable prompt templates that clients can fetch. A client calls get_prompt("weather_report", {"city": "Tokyo"}) and gets back the formatted string. This is useful for standardizing how an LLM is requested to do something.

@mcp.prompt()
def weather_report(city: str) -> str:
    """Generate a prompt asking for a weather report."""
    return f"Please provide a detailed weather report for {city}, including temperature, humidity, and forecast."

This starts the server listening on stdin/stdout.

if __name__ == "__main__":
    mcp.run(transport="stdio")

Agent2Agent protocol

We studied A2A in Chapter 1, Understanding AI Agents on AWS, where we looked into an example of a travel agent trying to coordinate between multiple agents such as a flight agent, hotel agent and others to plan a trip.

A2A serves as a standardized bridge that allows diverse systems such as those built on LangGraph, CrewAI, or Google ADK and AWS Strands SDK to communicate, discover one another, and manage shared workflows across different organizations.

Originally introduced by Google in 2025 and merged with IBM's Agent Communication Protocol (ACP), it is now a vendor-neutral project governed by the Linux Foundation. A2A is dedicated to peer-to-peer agent interaction, allowing opaque agents to delegate complex tasks and handle open-ended problem-solving while keeping their internal implementation details private, and the MCP focuses on connecting agents to specific tools and functions.

Understanding the difference between MCP vs A2A

MCP is an emerging standard focused on connecting LLMs with data and external resources. The focus of MCP is to reduce the complexity involved in connecting agents with tools and data. Tools are typically stateless and perform specific, predefined functions (for example, a calculator or a database query). However, this distinction raises an important question: can we encapsulate agent as tools via MCP?

The practice of encapsulating an agent as a simple tool is fundamentally limiting, as it fails to capture the agent's full capabilities. Tools are for executing actions, while agents are for solving problems. Treating agents as tools oversimplifies their capabilities and breaks their ability to handle complex, iterative, and collaborative workflows.

The Agent2Agent (A2A) protocol is designed to standardize communication between AI agents, particularly those deployed in external systems. A2A is positioned to complement MCP, addressing a distinct yet related aspect of agent interaction. The focus of A2A is enabling agents to collaborate within their native modalities, allowing them to communicate as agents (or as users) rather than being constrained to tool-like interactions. This enables complex, multi-turn interactions where agents reason, plan, and delegate tasks to other agents. Let's take an example.

Having established why agents cannot be reduced to tools and how A2A enables true inter-agent collaboration, we now move from concept to structure. In the next section, we explore the A2A architecture in detail, how agents are discovered, how they communicate through standardized messages, and how tasks, artifacts, and agent cards enable scalable, interoperable multi-agent systems.

Why is a standardized protocol needed for agents?

As agents become more capable, they also become more specialized and more likely to work as part of a larger multi-agent system rather than in isolation. However, today's agent ecosystem is fragmented across different frameworks, vendors, and implementation styles, making collaboration difficult. A2A is needed to provide a common protocol that allows agents to communicate, coordinate, and work across organizational and technical boundaries without requiring them to share their internal implementation details. Some of the reasons why A2A is needed for multi-agent collaboration are shown in the following diagram:

Figure 5.15: Why A2A is needed
Figure 5.15: Why A2A is needed

Let's expand on the details shown in the preceding diagram:

Solve framework fragmentation: Currently, there are numerous frameworks for building agents (such as LangGraph, CrewAI, and Microsoft's framework), but they are not compatible with each other out of the box. A2A provides a shared protocol so agents can communicate regardless of the specific model or language they use.
Enable complex collaboration: As AI evolves from simple chatbots to "agentic systems," complex tasks (like planning a full trip with flights, hotels, and activities) require multiple specialized agents to work together. A2A provides the standardized structure and methods needed for this coordination.
Act as a common language (the HTTP analogy): Just as the World Wide Web needed HTTP to allow data transfer across different systems, the agent landscape needs A2A to serve as a universal bridge, allowing the ecosystem to grow beyond siloed applications.
To facilitate cross-organization workflows: A2A allows agents to collaborate across different teams and even different organizations. It allows these agents to remain opaque, meaning they can work together without needing to expose their internal implementation details or private code.
To preserve agent capabilities: While protocols like MCP are designed to connect models and agents to tools, an agent should not always be reduced to a simple tool invocation. Many tool calls can themselves involve reasoning and non-deterministic behavior, but agents typically operate at a broader level: handling ambiguity, managing multi-step workflows, coordinating with other agents, and pursuing open-ended goals. A2A is needed to support that richer form of interaction.
To ensure vendor neutrality: Being hosted by the Linux Foundation and governed by a technical steering committee, A2A prevents a single company from controlling how agents interact, ensuring the protocol evolves based on the needs of the entire community.
With the motivation for A2A now established, the next step is to see how these ideas apply in practice. A concrete multi-agent example makes it easier to understand how specialized agents communicate, coordinate, and complete a shared business task.

How A2A architecture works

A key technical feature of how A2A works is that agents remain opaque. The protocol only standardizes the bridge between them. Agent A does not need to know Agent B's internal code, what prompts it uses, or what database it queries; it only needs to know how to format the A2A request and interpret the A2A response. Figure 5.17 shows how two agents communicate using the A2A protocol, highlighting the roles of a client agent and a server (remote) agent:

Figure 5.17: Long term memory
Figure 5.17: Long term memory

Let's study in detail what these components represent:

Agent A: This is the Client Agent that starts the conversation and makes a request for work to be done. Usually, the Client Agent is the front-facing agent that interacts directly with the end-user. It is responsible for discovering other agents. It looks for the Agent Card of other agents to see what they are capable of.

Agent B: This is also referred to as the Remote Agent or Server Agent. The Remote Agent is the one that receives the request and performs the specific task. It acts as the server because it hosts its capabilities at a specific URI and publishes its Agent Card (at well-known/agent-card.json) so others can find it. It decides how to fulfill the request. If a task is simple, it acts like a standard server and returns a message immediately. If the task is complex, it creates a Task and manages the lifecycle of that job until it produces an Artifact (or the result). Below is an example of how an agent card looks for Weather Agent or Agent B in this case:

{
  "name": "Weather Agent",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "skills": [
    {
      "id": "get_weather",
      "name": "Get Weather",
      "description": "Returns current weather conditions for a given city."
    }
  ],
  "url": "https://api.example.com/weather-agent/"
}
Agent Card can include both capabilities and skills: capabilities tell other agents how this agent communicates, while skills tell them what work it can perform.

A key feature of the Server/Remote agent is that it is opaque. It doesn't have to show the Client Agent how it works internally (what code it uses or what models it runs); it only needs to provide the output defined by the protocol.

Next, let's explore how communication happens:

Discovery via Agent Cards: Agents identify each other using an Agent Card (a JSON file hosted at a well-known URL). Similar to a Swagger/OpenAPI doc, this card acts as a digital business card, detailing the agent's name, capabilities, supported protocols, media types, and authentication requirements. It contains:

Agent's URI (endpoint)
Supported protocol bindings (e.g., HTTP)
Protocol bindings: Protocol bindings are defined in an agent's Agent Card (the well-known/agent-card.json file). This tells the Client Agent exactly which language or technical format it needs to use to interact with that specific Remote Agent. You can think of it like this: while A2A provides the language, Protocol binding is the physical connection used to send that language from one agent to another.

Imagine you have a letter written in English (the common language). A2A supports three ways of transport or protocol bindings:

HTTP Binding: Like sending the letter through Standard Mail. It's the most common and easy to use.
gRPC Binding: Like sending the letter via a High-Speed Courier. It's faster and more efficient for heavy data.
JSON-RPC Binding: Like sending the letter via a Telegram. It follows a very specific set of remote-control rules.
If one agent is only using a gRPC pipe and the other is only using an HTTP pipe, they actually cannot talk directly. They need to agree on which protocol binding to use which can be defined in their agent cards.

Understanding A2A data model

In A2A, the client agent sends a message composed of one or more parts. The remote agent may create a task to track execution, and that task produces artifacts containing the output parts. The flow is shown in Figure 5.18:

Figure 5.18: The A2A data model workflow
Figure 5.18: The A2A data model workflow

The client uses GetTask to check task status and retrieve results. When the remote agent begins processing that request, it may create a Task to track the work over time. As the task progresses or completes, it produces Artifacts, which are output containers that also contain one or more Parts. The client can call GetTask to retrieve the latest task status and any artifacts returned so far.

Communication styles in A2A

There are four execution modes to handle different types of tasks; A2A supports four communication styles.

Figure 5.19: Long-term memory
Figure 5.19: Long-term memory

Synchronous

This style is for simple, immediate responses. In A2A, synchronous execution works in a simple request-response manner where Agent A sends a message to Agent B using the SendMessage method, and Agent B immediately processes the request and returns a response. In this mode, the client agent waits for the result, making it suitable for quick, short-lived tasks.

Asynchronous

For complex jobs or long-running jobs, asynchronous communication is used when a task takes time and the client agent should not wait (block) for the result. The agent returns a Task ID, and the requester polls for status updates (e.g., submitted, working, completed).

Figure 5.20: Async exchange between Agent A and Agent B via A2A protocol
Figure 5.20: Async exchange between Agent A and Agent B via A2A protocol

In asynchronous execution using polling, Agent A sends a request and Agent B responds with a Task object instead of the final result. This task includes a task ID and a status indicating its progress. Agent A does not wait but instead periodically calls the GetTask method using the task ID to check the status. Once the task reaches a completed state, the final results are returned as artifacts.

Streaming

This communication style uses Server-Sent Events to provide real-time updates or chunked text as it is generated. This enables you to see live progress updates, as shown in Figure 5.21:

Figure 5.21: Agent A and B with streaming
Figure 5.21: Agent A and B with streaming

In streaming execution, real-time updates are enabled only if the server declares support by setting capabilities.streaming = true in its Agent Card. Agent A uses the SendStreamingMessage method, and the server responds with an open HTTP connection (text/event-stream). Over this connection, Agent B continuously sends updates such as task status changes, intermediate messages, and partial results. These updates are delivered as structured events, allowing the client to receive progress and results incrementally until the task is complete.

Push notifications

You can use push notifications in A2A when tasks take a long time or the client cannot stay connected continuously. Instead of polling or streaming, the client provides a webhook URL, and the server notifies it when important events occur, such as task completion or when input is required. For example, in a healthcare workflow, a pharmacy agent can notify the system when a prescription is ready after several hours. In a travel booking scenario, a flights agent can send a notification when ticket booking is confirmed. This approach is ideal for long-running, event-driven workflows where continuous connection is not practical. Figure 5.22 gives an overview of the workflow:

Figure 5.22: Agent A and Agent B with push notifications true
Figure 5.22: Agent A and Agent B with push notifications true

Push notifications are enabled only if the server declares capabilities.pushNotifications = true in its Agent Card. Agent A provides a PushNotificationConfig (including a webhook URL and optional authentication) either during the initial request or via a separate method. Agent B then sends HTTP POST notifications to this webhook whenever there are significant updates, such as task completion or input required. After receiving a notification, Agent A typically calls GetTask to retrieve the full task details and results.

Now that we have covered the A2A concepts, let us see how they are implemented in practice.

How to implement A2A

The easiest way to understand the implementation landscape is to think of it in three layers:

Core protocol layer – the A2A SDK
Framework integrations – libraries that sit on top of the SDK and reduce boilerplate
Platform-specific implementations – hosted or framework-specific ways to expose A2A endpoints
This hierarchy matters because all three layers solve different problems. The A2A SDK gives you the protocol primitives. Integrations such as AWS Strands build on top of those primitives to make agent-to-agent communication easier to use inside a framework. Platform offerings such as LangSmith Agent Server expose A2A endpoints for deployed agents in a managed environment.

Core protocol layer: the A2A SDK

At the foundation is the A2A SDK (a2a-sdk), which is the low-level protocol library. This is the most direct way to build an A2A-compatible client or server. It provides the raw protocol building blocks, including data types such as Message, TextPart, AgentSkill, and AgentCapabilities, along with client-side utilities such as A2ACardResolver, ClientFactory, and ClientConfig. In other words, the SDK gives you the objects and interfaces needed to construct messages, discover remote agents through agent cards, send requests, and process responses.

If you use only the A2A SDK, you are responsible for wiring these pieces together yourself. That gives you full control, but it also means more protocol plumbing. You must explicitly define how your server publishes its capabilities, how incoming requests are routed, how tasks are created and updated, and how responses are returned to the client.

Higher-level layer: framework integrations

On top of the A2A SDK are higher-level integrations that make it easier to use A2A inside an agent framework. These integrations do not replace the protocol. Instead, they implement the protocol for you while preserving the framework's programming model. Some good examples are Google ADK and AWS Strands A2A (strands-agents[a2a]). We will cover AWS Strands A2A SDK in this chapter.

Strands provides two especially important abstractions:

A2AServer: Exposes a Strands agent as an A2A-compliant server.
A2AAgent: Lets you consume a remote A2A server as if it were a local Strands agent.
This means that the A2A SDK remains the protocol foundation, but Strands gives you a more convenient developer experience for building and consuming A2A-enabled agents.

Platform-specific layer: LangChain and LangSmith

A third layer consists of platform-specific implementations. this is represented by LangSmith Agent Server, which is the primary way LangChain currently exposes A2A support. In this case, the platform handles the protocol details such as JSON-RPC messaging and task management for agents deployed on that platform. Your agent still participates in A2A communication, but the hosting layer manages much of the operational behavior for you.

So far, the distinction should be clear:

A2A SDK = protocol primitives
Strands A2A = framework integration built on the SDK
LangSmith Agent Server = managed platform endpoint for deployed agents
That separation makes the ecosystem easier to understand.

In this chapter, we will use Strands A2A for the implementation example because it gives us the cleanest path from an agent definition to a working A2A server on AWS.

The Travel Orchestrator is implemented in the travel_orchestrator.py file. This is the A2A client and it does not use an LLM as it simply sends A2A messages to the two agent servers and prints the results. Here's the complete workflow of this agent:

Step 1: Build an A2A message

def make_message(text: str) -> Message:
    return Message(
        kind="message",
        role=Role.user,
        parts=[Part(TextPart(kind="text", text=text))],
        message_id=uuid4().hex,
    )
This creates a standard A2A Message object with a text part, just like a user typing in a chat.

Step 2: Discover the agent and send the message.

async def send_a2a_message(base_url: str, text: str) -> str:
    async with httpx.AsyncClient(timeout=TIMEOUT) as hc:
This further involves multiple steps:

Fetch the agent card from /.well‑known/agent‑card.json file:

A2ACardResolver fetches the agent card, which is a JSON document describing the agent's capabilities; ClientFactory then creates an A2A client configured specifically for that agent; and send_message sends a JSON-RPC message/send request and yields response events.

def extract_text(result) -> str:
    if hasattr(result, "artifacts") and result.artifacts:
        texts = []
        for artifact in result.artifacts:
            for part in artifact.parts:
                texts.append(part.root.text)
        return "".join(texts)

    print(f"Flights: {flights}")
The A2A protocol flow between client and server is as follows:

The client fetches the agent card to discover what the agent can do
The client sends a message/sends a JSON-RPC request with the user's question
The server's Strands Agent processes the message, calls its tools, and returns a task with artifacts containing the final text response

Summary

In this chapter, you learned how standardized communication protocols make agentic systems easier to build, extend, and scale. You first explored MCP and saw how it solves the growing complexity of connecting agents to many tools and data sources. Instead of building separate integrations for every model and every external system, MCP introduces a shared interface through clients and servers, making tool discovery, resource access, and prompt reuse more consistent and maintainable. You also learned the main MCP concepts, including hosts, clients, servers, transports, lifecycle management, authorization, and server capabilities such as tools, resources, and prompt templates.

You then explored the A2A Protocol, which addresses a different but equally important problem: enabling agents to collaborate with other agents. Unlike tools, agents are open-ended problem solvers that can reason, delegate, and participate in multi-step workflows. A2A provides a standard way for agents to discover each other through agent cards, exchange messages, manage tasks and artifacts, and support different execution modes such as synchronous requests, asynchronous polling, streaming, and push notifications. This makes it possible to build multi-agent systems where specialized agents work together without exposing their internal implementation details. Through the hands-on examples, you saw both protocols in action. You built an MCP-based weather assistant with FastMCP and then extended the ideas into a multi-agent travel scenario using Strands and A2A, where a travel orchestrator communicates with weather and flight agents.

MCP and A2A complement each other because they address two different layers of interoperability in agentic systems. A2A enables collaboration between the agents, and MCP enables each agent to do its own work by using external tools and data.
