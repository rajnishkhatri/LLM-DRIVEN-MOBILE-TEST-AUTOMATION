Chapter 6: Production Deployment And Enterprise Integration
6

Over the past five chapters, you've built agents that reason, use tools, remember conversations, and work in teams. You gave them access to web search, file systems, and APIs. You added short-term and long-term memory backed by AgentCore memory. You coordinated multiple specialized agents through supervisor-worker, swarm, and graph patterns, and explored Agent Communications with MCP and A2A. All of this runs nicely on your laptop.

However, running agents in production is different. The moment someone says, let's put this in front of real users, you're dealing with questions nobody asked during development. What happens when 200 people hit your agent at the same time? Or what happens when the model provider has a bad day? Similarly, if your agent crashes at 3 AM and nobody notices until Monday, what would you do?

The AI part isn't what slows teams down; it's the infrastructure, networking, IAM (Identity and Access Management) policies, and other factors. What should have been a two-day deployment task turns into a week-long troubleshooting because nobody on the team has deployed a containerized application before, and the error messages aren't easy to debug.

This chapter is about closing that gap, not by turning you into a DevOps engineer, but by giving you enough to get your agents running in production. Though for production-hardened deployments with custom networking, compliance requirements, multi-region failover, etc., you'll want to partner with your infrastructure team.

We'll start with the simplest deployment path (AWS Lambda), move to always-on containers (Amazon ECS), and then explore Amazon Bedrock AgentCore, which is a platform built specifically for production agents. By the end of this chapter, you'll have a clear understanding of choosing the right deployment path and the patterns for connecting your agents to enterprise databases, APIs, and event-driven systems.

Deployment path

Suppose you've built a document analysis agent. A customer uploads a contract to your web app, which calls the agent behind the scenes. The agent extracts key terms, flags risky clauses, and returns a summary. The whole thing takes about 30 seconds. Traffic is unpredictable—maybe 10 requests on a quiet Tuesday, and around 500 during end-of-quarter rush.

Now let's say there is a different agent in the hospital, connected to the electronic health records system, maintaining persistent sessions with scheduling databases and provider calendars. Establishing those connections takes time and authentication overhead you don't want to repeat on every request. It handles requests from staff around the clock, and the workflow for booking an Operating Room can involve multiple back-and-forth calls across systems in a single session.

These two agents have completely different infrastructure needs. The first one, with short-lived tasks, unpredictable traffic, and no state between requests, is a perfect fit for serverless. The second one, with persistent connections, multi-turn sessions, and always-on availability, needs an always-on container.

AWS gives you four options for running agents in production: AWS Lambda, Amazon Elastic Container Service (Amazon ECS), Amazon Elastic Kubernetes Service (Amazon EKS), and AgentCore. Each one fits a different set of constraints, and picking the wrong one won't end your project, but it can cost you weeks of rework. Let us explore each path.

AWS Lambda: Serverless and event-driven

Back to that document analysis agent. A customer uploads a contract, and your agent needs to process it. You don't want to run a server 24/7 waiting for uploads that might come once an hour or once a minute. You just want your code to run when a document arrives, process it, and stop.

AWS Lambda lets you attach your code to that upload event directly. You write a handler function, connect it to a trigger (an S3 upload, an API Gateway request, a scheduled event), and AWS Lambda runs it when the trigger fires. Here's a Strands agent running on AWS Lambda:

from strands import Agent
from strands.models.bedrock import BedrockModel
# Initialize outside the handler — this is the key decision
model = BedrockModel(model_id="us.anthropic.claude-sonnet-4-20250514-v1:0")
agent = Agent(model=model, system_prompt="You are a document analysis assistant...")
def lambda_handler(event, context):
    document_text = event["body"]["document_text"]
    result = agent(f"Analyze this contract:\n\n{document_text}")
    return {"statusCode": 200, "body": str(result)}
The agent is initialized outside the handler function. AWS Lambda doesn't spin up a fresh Python process for every request. When traffic is flowing, it reuses the same execution environment across invocations. Your model and agent objects survive between calls. The first request pays the initialization cost: loading the Strands library, establishing the Amazon Bedrock connection, parsing the system prompt. Every subsequent request skips all of that and goes straight to the handler. You can move that initialization inside the handler, and you'll be paying the setup cost on every single invocation and unnecessary latency that adds up.

The GitHub repository has the production version of this code with proper API Gateway request parsing, input validation, and error handling.

The deployment uses a Serverless Application Model (SAM) template – a YAML file where you define the AWS Lambda function, the API Gateway trigger, the IAM permissions, and the container configuration, and deploy it all with a single command. The full template lives in the companion repository, but two pieces are worth understanding here because they're easy to get wrong and hard to debug when you do.

The first is the IAM policy:

Policies:
  - Statement:
      - Effect: Allow
        Action:
          - bedrock:InvokeModel
          - bedrock:InvokeModelWithResponseStream
        Resource:
          - "arn:aws:bedrock:*::foundation-model/*"
          - !Sub "arn:aws:bedrock:*:${AWS::AccountId}:inference-profile/*"
Two resource types, not one. The foundation‑model/* ARN (Amazon Resource Name) covers direct model access. But if you're using a cross-region inference profile (and you are, because model IDs that start with us. like us.anthropic.claude‑sonnet‑4‑20250514‑v1:0 are inference profile IDs), then your AWS Lambda functions also need permission to invoke inference profiles. Without the second resource, you'll get an access denied error that doesn't clearly indicate which permission is missing. Ideally, you should include both from the start.

Then there's the container packaging. Agent dependencies (Strands, tool libraries, boto3, and whatever your tools pull in) add up fast. AWS Lambda's zip deployment has a 250MB limit, and agent workloads blow past that routinely. The template uses PackageType: Image instead, which gives you up to 10GB of headroom. When you write a standard Dockerfile, SAM builds the image, and AWS Lambda runs it. The trade-off is slightly slower cold starts compared to zip, but since you'd exceed the zip limit anyway, it's not really a choice.

Also worth knowing: Amazon Bedrock model IDs require the full version string. The model ID is us.anthropic.claude‑sonnet‑4‑20250514‑v1:0, not us.anthropic.claude‑sonnet‑4‑20250514. Drop the ‑v1:0 suffix and you'll get a model-not-found error that doesn't explain what's wrong. The template stores this as an environment variable so you can swap models without redeploying code.

The GitHub repository includes a deploy script that handles the full workflow:

chmod +x deploy.sh cleanup.sh
./deploy.sh
The script checks prerequisites (SAM CLI, Docker, AWS credentials), auto-detects whether you're on an ARM or Intel machine, builds the container image, and deploys everything through CloudFormation. Two to three minutes later, it prints an API endpoint. POST a contract to that URL; your agent analyzes it. On Windows, run this from WSL or Git Bash. When you're done, ./cleanup.sh tears down every resource the deployment created.

If this looks familiar, it's the same agent-with-tools pattern from earlier chapters we learned, now packaged inside a single Lambda function with API Gateway as the entry point.

A user sends a query through API Gateway, which invokes the Lambda function. Inside that function, your agent sits at the center. It calls out to the LLM (Amazon Bedrock, in this case) for reasoning, and invokes tools to perform specific tasks like clause extraction or risk scoring. Those tools are just Python functions bundled within the same Lambda package; they run in-process, in the same execution environment. The LLM sits outside the Lambda boundary because it's a remote API call over the network. There are no queues, no orchestration layers, no sidecar containers. One function, one agent, and just one execution environment.

There are three things about AWS Lambda that will shape how you design your agent:

Statelessness: Each invocation is independent. If a customer uploads a contract and your agent asks a clarifying question, then the customer responds, that's a new invocation. The agent doesn't remember the first interaction unless you explicitly persist conversation state somewhere between calls and restore it on the next invocation. You can solve this with DynamoDB: store the conversation history keyed by a session ID, load it at the start of each invocation, and save it at the end. The hands-on tutorial at the end of this chapter provides a walk-through of this pattern. But it's the kind of thing you won't think about until your users complain that the agent has amnesia.
Cold starts: Monday morning, nobody has used the agent since Friday. A customer uploads a contract, and instead of the usual sub-second response, they wait 2 to 5 seconds while Lambda spins up a fresh execution environment and loads your dependencies. That's a cold start. It only happens on the first invocation, or when Lambda scales up new instances during a traffic spike, but it's noticeable. Container images make cold starts slightly slower than zip deployments because there's more to load, but since agent dependencies typically exceed the 250MB zip limit anyway, that's a trade-off you're already making. Provisioned concurrency keeps set number of Lambda instances pre-warmed and ready to go, though at that point you're paying for idle compute, which undercuts one of Lambda's main advantages.
The execution ceiling: Your document analysis agent works great for simple contracts. But a month in, a customer uploads a 200-page contract and your agent needs to call the model multiple times, cross-reference clauses, and generate a detailed report. Twelve minutes in, Lambda kills the invocation. You've hit the 15-minute maximum limit. For most single-agent tasks, 15 minutes is plenty. But for multi-agent workflows with retries and slow external calls, you'll hit this wall. Lambda's durable functions, announced at re:Invent 2025, use a checkpoint-and-replay mechanism: the function reruns from the start but skips over completed checkpoints, resuming execution from where it left off. But that adds complexity to your design.
AWS Lambda works well when your agent responds to an event, does its work, and finishes. If your agent needs to stay running, maintain persistent connections, or coordinate a team of agents in a long-running process, you need something with more staying power. That's next!

Amazon ECS: Always-on and container-driven

A nurse walks up to a scheduling terminal at 2 AM and types: Is Dr. Arti available Monday for a knee replacement? The agent checks the calendar and responds with three open slots. The nurse types back: The 9 AM slot works, patient ID is P‑1234. The agent books it, confirms equipment availability for OR-3, and sends notifications.

There are two messages. The second one only makes sense because the agent remembers the first. And this isn't a one-off interaction. Staff use this system around the clock, and each conversation might be three, four, or five messages deep before a procedure gets booked.

You could build this on AWS Lambda. Persist the conversation in DynamoDB, reload it on every invocation, rebuild the agent's context each time. It would work. But you'd be fighting the infrastructure instead of building the feature. A Lambda function wants to wake up, do a thing, and go away. This agent needs to be awake, warmed up, and ready at all times.

Amazon ECS gives you that. You put your agent in a Docker container, hand it to Amazon ECS, and tell it to keep this running. When you run it as an Amazon ECS service, it stays up. If the container crashes at 3 AM, the service notices and starts a new one. You don't get paged. You don't write recovery scripts.

From Lambda handler to web server

The mental shift from Lambda to ECS: on Lambda, your agent is a function that gets called. On ECS, your agent is a web server that's always listening.

The Lambda version looks like this:

def lambda_handler(event, context):
    result = agent(event["body"]["document_text"])
    return {"statusCode": 200, "body": str(result)}
Something calls your function, you respond, and you're done. The ECS version flips that around:

app = FastAPI()
model = BedrockModel(model_id="us.anthropic.claude-sonnet-4-20250514-v1:0")
@app.post("/schedule")
async def schedule(request: ScheduleRequest):
    agent = Agent(model=model, tools=[...], system_prompt=PROMPT)
    # Feed in the conversation so far
    for msg in request.history:
        agent.messages.append({"role": msg.role, "content": [{"text": msg.content}]})
    return str(agent(request.message))
Your agent boots up, opens a port, and waits. Requests come anytime. The model object and boto3 session initialize once when the container starts and persist for the life of the container. No cold starts between requests and no rebuilding the agent from scratch on every call.

The conversation history part is worth pausing on. Each request carries request.history object, the full conversation so far. The frontend keeps track of everything the user and agent have said, and sends it all with every new message. The agent gets seeded with that history before processing the latest message. That's how, when the nurse says "the 9 AM slot works" in message two, the agent still knows she is referring to Dr. Arti and a knee replacement from message one.

This is the simplest approach, but not the only one. Strands has a built-in session management system that can persist conversation history to the local filesystem or to Amazon S3, and you can implement a custom session repository backed by DynamoDB or any database. Those approaches are better for production because the server owns the state. The frontend-carries-history pattern works well for demos and lightweight deployments where you don't want to set up a persistence layer, but for anything with real users, you'd want the conversation stored server-side so it survives page refreshes and can be audited.

What's actually happening on AWS

You don't need to be a networking expert to understand the Amazon ECS deployment model. Here's what it looks like:

Figure 6.2: Agent deployed on Amazon ECS
Figure 6.2: Agent deployed on Amazon ECS

A user opens a URL in their browser. That request hits a load balancer, which routes traffic to healthy containers. If you're running two containers and one dies, the load balancer sends everything to the surviving one while Amazon ECS spins up a replacement. Your users don't notice.

Behind the load balancer, an Amazon ECS service keeps your containers running. You tell it, I want two copies of my agent running at all times, and it makes that happen. If the container crashes, it gets replaced. And if you need to deploy a new version, the service rolls it out gradually, keeping the old version running until the new one passes health checks.

Each container runs from a task definition, which is a config file that says: use this Docker image, configure it with specific CPU and memory, and send its logs to CloudWatch. Think of it as a recipe card. The service is the kitchen that follows the recipe.

For the compute itself, you have two options. AWS Fargate means you specify CPU and memory and AWS handles the servers. You never see an EC2 instance, never patch an operating system, never think about capacity. Amazon EC2 launch type means you manage the underlying instances yourself, which you'd only do if you need something Fargate can't provide, like a GPU. We would recommend that you start with Fargate and later you can switch to EC2 launch type, if needed.

The GitHub repository has a sample deployment that puts all of this together. It's not production-hardened (the tools return mock data, there's no authentication, error handling is minimal), but it walks through every step of getting a Strands agent onto Amazon ECS with AWS Fargate. You need to first clone the repo, navigate to the ECS deployment directory, and run:

chmod +x deploy.sh cleanup.sh
./deploy.sh
Four minutes later, you get a URL. Open it in your browser and you'll see a chat interface. Try typing, Is Dr. Smith available next Tuesday for a knee replacement?, and follow up with just a time slot and patient ID. The agent connects the dots across messages. The point isn't the scheduling app itself. It's seeing the full journey from Python code on your laptop to a running agent behind a public URL on AWS, and being able to read through the deploy script to understand each step.

When you're done, ./cleanup.sh tears everything down. The README covers networking details, IAM configuration, and troubleshooting for readers who want to dig into the infrastructure side.

When to reach for Amazon ECS

Amazon ECS comes into its own in two scenarios.

The first is multi-agent systems. The e-commerce order processing system from Chapter 4 had six specialized agents coordinating through the graph pattern: risk analysis, fraud detection, inventory, shipping, the whole pipeline. On ECS, all of those agents live in the same container, talking to each other through plain function calls. No network hops, no serialization overhead, no message queues between them. You deploy the entire team as one unit and scale by adding more container replicas.

The second is anything with expensive startup costs: database connection pools that take seconds to establish, authenticated sessions with third-party APIs that involve OAuth token exchanges, and ML models loaded into memory. On ECS, that happens once when the container starts and persists for the life of the container. On AWS Lambda, you'd pay some of that cost on every cold start, and all of it when the Lambda function scales up new instances during a traffic spike.

Amazon Bedrock AgentCore

In the last two sections we covered deploying agents on AWS Lambda and Amazon ECS. That meant writing Dockerfiles, configuring load balancers, setting up IAM roles, putting health checks in place, and managing task definitions. And these are the simple versions. There is a lot that gets added when we need to productionize an agent, such as monitoring, auto-scaling policies, managing certificates, configuring Virtual Private Cloud (VPC), and a dozen other things that have nothing to do with your agent's actual job.

All these things discussed in the preceding lines are not agent specific. Everything that you do to productionize the agent, you'd do the same way for REST API, batch processors, building websites, etc. The infrastructure doesn't know or care that it's running an AI agent. But agents have problems that generic compute doesn't solve for you: per-user session isolation so one conversation can't leak into another, tool-level authorization so an agent can't exceed its boundaries, identity propagation so tools act on behalf of the right user, and observability that captures reasoning steps and not just HTTP error codes. We are left with building all of that ourselves on ECS/EKS or Lambda.

This is where Amazon Bedrock AgentCore comes in. We introduced AgentCore in Chapter 1, Understanding AI Agents on AWS, as part of the AWS AI stack, a managed platform sitting between the fully-managed Bedrock Agents tier and the do-it-yourself infrastructure tier. In Chapter 3, Agent Memory, we used AgentCore Memory to give agents short-term and long-term memory across sessions. Those were individual services solving individual problems. Now we'll look at how the full set of AgentCore services fits together and what the platform actually means for getting your agents into production.

The AgentCore architecture

AgentCore is an AWS managed platform, where you get a set of composable services, each solving a specific production challenge that every team hits when they try to move agents from the prototyping phase to production. You can use all of them together, or pick the ones you need.

Every box shown in Figure 6.3 solves a problem you'd otherwise build yourself. Understanding the architecture is what turns AgentCore from another managed service into a genuine shortcut to production.

Let us look at each of the components:

Runtime is where your agent actually executes. It's framework-agnostic. It consists of Strands, LangGraph, CrewAI, LlamaIndex, OpenAI Agents SDK, Google ADK, Claude Agent SDK, or any custom framework you would like to use. Runtime doesn't care. It hosts the agent, connects it to whatever model you choose—Bedrock, OpenAI, Anthropic, Google, etc. The Agent in Runtime can be exposed through the Agent-to-Agent protocol we covered in Chapter 5, so agents on other platforms can discover and talk to yours.

Now look at what surrounds Runtime. On the right side, Gateway takes your enterprise APIs (described as OpenAPI specs, Smithy models, Lambda functions, or remote MCP servers) and turns them into MCP-compatible tools your agent can discover and call. No integration code to write per API.

Below Gateway, Browser and Code Interpreter are managed tool runtimes: Browser gives your agent a sandboxed browser for interacting with web pages, and Code Interpreter provides an isolated sandbox for running Python, JavaScript, or TypeScript. All three show up as tools your agent can call, indistinguishable from custom tools you wrote yourself.

Identity and Policy sit at the boundary. Identity handles authentication in both directions: users authenticating to your agent (via Cognito, Okta, Entra ID, or standard OAuth) and your agent authenticating to external services on behalf of those users. Without this, either anyone could call your agent, or your agent couldn't prove who it's acting for when it calls downstream APIs. Policy provides deterministic governance, with rules written in Cedar (an open-source policy language developed by AWS) that intercept every tool call before it executes. When a policy says "no refunds over $1,000," that's enforced at the infrastructure level, and not inside the agent's reasoning loop. No amount of prompt engineering overrides it. We will cover identity later in this chapter, and policy with Cedar-based rules in the final chapter.

Memory is the same service you covered in Chapter 3, Agent Memory. Short-term memory for conversation flow, long-term memory for learning across sessions. Here, it's wired directly into Runtime as a managed service.

Observability spans the bottom of the diagram because it captures everything across all services: reasoning steps, tool invocations, model calls, policy decisions, latency, errors. It's built on OpenTelemetry, so it plugs into whatever monitoring stack you already run (CloudWatch, Datadog, Grafana, Splunk, etc.). We'll cover this in detail in the final chapter.

Evaluations sits alongside Observability, offering LLM-as-judge scoring, built-in evaluators for faithfulness and relevance, and continuous online evaluation in production. We'll cover evaluations in Chapter 7, Evaluation, Observability, and AI Governance.

One important thing to note about AgentCore is that these services are composable. You can pick and choose what service you want to use from here. Run your agent on ECS but use Gateway for tool integration. Use Runtime for hosting but manage your own authentication. Use just Memory if that's all you need. Each service has its own API, so you can adopt them independently. But when you use them together, they're integrated. Identity flows through to Gateway, Runtime connects to Memory automatically, Observability captures the full picture without you instrumenting anything.

Now let's look at how all of these pieces work together. Let's walk through a real interaction. A user asks your agent, Analyze this sales data and create a summary report.

Authentication: The request goes through AgentCore Identity, which validates the user's bearer token against their identity provider and creates appropriate session credentials
Agent processing: The request hits your agent running in AgentCore Runtime, which checks AgentCore Memory for context about this user and previous interactions, including long-term memory insights like this user prefers visual charts and usually asks for quarter‑over‑quarter comparisons
Tool discovery: The agent queries AgentCore Gateway: I need tools for data analysis and report generation. Gateway's semantic search returns the most relevant tools from the catalog.
Policy evaluation: Before any tool executes, AgentCore Policy intercepts the call and evaluates it against Cedar rules. It may ask the following questions: Can this user query sales data only for their own region, or across the entire company? Is the report limited to a specific department or product category? Can the agent call the export tool? Only if Policy permits, only then the tool call will proceed.
Tool execution: Gateway routes the authorized tool calls. The agent uses Code Interpreter to analyze the data in a sandboxed environment, generates charts based on the user's known preferences, maybe uses Browser tool to pull additional market context from a web portal.
Memory update: AgentCore Memory stores the interaction. Short-term memory captures the conversation flow. In the background, long-term memory extraction runs—reinforcing the chart preference, noting that this user frequently asks for sales analysis, and storing any new facts mentioned during the conversation.
Observability and evaluation: Throughout this entire flow, AgentCore Observability captures every step - every authentication decision, the memory retrieval, every tool call with parameters and results, every policy evaluation, every model invocation. AgentCore Evaluations scores the interaction against quality criteria you've defined: was the report accurate, did the agent follow the right steps, and did it stay within scope. Both feed into the same trace, so you get a single view of what happened and how well it went.
The user sees a report with charts. Behind the scenes, the full AgentCore stack coordinates to make that happen securely, with governance, and with full traceability. On AWS Lambda or Amazon ECS, you'd build most of that coordination yourself.

Let us look at the Runtime component in the architecture and how we can deploy the agents in it.

AgentCore runtime

Runtime is where the Agent lives and executes. Each user session gets its own microVM, as shown in Figure6.4. The agent can maintain state, hold database connections, and accumulate context across multiple turns of conversation, all within that dedicated environment. When the session ends, the entire microVM is terminated and the memory is sanitized. There is no possibility of data leaking between sessions because there is nothing shared between them. For example, let's say in the financial services industry, an agent is processing one client's portfolio data, and with Agentcore runtime, there's zero chance of it leaking to another client's session.

Figure 6.4: Runtime Session Isolation
Figure 6.4: Runtime Session Isolation

Consider what happens during a multi-turn conversation. The user asks your agent to analyze a financial document. The agent extracts data, stores intermediate results, and may write temporary files while processing. On AWS Lambda, all of that state vanishes between invocations. On Amazon ECS, that state lives in a shared container where another user's request could theoretically access it. On AgentCore, each user gets their own sandbox. The agent can behave as if it is running on a dedicated machine, because it effectively is.

When a user sends a request, AgentCore creates a new session and spins up a microVM. That session moves through three states: Active while your agent is processing, Idle when it is waiting for the next user message, and Terminated when the session ends. The default idle timeout is 15 minutes—if the user goes quiet longer than that, the session terminates and the microVM is cleaned up.

The important thing to understand about the cost model is that you only pay for Active time. During the Idle state, the microVM remains provisioned and your session state is preserved. If your agent isn't doing any processing, CPU charges drop to zero and you are only billed for what your agent actually consumes, not for the time spent waiting. A typical customer support conversation where the user takes a minute between messages means you are paying for the 10-20 seconds of active processing per turn, not the silence in between.

So, how long can a session run? That depends on the invocation pattern. For synchronous request-response calls, the ceiling is 15 minutes per request, which is similar to AWS Lambda. Streaming connections (HTTP response streaming and WebSocket) can stay open for up to 60 minutes. And for heavy lifting tasks like batch processing, multi-agent research tasks, long document pipelines—asynchronous jobs can run for up to 8 hours. If your agent kicks off one of these longer operations, it signals HealthyBusy through the health check endpoint so AgentCore knows the session is working, not idle. The SDK provides add_async_task and complete_async_task helper functions that manage this automatically.

Now let's see how the deployment to agentcore runtime looks:

from bedrock_agentcore.runtime import BedrockAgentCoreApp
from strands import Agent, tool
from strands.models.bedrock import BedrockModel
app = BedrockAgentCoreApp()
@tool
def extract_clauses(text: str) -> dict:
    """Extract key clauses from contract text."""
    return {"clauses": ["termination", "liability", "indemnification"]}
model = BedrockModel(model_id="us.anthropic.claude-sonnet-4-20250514-v1:0")
agent = Agent(
    model=model,
    tools=[extract_clauses],
    system_prompt="You are a document analysis assistant..."
)
@app.entrypoint
def handle(payload):
    response = agent(payload.get("prompt"))
    return response.message["content"][0]["text"]
if __name__ == "__main__":
    app.run()
In the preceding code, only four things changed from local development code: we imported BedrockAgentCoreApp, created an app instance, decorated your invocation function with @app.entrypoint, and called app.run(). Behind the scenes, BedrockAgentCoreApp turns your agent into an HTTP service with two endpoints: /invocations for processing requests and /ping for health checks. We do not write any server code, the SDK handles all of it.

The agent logic is identical. Your tools, system prompt, and model configuration all remain the same code you have been writing since Chapter 2, Building Agents with Tools. You can test this locally by running python agent.py and sending a POST request to http://localhost:8080/invocations. For instance, if you run this in a terminal, you will see something like this:

The runtime is framework agnostic, meaning you can host Strands Agents, LangGraph, CrewAI, OpenAI Agents SDK, Google Agent Development Kit (ADK), Claude Agent SDK, or any custom framework. If your team has agents built with different frameworks, they all deploy the same way. This matters in practice because most organizations end up with agents in multiple frameworks, either through acquisition, team preferences, or because different frameworks suit different problems.

Let's talk about what framework-agnostic actually looks like in practice. Let's say your team has been building agents with Claude Code and you've already got a whole programming model going—your CLAUDE.md with project context, a skills/ folder with reusable capabilities, MCP servers wired up to your tools, maybe even sub-agents running jobs in parallel.

You can deploy all of that to AgentCore runtime as-is. You wrap your agent entry point with @app.entrypoint, add app.run() at the bottom of the code. The Claude Agent SDK handles its own tool discovery, skill loading, and sub-agent orchestration inside the microVM. Runtime doesn't know or care that it's running a Claude Agent SDK agent versus a Strands agent versus something you duct-taped together with raw API calls. It just manages the session, the isolation, and the scaling.

Deployment walkthrough

Now that you have agent code ready, let us walk through deploying it to AgentCore using the Python SDK. The AgentCore Starter Toolkit provides a Runtime class that handles the full lifecycle: configure, launch, invoke, and clean up:

from bedrock_agentcore_starter_toolkit import Runtime
from boto3.session import Session
region = Session().region_name
runtime = Runtime()
# Step 1: Configure — generates a Dockerfile, sets up IAM role and ECR
runtime.configure(
    entrypoint="agent.py",
    requirements_file="requirements.txt",
    auto_create_execution_role=True,
    auto_create_ecr=True,
    region=region,
    agent_name="doc-analysis-agent"
)
# Step 2: Launch — builds the container, pushes to ECR, deploys to Runtime
launch_result = runtime.launch()
The configure step generates a Dockerfile from your code, creates an IAM execution role with the permissions your agent needs, and sets up an Amazon ECR repository. The launch step builds the container image, pushes it to ECR, and creates the AgentCore Runtime endpoint. The first deployment takes a few minutes while it packages everything. Subsequent updates are faster because the toolkit reuses cached dependencies.

Once the endpoint is ready, you can test it through the toolkit's runtime.invoke() method. In production, you'd call the agent from other services using boto3's invoke_agent_runtime – which has a similar pattern as calling any other AWS service. Each invocation creates a session backed by a microVM, and that session costs money (vCPU and memory) while it's active. When a conversation is done, stop the session explicitly or configure an idle timeout so sessions clean themselves up. Try out the notebook of agentcore runtime in the GitHub repo associated with this chapter: https://github.com/PacktPublishing/AI-Agents-on-AWS/tree/main

You might have noticed the code snippet above the parameter auto_create_ecr=True, which built a Docker container behind the scenes. That's the direct code deployment path, where you hand it your source code and it handles the rest. If your team already has CI/CD pipelines that produce Docker images, you can bring your own container instead. Either way, Runtime doesn't care how the code arrived. One thing to know if you go the container route: AgentCore requires ARM64 images (Graviton), so you would have to plan your builds accordingly.

AgentCore Gateway

In Chapter 5, Agent Communication, you built MCP servers and clients from scratch. You saw how a single MCP server can expose tools, resources, and prompt templates through a standardized protocol, and how your agent discovers and calls those tools without custom integration code. That works well when you have a handful of MCP servers and you're writing the tool code yourself.

But most enterprises don't have MCP servers. They have hundreds of REST APIs described by OpenAPI specs, internal services behind authentication layers, and legacy systems that nobody wants to touch. Writing an MCP server wrapper for each one with auth, error handling, retries, and rate limiting is a full-time job. And when the API team changes an endpoint or rotates credentials, you're back in the code.

AgentCore Gateway bridges that gap. You point it at an OpenAPI spec, and it generates MCP-compatible tools automatically, with no server code to write, no wrapper to maintain. Your agent discovers those tools at runtime the same way it discovered tools from the MCP servers you built in Chapter 5, Agent Communication, except now the tools come from your existing API catalog instead of hand-built servers.

Gateway supports several backend types. You can point it at an OpenAPI spec for existing REST APIs, a Lambda function for custom logic, or a remote MCP server for tools that already speak the protocol. Each backend generates MCP-compatible tools automatically. Your agent sees tools and does not need to know what is behind them.

You can combine multiple APIs, functions, and existing MCP servers into a single tool catalog. Your agent does not need to know that check inventory hits a Lambda function while send notification goes through an API Gateway endpoint, while update CRM talks to Salesforce. From the agent's perspective, they are all just tools.

Targets

Gateway calls each registered API a target. You register a target by pointing Gateway at an API definition—an OpenAPI spec, a Smithy model, a Lambda function, an API Gateway stage, or a remote MCP server. Then Gateway reads it, extracts each operation, and generates an MCP-compatible tool for each one. Descriptions, parameter schemas, return types, all automatic. Your agent sees tools. It doesn't need to know whether a given tool hits a REST endpoint, invokes a Lambda, or calls another MCP server behind the scenes.

Let's say you have a customer API with an OpenAPI spec in Amazon S3. Here's how it looks like:

import boto3
client = boto3.client('bedrock-agentcore-control')
# Create a gateway
gateway = client.create_gateway(
    name='enterprise-tools',
    roleArn='arn:aws:iam::123456789012:role/GatewayExecutionRole',
    protocolType='MCP',
    authorizerType='AWS_IAM'
)
# Register a REST API as a target — Gateway reads the spec and creates tools
client.create_gateway_target(
    gatewayIdentifier=gateway['gatewayId'],
    name='customer-api',
    targetConfiguration={
        'mcp': {
            'openApiSchema': {
                's3': {
                    'uri': 's3://my-bucket/customer-api-spec.json'
                }
            }
        }
    }
)
Two things are happening here. The first call creates the gateway—think of it as standing up the front door. The roleArn is the IAM role Gateway will use when it calls your downstream APIs on the agent's behalf. protocolType is MCP (the only option today), and authorizerType controls who's allowed to connect—AWS_IAM means any caller with the right IAM permissions can reach the gateway without setting up a separate OAuth provider.

The second call registers your API as a target. You're telling Gateway: here's an OpenAPI spec in S3 — go read it and turn every endpoint into an MCP tool. Gateway does exactly that. It parses the spec, figures out what each endpoint does, and creates a tool for each one—complete with descriptions, parameter schemas, and return types pulled straight from the spec.

If that OpenAPI spec defines endpoints for GET /customers/{id},POST /customers/{id}/orders, and GET /customers/{id}/balance, Gateway creates three MCP tools from them. Your agent connects to the gateway URI, discovers those tools, and calls them the same way it calls tools from the MCP servers. No wrapper code, no MCP server to deploy and maintain.

Where this really pays off is composition. When you register your customer API, a Lambda function runs fraud checks, and a third-party weather service—all as targets on the same gateway. Your agent sees one unified tool catalog. Check balance hits your internal REST API, run fraud check invokes a Lambda, get weather calls an external service. The agent doesn't know or care about the difference. They're all just tools on the same MCP connection.

The GitHub samples repository has tutorials that walk through creating a gateway, registering targets, and connecting an agent: https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/01-tutorials/02-AgentCore-gateway

Semantic search

With five or ten tools, you can load all the tool definitions into the agent's prompt and let the model pick. That's what you did in Chapter 5, Agent Communication, and it works fine at that scale. However, at 200 tools, you have a problem. The definitions alone consume a significant chunk of the context window, and models get noticeably worse at selecting the right tool as the list grows.

Gateway handles this with semantic search. When you register targets, Gateway creates vector embeddings of each tool's name, description, and parameters, and indexes them. The index updates on its own as you add or remove targets, and we don't manage it.

The search itself is exposed as an MCP tool called x_amz_bedrock_agentcore_search. So, the flow looks like this: your agent gets a user request, let's say, which scenes in Episode 4 still have unfinished VFX shots before the Friday delivery?—and calls the search tool with a query like, VFX shot completion status by episode. Gateway compares that against the embeddings and returns the top matches, maybe production_tracker_api_get_vfx_status. The agent picks from that short list and calls the tool directly. It never loads the other 199 tool definitions into the prompt.

The practical benefit is fewer tokens per request and better tool selection. But search quality depends on your API documentation. If your OpenAPI spec has well-named operations with clear descriptions, the embeddings are useful and matches are accurate.

Authentication: Inbound and outbound

Any production deployment needs to answer two questions: who's allowed to call the gateway, and how does the gateway prove its identity to the APIs it's calling on your behalf?

For inbound auth, controlling who can reach the gateway, you pick between IAM and JWT. If your agent already runs on AWS with an IAM role (on Runtime, Lambda, or ECS), IAM is the simpler path. Grant the role permission to invoke the gateway and you're done. For scenarios where end-user identity needs to flow through, Gateway supports JWT-based auth through Cognito, Okta, or any OAuth 2.0 provider.

Outbound auth is configured per target. Your internal customer API might use an OAuth token, a third-party weather service might use an API key, and a public dataset might need no auth at all. Gateway stores those credentials in Secrets Manager, handles token refresh, and caches tokens so it doesn't hammer downstream identity providers with repeated requests.

Gateway keeps inbound and outbound tokens completely separate. The token proving your agent can use Gateway and the token proving Gateway can call the downstream API are different credentials with different scopes. A downstream API can't take the inbound token and reuse it to impersonate your agent elsewhere. If you're in a regulated industry, your security team will appreciate this; it's one of the first things auditors check. Gateway handles the mechanics of authenticating to downstream APIs. But there is a bigger question it does not answer on its own: Who is the user behind the request, and what are they allowed to do? That is the job of AgentCore Identity.

AgentCore Identity

Every agent in production faces a two-sided authentication problem. On one side, callers need to prove who they are before the agent will talk to them, whether that caller is a user, another agent, or an automated workflow. On the other side, when the agent needs to call an external service, like a CRM, a calendar API, or a code repository, it needs credentials for that service. Without the first, anyone can hit your agent endpoint. Without the second, you end up embedding secrets in environment variables or hardcoding API keys in your agent code, which is how breaches happen.

AgentCore Identity handles both sides. For inbound authentication, Identity supports JWT-based authorization. Your identity provider (Amazon Cognito, Okta, Microsoft Entra ID, or any standard OAuth 2.0/OIDC provider) issues the token, and Identity validates it before the request reaches your agent. For outbound authentication, Identity manages the credentials your agent needs to access external services, storing OAuth 2.0 tokens and API keys in a secure token vault rather than in your agent's code or configuration. Credentials are encrypted with AWS KMS, bound to specific agent-user combinations, and every access is logged for audit.

The outbound side is where most of the complexity lives:

First, your agent needs to access a user's personal data: their Google Calendar, their Salesforce records, their GitHub repositories. This requires the user's explicit consent through an OAuth 2.0 authorization code grant (the flow where the user clicks Allow in a browser to authorize access). The user authorizes the agent once. Identity stores the resulting tokens securely, handles token refresh when they expire, and your agent can access that user's data on subsequent requests without asking for consent again.
Second, your agent needs to access system-level resources like an internal knowledge base, a data warehouse, or a monitoring API, where no specific user is involved. This uses the OAuth 2.0 client credentials grant (machine-to-machine authentication, where the agent authenticates as itself). Many agents need both patterns simultaneously: user-delegated access for personal data and machine-to-machine access for shared resources.
In your agent code, this shows up as SDK annotations. You decorate a function with @requires_access_token or @requires_api_key, and the SDK handles credential retrieval, injection, and refresh automatically. Identity comes with built-in credential providers for services like Google, GitHub, Slack, Salesforce, and Atlassian, among others, with authorization endpoints and provider-specific parameters pre-configured. For anything else, you can set up custom OAuth 2.0 credential providers that work with any standards-compliant service.

When Identity validates an inbound token and manages outbound credentials, it maintains the connection between who is calling and what the agent is doing on their behalf. This context —the caller's identity paired with the agent's identity—is what enables the rest of the AgentCore platform to enforce per-user, per-action governance.

If you are deploying on Lambda or ECS instead of AgentCore, you build credential management yourself: storing tokens in Secrets Manager, implementing OAuth flows in your application code, handling token refresh, and managing the overall security. It works, but it is undifferentiated work that Identity handles as a managed service.

For a hands-on walkthrough of setting up AgentCore Identity, see the tutorial in the companion repository: https://github.com/awslabs/agentcore-samples/tree/main/01-tutorials/03-AgentCore-identity

Enterprise integration and industry use cases

Once you deploy an agent, it needs to talk to other systems like databases, internal APIs, third-party services, and event streams. If you are using AgentCore Gateway, it handles a lot of this: point it at an OpenAPI spec and you get tools with auth and error handling built in. The patterns discussed in the following sections apply when you're on Lambda or ECS, or when you need behavior that Gateway doesn't cover.

Databases are often the first integration that breaks at scale. An agent serving forty concurrent users, each triggering two or three queries, will exhaust a typical Amazon Aurora (Amazon's managed relational database) connection pool within minutes. Amazon RDS Proxy, which sits between your agent and the database to manage connection pooling, fixes this by multiplexing hundreds of agent requests over a smaller set of actual database connections. The agent code doesn't change, but the infrastructure absorbs the concurrency. We would recommend that you keep analytical queries (reports, aggregations) off your transactional database entirely and replicate to Redshift or Athena instead. Conversation state maps naturally to DynamoDB, which we covered in Chapter 3, Agent Memory. Credentials belong in Secrets Manager with automatic rotation, not in environment variables. You can scope the IAM policy to the exact secret ARN the agent needs, and keep database traffic inside a private subnet.

External APIs fail in ways your agent needs to handle gracefully. Internal services go down during deployments. Third-party providers enforce rate limits and return 429s. Some endpoints just stop responding with no error at all. Set a timeout on every call, retry with exponential backoff, and return a structured error the agent can reason about. I couldn't complete the underwriting check; proceeding with a preliminary assessment is better than a 500 error code. Circuit breakers prevent your agent from burning through timeouts when a service is clearly down. For rate-limited APIs, respect Retry‑After headers and cache responses when the data doesn't change between calls.

Event-driven integration decouples your agent from the systems that feed it. A document lands in Amazon S3, an Amazon EventBridge rule (configured on the bucket) picks up the object-created event and routes it to the agent. The upstream system doesn't know about the agent. The agent doesn't know about the notification system that alerts users when processing finishes. When volume spikes, put SQS between EventBridge and the agent to absorb bursts. Messages that fail three times route to a dead letter queue. A CloudWatch alarm fires, someone investigates, and once the issue is fixed, they replay the messages. For scheduled work like weekly reports or batch processing, EventBridge Scheduler triggers an ECS RunTask instead of a Service. RunTask spins up, runs the job, and terminates. Ten minutes of Fargate cost instead of 24 hours.

Beyond individual integrations, you'll also need to decide how your agent responds to users and upstream systems. Most production agents handle both synchronous and asynchronous work. The chat interface goes synchronous with streaming so users see progress. Document pipelines and batch jobs go async: the user submits a request, gets a task ID back immediately, and either polls for results or gets a callback when processing finishes. Status updates pushed through a WebSocket keep dashboards current without holding HTTP connections open.

A bank's fraud detection system was catching suspicious crypto transactions but flagging legitimate customers so often that Why can't I buy Bitcoin? became a daily support ticket. The fraud team was drowning in false positives while actual fraudsters slipped through.

The fraud model itself was solid, a SageMaker endpoint trained on transaction patterns. The problem was context. The model saw each transaction in isolation. It didn't know that a customer had been making similar purchases for months. Figure 6.7 demonstrates the transaction flow:

The agent doesn't use hardcoded conditional logic, such as if risk_score > 0.8 then call Lambda. It reads the tool descriptions and orchestrates them based on the situation.

Deployment fit: AWS Lambda. Each transaction is independent, no multi-turn conversation, no persistent state between invocations. Lambda is a natural fit: the agent processes one transaction, returns a decision, and terminates. During quiet periods it scales to zero. During market volatility it scales to hundreds of concurrent invocations.

Scheduling surgery requires coordinating a surgeon, an anesthesiologist, possibly a specialist, an available Operating Room (OR), specific equipment that might be in use elsewhere, and a time the patient can actually show up. A large hospital system was doing this manually. Coordinators spent hours on the phone, checking calendars, leaving voicemails. A scheduling conversation might run five messages deep before a procedure gets confirmed, so this is a multi-turn workload. Manufacturing: Predictive maintenance on the factory floor

A factory had expensive CNC machines with bearings that failed without warning. One day the machine runs fine, the next it's down for three days waiting for parts. Each failure cost roughly $50,000 in lost production. Scheduled maintenance (replace bearings every six months regardless) was wasteful, and bearings still failed between replacements. Monitoring vibration sensors manually produced too much data and too many false alarms. Figure 6.9 shows how an agent-based flow for predictive maintenance works:
