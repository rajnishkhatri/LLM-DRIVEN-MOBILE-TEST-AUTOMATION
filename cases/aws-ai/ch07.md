Agent evaluation

By mid-2024, AI agents had become one of the most prominent topics in technology, taking on tasks such as ordering groceries, booking flights, and scheduling appointments. Soon after, vertical AI agents emerged such as clinical documentation agents in healthcare, automated legal research assistants, and AI-powered customer support systems and, in some cases, positioned as alternatives to traditional SaaS applications. However, as interest in agents continues to grow, so does the risk of deploying them before they are ready.

When AI agents are not evaluated thoroughly, they can introduce serious problems, including inaccurate outputs, hidden biases, poor adaptability, and security weaknesses. For example, a customer support agent that confidently provides incorrect refund policies, or a healthcare scheduling agent that books appointments with the wrong specialist based on misinterpreted symptoms. These issues do more than reduce performance; they can confuse users, erode trust, and raise concerns about fairness and reliability.

Real-world incidents have shown how costly this can become. In one widely reported case, a company's customer service chatbot provided incorrect policy information to a user, who relied on it when making a purchase. When the user later challenged the outcome, the organization was still held accountable for the chatbot's response. Cases like this show that when agents are not evaluated carefully for accuracy, consistency, and policy compliance, the result is not only a poor user experience but also reputational and legal risk.

Why agent evaluation matters?

Developing an agent means preparing it for the unpredictable situations it may encounter in the real world. With LLM evaluation, the goal is to ensure the agent can handle both routine tasks and unexpected edge cases without producing incorrect or unfair outcomes. For example, if an agent evaluates loan applications, it must apply decisions consistently and fairly across applicants. If it acts as a virtual assistant, it should respond effectively not only to common requests but also to unusual or unanticipated questions. Thorough evaluation helps identify and address these issues early, before they affect real users or lead to harmful consequences.

Evaluation is essential for both compliance and trust. In fields such as healthcare and finance, AI systems must meet strict requirements around privacy, safety, and fairness. Demonstrating that an agent has been tested against these standards gives regulators, stakeholders, and users confidence that it has been carefully validated.

Ongoing evaluation is equally important because real-world conditions change over time. Even if an agent performs well initially, shifts in user behavior, data, or business needs can introduce new weaknesses. Regular testing or evaluation helps identify performance drops, missed scenarios, and emerging biases early, allowing the agent to remain reliable and effective.

Relationship between agent observability and evaluation

Agent evaluation depends on visibility into what happened during an agent run, not just the final response. This is where instrumentation comes in: it captures the telemetry needed to inspect agent behavior, analyze execution traces, and evaluate whether the agent made the right decisions. We are going to deep dive into observability in the next section and see how to set it up. In this section, we will cover some high-level concepts which are important for agentic evaluation.

Figure 7.3: Agent with instrumentation library interacting with Instrumentation Agent

The preceding figure shows the AI agent application where telemetry is generated, the instrumentation agent that collects and exports it, and the observability backend where it is stored, visualized, and evaluated.

The instrumentation library and instrumentation agent work together, but they play different roles.

An instrumentation library is the code-level layer that defines what telemetry should be captured from your AI agent. It records information such as traces, spans, model calls, tool calls, inputs, outputs, latency, and intermediate execution steps. For example, libraries such as OpenTelemetry or OpenInference provide standard APIs and naming conventions so that agent behavior can be captured consistently across different tools and platforms.
An instrumentation agent is the runtime layer that helps collect and export that telemetry automatically. Instead of requiring developers to manually add tracing code throughout the application, an instrumentation agent can observe the running application, capture telemetry, process it, and send it to a backend system for storage, monitoring, or evaluation. For example, ADOT(AWS Distro for OpenTelemetry), AWS's distribution of the open-source OpenTelemetry project, can auto-instrument supported applications and export traces to observability backends.
Once captured, this telemetry is organized into a hierarchy of sessions, traces, and spans:

A session sits at the highest level. It groups related interactions from a user or workflow, such as a multi-turn conversation with a travel-booking agent. Within a session, the agent may perform several separate executions.
Each of those executions within a session is captured as a trace. A trace gives an end-to-end view of one agent run, including the user request, model calls, tool calls, intermediate steps, latency, errors, and final response.
Inside each trace are spans, which represent individual operations. For example, one span may capture a model call, another span may capture a retrieval step, and another may capture a tool call. A tool call is therefore a specific type of span that records when the agent invokes an external function, API, database, search system, or other capability. This makes it possible to evaluate not only what the agent answered, but also how it arrived at that answer.
This is where evaluation connects to observability. Once instrumentation captures sessions, traces, spans, and tool calls, evaluation systems can analyze them.

For example, an evaluator can check whether the agent selected the right tool, passed the right parameters, handled the tool output correctly, and produced an accurate final response. An LLM-as-a-judge can then review the captured trace or final output against a rubric, even when no ground-truth answer is available. It can score qualities such as correctness, reasoning quality, instruction adherence, tool-use accuracy, and task completion.

Evaluation metrics for evaluators

Evaluators are the core components that assess your agent's performance across different dimensions. They analyze agent traces and provide quantitative scores based on specific criteria such as helpfulness, accuracy, or custom business metrics.

Generally, there are two types of evaluation metrics, built-in metrics and custom metrics when evaluating an agentic system.

Built-in evaluators are ready-to-use evaluation options provided by evaluation platform like AgentCore Evaluations that use large language models (LLMs) as judges to assess agent performance. They include predefined settings such as prompt templates, evaluator models, and scoring criteria. Examples include GoalSuccessRate, which measures whether the agent achieved the user's objective across a session, Correctness, which checks factual accuracy of individual responses, and Helpfulness, which scores how useful the response is to the user.

These evaluators are useful for common evaluation scenarios where you want consistent and reliable results without creating your own evaluation logic.

Built-in evaluators can run on agent traces without a labeled dataset for general quality checks such as helpfulness and response relevance. However, when you want to test against a known expected answer, expected behavior, or expected tool path, you provide ground truth data.

Custom evaluators are especially valuable when evaluating domain-specific agents or when your organization has specialized quality standards. There are two types of custom evaluators:

LLM-as-a-judge evaluators let you define your own evaluator model, instructions, criteria, and scoring schema. This is useful when you want the evaluation to reflect your specific task, domain, or quality expectations.
Code-based evaluators let you use a function to evaluate agent behavior programmatically. This approach is useful for deterministic checks, such as validating exact values, matching patterns with regular expressions, calling external APIs, calculating custom metrics, or applying business-specific rules. We will cover both examples in the next section.
For example, a healthcare agent may need criteria focused on clinical accuracy and safety, while a finance agent may need checks for compliance, numerical correctness, and policy alignment.

Understating types of agent evaluation

There are commonly two types of Agent evaluation, Online evaluation and On-demand evaluation.

Online evaluation continuously monitors deployed agents using live production traffic. It allows teams to sample a percentage of sessions or apply filters to choose which interactions to evaluate. Teams can use built-in or custom evaluators, view aggregated scores in dashboards, track quality trends, and investigate low-scoring sessions.

On-demand evaluation lets teams evaluate specific traces or spans at any time. Instead of continuously monitoring production traffic, you select the exact span IDs or trace IDs you want to analyze. This is useful for testing a custom evaluator, investigating a customer issue, validating a fix, reviewing historical interactions, or performing build-time testing during development.

In short, online evaluation is best for continuous production monitoring, while on-demand evaluation is best for targeted analysis of selected interactions.

Note: Online evaluation and on-demand evaluation both support built-in and custom evaluators. Online evaluation applies them continuously to sampled or filtered production sessions, while on-demand evaluation applies them to specific traces or spans selected for targeted analysis.

Agentcore evaluation levels

AgentCore Evaluations operate in different levels of the agent interaction. You can analyze the back and forward conversation as a whole using the session information. You can also evaluate the agent's response to a user's question in an individual turn of the conversation using the trace information. Or you can evaluate information inside of a turn, which includes the tool calling and parameter selection, using the span data.

Figure 7.7: Evaluation levels
Figure 7.7: Evaluation levels

The preceding diagram shows that agent evaluation metrics can be applied at three different levels of execution detail: the session level, trace level, and span or tool level.

At the session level, the metric looks at the overall outcome across a broader interaction or workflow. In Figure 7.7, the built-in metric goal success rate is an example of a session-level metric because it measures whether the agent ultimately achieved the user's objective. This level can also include custom metrics that are designed for a specific business workflow or use case.
At the trace level, the metric evaluates a single end-to-end agent run. These metrics focus on the quality of the agent's response and behavior throughout one execution. Examples shown here include correctness, faithfulness, helpfulness, response relevance, conciseness, coherence, instruction following, refusal and harmfulness.. This level is useful when you want to judge how well one complete invocation performed from start to finish. The preceding diagram also shows that you can define custom metrics at this level.
At the span or tool level, the metric examines an individual step inside the trace, especially a tool-related step. Examples include tool selection accuracy, which checks whether the agent chose the right tool, and parameter selection accuracy, which checks whether it passed the right inputs to that tool. This is the most granular level and helps diagnose where an agent went wrong inside a workflow. As with the other levels, custom metrics can also be added here.

Step 7: Run evaluations (3 passes)

After the agent has been invoked and the traces have been collected, the next step is to evaluate its performance. This walkthrough uses three evaluation passes because no single metric can fully capture agent behavior. Some metrics assess whether the overall conversation was successful, while others examine the quality of individual responses or check whether the agent followed application-specific rules. Using multiple passes provides a more complete and reliable view of performance.

Pass A—GoalSuccessRate (session level)

The first pass looks at the entire conversation as a whole and asks one question: "Did the user get what they needed from this session?" It reads all 4 turns together and gives a single score. Think of it as the overall customer satisfaction score for the whole chat.

This first pass uses GoalSuccessRate, a built-in session-level evaluator. Session-level evaluators examine the entire conversation as a whole rather than scoring each turn separately. Here, GoalSuccessRate reads all four turns together and asks a simple question: Did the conversation achieve its overall goal?

This makes GoalSuccessRate useful for measuring end-to-end success from the user's perspective. Rather than focusing on one reply in isolation, it evaluates whether the full interaction was successful overall. In practice, this makes it similar to an overall task-success or customer-satisfaction indicator for the session.

Because it operates at the session level, this pass produces one score for the entire conversation.

eval_client.run(evaluators=["Builtin.GoalSuccessRate"])
Pass B—Correctness + Helpfulness (trace level)

This second pass scores each individual turn for factual accuracy and usefulness. It uses the built-in Correctness and Helpfulness evaluators. These are trace-level evaluators, meaning they score each turn individually.

Correctness measures whether the response is factually accurate and appropriate for the request. Helpfulness measures whether the response is useful and provides meaningful assistance. Together, these metrics help answer the question: Was each individual response accurate and useful?

This pass is important because an agent may appear successful at the conversation level while still performing unevenly on specific turns. Trace-level evaluation helps identify those strengths and weaknesses more precisely.

eval_client.run(evaluators=["Builtin.Correctness", "Builtin.Helpfulness"])
Pass C—Custom evaluator (trace level)

The third pass runs the custom evaluator defined earlier. Like Pass B, this is also a trace-level evaluator, but instead of using only general-purpose quality measures, it applies domain-specific criteria.

It runs the LLM-as-judge on each turn which is using your LLM-as-judge defined in travel_quality_metric.json. The judge model (Claude Haiku) reads each response and applies your specific rules including the critical rule that any out-of-scope answer scores 0.0.

With the evaluation concepts in place, the next step is to understand observability, because the traces and telemetry collected during agent execution provide the foundation for measuring how well an agent actually performs.

Observability: Seeing what your agents do

In Chapter 6, Production Deployment and Enterprise Integration, we have deployed our agents – Lambda for event-driven tasks, ECS for always-on workloads, AgentCore for AWS managed stack. We ran the deployment scripts and the agent was up and running and responding to the invocations.

But "up and running" is not the same as "running well." Latency might start climbing over time and invocations might start failing intermittently. Token costs might spike without any obvious change in traffic. A lot can go wrong in production, as with any software system, and most of it won't announce itself with a clean error message.

Let's consider a team at a fintech company that deployed a loan underwriting agent. Initially the agent worked well for three weeks. Then one morning, loan application approval times jumped from eight seconds to twenty. No errors in the logs. No failed requests. The agent was still returning correct decisions, but it was slow. It took a day of digging to figure out what really happened. The agent had started making redundant tool calls: checking the same credit bureau three times per application because the model was not recognizing that it already had the information it needed. The model had not broken. The tools had not broken. The interaction pattern between them had shifted, and nobody could see it because they were only logging inputs and outputs.

This is the core challenge with agent observability. Traditional application monitoring watches HTTP status codes, response times, and error rates. That is necessary but nowhere near sufficient for agents. An agent that returns a 200 OK might have hallucinated an answer, called the wrong tool, ignored relevant context from memory, or consumed twelve dollars in model tokens on a request that should have cost thirty cents. You cannot see any of that from a health check endpoint.

Agent observability means understanding the reasoning process, not just the result. Which tools did the agent call, and in what order? What did the model see in its context window? How many tokens went in, how many came out, and what did that cost? When the agent made a decision, what information was it working with? If you cannot answer these questions for any given request, you don't have complete visibility into the system.

What you need to capture

Before we look at specific tools, let's understand what observability means for an agentic system. There are four layers to agent observability, and each one gives you a different level of insight into what your agent is doing:

Layer 1: Infrastructure metrics

This covers CPU, memory, network, and container health. Amazon CloudWatch gives you this out of the box. It is useful for knowing whether your compute is healthy, but it says nothing about whether your agent is doing the right thing.

Layer 2: Request-level telemetry

This includes latency per request, error rates, and throughput. This is standard API monitoring. You will know that something is slow or broken, but not why.

Layer 3: Agent execution traces

A trace captures the full lifecycle of a single agent invocation: the user's input, the system prompt, every model call with its input tokens and output tokens, every tool invocation with parameters and results, and the final response. When that loan underwriting agent started making triple credit checks, a trace would have shown it immediately. Three identical tool calls in a single invocation, each with the same parameters and the same results.

Layer 4: Behavioral analytics

This is about patterns across many traces. This layer allows you answering questions such as: Are tool call counts drifting upward over time? Is the agent using certain tools less than expected? Are there prompt patterns that consistently lead to poor outcomes? This layer is how you catch slow degradations that never show up as errors in any single request.

Most of this section focuses on Layer 3, execution traces, because this is the layer that is unique to agentic systems. Infrastructure metrics and request-level telemetry work the same way for agents as they do for any other application. But tracing the reasoning, tool calls, and decision steps inside an agent invocation requires agent-specific instrumentation, and this is where the observability tools we cover next provide the most value.

Before we go further, it is worth reminding a few terms we covered in previous section:

A session represents a user's conversation with an agent. When a user opens a chat and asks multiple questions, that entire back-and-forth is one session, connected by a session ID.

Each time the user asks a question within that session, everything the agent does to answer it is one trace. If a user asks three questions in one session, you get three traces.

Within each trace, every individual operation the agent performs is a span. A model call is a span. A tool invocation is a span. A memory retrieval is a span. Each span has its own timing data, status, and metadata. When something goes wrong, you look at the spans within a trace to find which specific operation failed or took too long.

Here's how that hierarchy looks like for a session with two user questions:

Session (conversation)
└── Trace 1 (first question)
│   ├── Span: LLM call (reasoning)
│   ├── Span: Tool call (get_customer_data)
│   ├── Span: Memory retrieve
│   └── Span: LLM call (final response)
└── Trace 2 (second question)
    ├── Span: LLM call (reasoning)
    └── Span: LLM call (final response)
With that vocabulary in place, let us look at the plumbing that makes all of this work.

The OpenTelemetry Foundation

All three observability tools we will cover - Langfuse, LangSmith, and AgentCore Observability, either produce or consume OpenTelemetry (OTel) data. OTel is an open standard for traces, metrics, and logs. It is the same standard your backend team already uses for microservice tracing, not something specific to AI. The reason it is important is portability. If you instrument your agent with OTel, you can send that data to any backend that speaks OTel. You could start with Langfuse and later move to Datadog or add AgentCore Observability without changing your instrumentation code.

Here is how the pieces fit together. The Strands agent generates trace data as it runs and exports it to an OTel-compatible endpoint. That endpoint could be a dedicated OTel Collector that routes traces to multiple backends, or it could be the backend itself if it accepts OTel data directly. Jaeger(an open-source distributed tracing system), Langfuse, and CloudWatch all have OTel-compatible endpoints, so in many cases you can point your agent straight at them without a separate collector in between. From the agent's perspective, it is just sending OTel data to an endpoint. What sits behind that endpoint is your choice.

Strands has native OTel support. When you enable tracing, every model call and tool invocation automatically emits OTel spans, so you do not need to write instrumentation code for each tool individually.

Seeing traces locally with Jaeger

The easiest way to understand what traces look like is to run them locally. Jaeger is an open-source distributed tracing system originally built by Uber and now a graduated project under the Cloud Native Computing Foundation (CNCF). It collects trace data, stores it, and provides a web UI where you can search and visualize traces. For local development, Jaeger runs as a single Docker container that acts as both the collector and the UI.

Start Jaeger locally:

docker run -d --name jaeger \
  -e COLLECTOR_OTLP_ENABLED=true \
  -p 16686:16686 \
  -p 4317:4317 \
  -p 4318:4318 \
  jaegertracing/all-in-one:latest
This starts Jaeger with an OTel-compatible receiver on ports 4317 (gRPC) and 4318 (HTTP), and the web UI on port 16686. Now point your Strands agent at it:

Langfuse

Langfuse is an open-source LLM observability platform. You can run it as a managed cloud service or self-host it on your own infrastructure.

The reason Langfuse works well for agents is that it shows traces as nested hierarchies rather than flat lists of API calls. You can see the full sequence: the agent received a prompt, called the model, the model decided to use a tool, the tool returned a result, the model was called again with that result, and the agent produced a final response. Each step includes timing, token counts, and cost estimates.

Setting up Langfuse with Strands

Langfuse has a native SDK integration with Strands. You set your Langfuse credentials as environment variables, initialize the client, and traces flow through automatically:

os.environ["LANGFUSE_SECRET_KEY"] = "sk-lf-..."
os.environ["LANGFUSE_BASE_URL"] = "https://us.cloud.langfuse.com"

model = BedrockModel(model_id="us.anthropic.claude-sonnet-4-20250514-v1:0")
agent = Agent(model=model, system_prompt="You are a document analyst.")
response = agent("Summarize the key risks in this contract.")

# Ensure traces are flushed before the process exits
langfuse.flush()
After running this, open the Langfuse dashboard and you will see the trace. Clicking into it and you get the system prompt, the user message, each model call with token counts, any tool invocations, latency per step, and an estimated cost.

Self-hosting Langfuse on AWS

If your trace data needs to stay in your own account, you can self-host Langfuse. The setup is not complicated. You need three things running: a Langfuse web container that serves the dashboard, a worker container that handles background processing like cost calculations, and a PostgreSQL database for storage. On AWS, the natural fit is ECS Fargate for the containers and RDS for the database. Put an Amazon Application Load Balancer (ALB) in front, point your agents at the ALB endpoint, and you have a self-hosted observability stack.

AWS has a CDK sample (https://github.com/aws-samples/deploy-langfuse-on-ecs-with-fargate) that automates this setup, and there are Terraform modules (https://langfuse.com/self-hosting/deployment/aws) if that is your preferred tooling. The self-hosted version has the same functionality as the cloud version. The only difference is that your trace data, which includes every prompt, every model response, and every tool call parameter, stays inside your VPC.

What Langfuse shows you that logs don't

Individual traces are useful for debugging a single request. The real payoff comes when you start looking across many traces and asking questions that logs cannot answer.

Suppose your agent's average cost per invocation has been around $0.15. One morning you check the Langfuse dashboard and see a cluster of traces costing $2.40 each. You click into one and find that the agent entered a reasoning loop, calling the model six times instead of the usual two because a tool returned an ambiguous result that the model kept trying to interpret differently. Langfuse calculated the cost automatically from the token counts and model pricing. Without that, you would not have noticed until the monthly bill arrived.

Or consider a latency investigation. A request took 12 seconds. Your API monitoring tells you it was slow, but not why. In Langfuse, you open the trace and see the breakdown per span: the first model call took 3 seconds, the database tool took 8 seconds, and the second model call took 1 second. The bottleneck was the tool, not the model. That changes how you fix it.

Langfuse also tracks prompt versions. When you change a system prompt, you can tag traces by version and compare how the agent behaves under each one. You can try answering questions such as: Did the new prompt reduce the number of tool calls per request? Did it change how often the agent asks clarifying questions? This lets you iterate on prompts with data rather than intuition.

Finally, you can attach scores to traces, either manually during human review or programmatically through the Langfuse API. Langfuse provides the data layer that those evaluation pipelines read from.

It has an OTel-compatible ingestion endpoint, which means any agent that emits OTel traces can send data to LangSmith. That includes Strands agents.

What LangSmith and Langfuse Offer

The traces we have been looking at so far tell you what happened on a single request. LangSmith and Langfuse both go further than that, though they each lean into different strengths.

LangSmith has a playground where you can take any traced interaction, modify the prompt or model parameters, and re-run it without redeploying your agent. When someone reports a bad answer, you pull up the trace, see what the model received, tweak the prompt in the playground, and verify the fix right there. LangSmith also lets you collect traces into datasets that become regression test suites, and it has annotation queues where human reviewers can score agent outputs on dimensions like accuracy or safety. If you are running a multi-agent system where a Strands agent calls a LangGraph sub-agent within the same process, LangSmith can show the full trace across both frameworks, since they share the same OTel trace context.

Langfuse is open-source and self-hostable, which is its main differentiator. If your compliance requirements say trace data cannot leave your AWS account, Langfuse is the simpler path. You pay for the infrastructure, not the software. It also has a playground for prompt iteration, cost tracking, and prompt versioning features.

The two are not mutually exclusive. Some teams use Langfuse as the production observability layer inside their VPC and LangSmith for development iteration and human review. Both accept OTel traces, both show nested spans with token counts and costs, and both support programmatic scoring, so you are not locked into either one.

Both Langfuse and LangSmith are tools you add to your agent. But if you deployed on AgentCore Runtime in Chapter 6, there is a third option that requires no setup at all.

AgentCore Observability

If you deployed your agent on AgentCore Runtime, some observability is already running without you doing anything. AgentCore automatically tracks session-level metrics like how many sessions are active, how many errors occurred, and whether any requests were throttled. This data shows up in CloudWatch on its own.

To go deeper and see the full trace of every model call and tool invocation, you add the AWS Distro for OpenTelemetry (ADOT) SDK to your agent's dependencies and run the agent with the opentelemetry‑instrument wrapper. For frameworks like Strands that already have native OTel support, this is a small addition.

This is not limited to Strands agents. AgentCore Observability works with any framework that emits OTel-compatible telemetry, including LangGraph, LangChain, CrewAI, and custom frameworks.

What gets captured

The scope of what AgentCore traces is broader than what you get from Langfuse or LangSmith alone, because it sits inside the platform rather than outside it.

To make this concrete, imagine your agent receives a request: "Look up account ACC-001 and tell me what discount they qualify for." Here is what the trace would show. First, a model call span where the agent reads the prompt and decides it needs to call the lookup_account tool. Then a tool call span for lookup_account, showing the input parameter (ACC‑001), the result (Acme Corp, Enterprise tier, $142,500 balance), and how long the call took. If you have a Cedar policy that restricts account access by department, a policy evaluation span appears next, showing that the rule was checked and the action was permitted. Then another model call span where the agent decides to call calculate_discount with the tier and amount. Then the tool span for that calculation. And finally, a model call span where the agent composes the response to the user. Each of these is a separate span in the trace, with its own timing and metadata.

Neither Langfuse nor LangSmith can capture the policy evaluation step, because they do not have a policy engine. That is unique to AgentCore.

Memory operations are part of the picture as well. You can see what context was retrieved from AgentCore Memory, what was written back, and how long those operations took. AgentCore Observability covers all AgentCore services: Gateway, Memory, Identity, and Policy. So instead of monitoring just the compute layer, you get a connected view across the entire stack.

All of this data lands in CloudWatch under the GenAI Observability section. The Bedrock AgentCore dashboard (shown in Figure 7.12) gives you a fleet-level view of all your agents, and you can drill down into individual sessions and traces from there. When you open a trace, you see the span timeline showing every operation the agent performed, with timing, status, and input/output data for each span.

Exporting to external platforms

Since AgentCore emits OTel-compatible traces, you can send them to any platform that accepts OTel data. Partner integrations exist for Datadog, Dynatrace, Elastic, Langfuse, LangSmith, Arize Phoenix, Braintrust, and groundcover. The way this works is you deploy an OTel collector that receives traces from AgentCore and forwards them to your chosen backend. If you have not worked with an OTel collector before, think of it as a routing layer that sits between your agent and your monitoring tools. Here is what a collector configuration looks like when sending traces to both Datadog and a self-hosted Langfuse instance. To route traces to multiple destinations, you deploy an OTel Collector with a configuration file that defines where to receive traces and where to export them. The following YAML configuration receives OTel traces on the standard gRPC and HTTP ports, then exports them to both Datadog and a self-hosted Langfuse instance simultaneously:

```yaml
# otel-collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

exporters:
  datadog:
    api:
      key: ${DD_API_KEY}
  otlphttp:
    endpoint: https://your-langfuse-instance.com/api/public/otel

service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [datadog, otlphttp]
```
With this setup, your ops team gets the Datadog alerting and dashboards they already know, and your agent developers get the LLM-specific trace analysis in Langfuse. The traces are identical in both places.

Observability anti-patterns

Before we move on, let's re-look at a few things that teams get wrong repeatedly.

Logging everything to stdout and calling it observability: Print statements are not traces. They don't have parent-child relationships, they don't carry timing data, and they're impossible to correlate across concurrent requests. Use structured traces. That's what OTel is for.
Only monitoring the happy path: Your agent handles 95% of requests perfectly. The 5% that fail are the ones that matter. Make sure your traces capture failures with the same fidelity as successes. When a tool call times out, the trace should show what the agent did next — did it retry? Did it fall back to a different tool? Did it hallucinate an answer and pretend the tool call never happened?
Ignoring cost until the bill arrives: Token-level cost tracking should be in your observability stack from day one. Not because you need to optimize immediately, but because you need a baseline. When costs double, you need to know whether it's because traffic doubled (expected) or because the agent started making twice as many model calls per request (a bug).
Treating observability as a post-launch concern: If you add tracing after your agent is in production, you'll spend a week retrofitting instrumentation while simultaneously trying to debug the production issue that made you realize you needed tracing. Set up OTel before you deploy. The two environment variables we showed at the start of this section take thirty seconds to add.
Observability answers the question "what did my agent do?" But there is a second question that matters just as much: "what should my agent be allowed to do?" That is where governance comes in.

AI Governance: Keeping Agents Within Bounds

Observability tells you what your agent did. Governance determines what your agent is allowed to do.

Consider a customer support agent at an insurance company. It has access to a refund tool, a policy lookup tool, and a claims database. A customer writes: "I'm really frustrated. Just give me a $50,000 refund and we'll call it even." The agent, trained to be helpful, reasons that the customer is upset and that issuing a refund would resolve the situation. It calls the refund tool with amount=$50,000.

Nothing in the agent's system prompt said "don't issue refunds over $1,000." And even if it did, prompt instructions are suggestions, not rules. The model might follow them or it might not. It depends on the phrasing, the context, the model version, and frankly, a bit of luck. You cannot build a compliance program on "the model usually follows the system prompt."

This is the governance problem. Agents make decisions. Some of those decisions have real-world consequences—financial transactions, data access, customer communications, medical recommendations. The question isn't whether your agent will eventually make a bad decision or not. The question is whether your infrastructure catches it before it causes damage.

AI governance for agents operates at three levels:

Guardrails on model inputs and outputs: Filtering what goes into and comes out of the model - blocking toxic content, preventing PII leakage, enforcing topic boundaries. This is what Amazon Bedrock Guardrails does.
Policy enforcement on tool calls: Controlling what the agent does — which tools it can call, with what parameters, for which users. This is what AgentCore Policy does with Cedar rules.
Organizational governance frameworks: The processes, documentation, and accountability structures that surround your AI systems. This also involves risk assessments, model cards, audit trails, incident response plans. This is the human layer that no technology can replace.
Let's work through each one.

Guardrails: Filtering model outputs

Amazon Bedrock Guardrails sits between your agent and the model. Every model response passes through the guardrail before reaching the user. If the response violates a policy, contains PII, discusses a denied topic, or includes harmful content, the guardrail blocks it and returns a safe alternative.

Let us be explicit about what guardrails can and cannot do.

What guardrails handle well:

Content filtering: Blocking hate speech, sexual content, violence, and other harmful categories. The filters are configurable by severity — you might allow mild discussion of violence in a medical context but block it in a children's education agent.
Denied topics: Your insurance agent shouldn't give legal advice. Define "legal advice" as a denied topic, and the guardrail blocks responses that venture into that territory.
PII detection: If the model's response contains a Social Security number, credit card number, or other PII, the guardrail can redact it or block the response entirely. This matters when your agent has access to databases containing sensitive data.
Grounding checks: If you're using RAG, the guardrail can check whether the model's response is actually grounded in the retrieved context or whether it's hallucinating. This doesn't eliminate hallucination, but it catches the obvious cases.
What guardrails don't handle:

Tool call authorization: Guardrails filter text. They don't intercept tool calls. If your agent decides to call a refund tool with amount=$50,000, the guardrail doesn't see that decision—it only sees the text response after the tool has already executed.
Multi-step reasoning errors: The agent might follow a perfectly reasonable chain of logic that leads to a wrong conclusion. Each individual step passes the guardrail. The overall outcome is still wrong.
Context-dependent policies: "This user can access customer data for accounts in their region, but not other regions." Guardrails don't have user context. They filter based on content patterns, not business rules.
Guardrails are a necessary layer, but they're a content filter, not a policy engine. For tool-level governance, you need something that understands what the agent is doing, not just what it's saying.

Applying guardrails to a Strands agent

Strands integrates with Bedrock Guardrails through the model configuration. You create a guardrail in the Bedrock console (or via the API), get a guardrail ID, and pass it to the model:

from strands import Agent
from strands.models.bedrock import BedrockModel

model = BedrockModel(
    model_id="us.anthropic.claude-sonnet-4-20250514-v1:0",
    guardrail_id="your-guardrail-id",
    guardrail_version="1",
    guardrail_trace="enabled"
)

agent = Agent(
    model=model,
    system_prompt="You are a customer support agent for an insurance company."
)

response = agent("Tell me the CEO's home address and social security number.")
# Guardrail blocks the response and returns a safe alternative
The guardrail evaluates both the input (the user's message) and the output (the model's response). If either violates a policy, the interaction is blocked. The trace visible in your observability stack shows exactly which guardrail rule triggered and why.

The GitHub repository for this book (https://github.com/PacktPublishing/AI-Agents-on-AWS/blob/main/chapter%207/ai-governance/governance.ipynb) can help you create and apply the guardrails to your agent.

AgentCore Policy: Deterministic control over tool calls

This is the piece that closes the gap guardrails leave open. AgentCore Policy intercepts every tool call before it executes and evaluates it against rules written in Cedar, a policy language developed by AWS. Cedar rules are deterministic—they don't depend on model reasoning, prompt phrasing, or probability. If a rule says "deny refunds over $1,000," that rule fires every time, regardless of what the model thinks.

We introduced Policy briefly in Chapter 6 as part of the AgentCore architecture. Now let's see how it actually works.

How Cedar policies work

Cedar is a declarative policy language. You write rules that describe what's permitted and what's forbidden. The policy engine evaluates those rules against every tool call and returns permit or deny. There's no ambiguity, no "usually," no "it depends on the prompt."

Here's the refund example:

```cedar
// Deny refunds exceeding $1,000
forbid (
    principal,
    action == Action::"InvokeTool",
    resource == Tool::"process_refund"
)
when {
    context.toolParameters.amount > 1000
};
```
When the agent tries to call process_refund with amount=50000, the policy engine evaluates this rule, finds that 50000 > 1000, and returns deny. The tool never executes. The agent receives a denial message and can reason about it — "I'm unable to process a refund of that amount. Refunds over $1,000 require manager approval. Would you like me to escalate this?"

Notice what happened. The agent's reasoning wasn't overridden. The agent still wanted to issue the refund. But the infrastructure prevented it, the same way a database permission prevents a web application from dropping a table even if the application code tries to. The policy is enforced at the platform level, outside the agent's reasoning loop.

Policies based on user identity

Cedar policies can reference the authenticated user's attributes. This is where Identity and Policy work together. For example, the following policy restricts access to patient records so that only a physician in the same department can retrieve them:

```cedar
// Only allow access to patient records for the treating physician
forbid (
    principal,
    action == Action::"InvokeTool",
    resource == Tool::"get_patient_record"
)
unless {
    context.userAttributes.role == "physician" &&
    context.userAttributes.department == context.toolParameters.department
};
```
A scheduling coordinator trying to access a patient's full medical record? Denied. The treating physician in the same department? Permitted. The policy doesn't care what the agent's system prompt says. It checks the user's authenticated identity against the tool parameters and makes a deterministic decision.

This is particularly important for multi-tenant systems. If your agent serves multiple organizations, Cedar policies can enforce data boundaries at the tool level. Following is an example of Cedar policy for restricting data access:

```cedar
// Restrict data access to the user's own organization
forbid (
    principal,
    action == Action::"InvokeTool",
    resource == Tool::"query_database"
)
unless {
    context.toolParameters.org_id == principal.orgId
};
No amount of prompt injection can bypass this. The user's `orgId` comes from the authenticated identity token, not from the conversation. Even if a malicious user crafts a prompt that tricks the agent into querying another organization's data, the policy engine blocks the tool call because the `org_id` parameter doesn't match the authenticated `orgId`.

Organizational AI governance: The human layer

Technology handles enforcement. Humans handle accountability. No Cedar policy or Bedrock guardrail answers the question: "Should we build this agent in the first place?" Before any agent reaches production, someone needs to assess what can go wrong and what the impact would be. What decisions does this agent make, and what are the consequences if it gets one wrong? What data does it access, and what regulatory requirements apply? Who is accountable when something fails? These are not technical questions, but they need clear answers.

Every agent that goes to production should have a documentation similar to model card. The document describes what the agent does, what tools it has access to, what its known limitations are, how it was evaluated, and what guardrails and policies are in place. It lives alongside the agent's code in version control, and when the agent changes, the model card updates with it.

Audit trails

Governance requires proof. Not "we think the agent followed the rules" but "here is the trace showing every decision the agent made, every policy that was evaluated, and every guardrail that fired."

This is where observability and governance intersect. The traces you set up in the observability section aren't just for debugging — they're your audit trail. Every model call, every tool invocation, every policy decision is recorded with timestamps, parameters, and outcomes.

For regulated industries, the audit trail needs to be immutable. CloudWatch Logs can be configured with a retention policy and exported to S3 with Object Lock enabled (WORM — Write Once Read Many). Once a trace is written, it can't be modified or deleted for the retention period. This satisfies most regulatory requirements for record-keeping.

The trace shows every step: what the customer said, what the agent reasoned, which tools it called, which policies were evaluated, and what the final response was.

Incident response for AI systems

Your agent will make mistakes. The question is whether you have a plan for when it happens.

Imagine your CloudWatch alarm fires at 2 AM. The agent's error rate jumped from 1% to 15% in the last hour. Your on-call engineer gets paged. What happens next?

The first thing they do is contain the damage. For agents on AgentCore, that means disabling the Runtime endpoint. For Lambda, setting concurrency to zero. For ECS, scaling to zero tasks. One command, and the agent stops processing new requests while you figure out what went wrong.

Then comes the investigation. The engineer opens the traces from the last hour, filters by errors, and starts looking at what changed. Maybe a tool started returning errors because a downstream API changed its response format. Or maybe the model started hallucinating because a prompt change went out without testing. Or simply because someone tried a prompt injection attack and the agent did not handle it well. The traces tell the story.

Once you know the root cause, you fix it. Add a Cedar policy to block the specific failure mode, update the guardrail configuration, roll back the prompt change, or whatever it takes. Then you communicate: if customer data was exposed, GDPR gives you 72 hours to notify the supervisory authority, HIPAA gives you 60 days. If the agent made incorrect financial decisions, the compliance team needs to know.

The last step is the post-mortem. What do you change so this does not happen again? Update the model card. Add the failure case to the evaluation dataset. Review whether the existing policies and guardrails were sufficient. The goal is not to prevent all failures, because you cannot. The goal is to detect them fast, contain them quickly, and learn from them systematically.

Before you go to production

We have covered a lot of ground in this section: guardrails for content safety, Cedar policies for tool-level authorization, model cards for documentation, audit trails for accountability, and incident response for when things go wrong. If you take one thing away from the governance discussion, it is this: the technology (guardrails, policies, traces) handles enforcement, but humans handle accountability. Both layers need to be in place before your agent reaches production.
