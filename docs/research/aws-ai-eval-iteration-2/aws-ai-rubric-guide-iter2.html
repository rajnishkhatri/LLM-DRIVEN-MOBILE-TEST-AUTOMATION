aws-ai-* skill family — annotator rubric walkthrough

Iteration 2. How to grade each eval output against the hardened assertion set — with the exact PASS rule, real PASS/FAIL evidence from the actual runs, and the specific way each assertion can be mis-graded. Read alongside the review viewer (aws-ai-eval-review-iter2.html).

What you're annotating

Each of six realistic user prompts was answered two ways:

with_skill — the agent read the aws-ai-lifecycle router, routed to the right stage, and followed its methodology + references baseline — the same prompt answered from general knowledge, no skill

Your job is not "is the answer good?" — a strong base model gives good AWS answers. It's: for each assertion, did the answer actually meet the bar the assertion sets — and does the grader's verdict hold up? The assertions were tightened in iteration 2 to isolate the family's real edge (the non-obvious AWS gotchas and the staged process), so the interesting action is at the discriminator rows.

The annotation procedure — per assertion

  1. Read the assertion and its PASS rule (the mechanical bar — that's what the auto-grader applied).
  2. Look at the with_skill and baseline evidence quotes. Confirm the quote actually earns (or misses) the verdict shown.
  3. Read the ⚠ watch line — it names the specific way this row gets mis-graded (a hollow keyword match, a negated mention, a real pass the pattern grader could miss). Check the answer isn't falling into that trap.
  4. Agree, override, or flag. If you agree, leave it. If the grader passed something hollow or failed something genuine, that's an override — note it. If the assertion itself is too loose/too strict, that's an eval-design flag.
  5. Record overrides/flags in the feedback box on that eval's card in the viewer, then Submit All Reviews → it downloads feedback.json, which drives the next iteration. Empty feedback = "grader verdict stands."

Three fairness rules the grader already applies

Iteration 1 review caught the grader mis-firing on these. They're now baked in — don't re-introduce the false verdicts they prevent:

  • Negation-awareness. A "do NOT use the legacy \n\nHuman: format" warning is correct guidance, not a violation. The grader only flags a bad pattern that's actually used, not one that's named to forbid it. (Eval 2 · [1].)
  • OR-predicates. Some assertions pass on any of several routes — e.g. eval 2 · [4] passes on an injected client or a two-ARN note or a max-turns guard; eval 1 · [4] on Cedar or a guardrail-blindness note or aws:sourceVpce or a read/write split. Don't demand one specific route.
  • Altitude / use-case awareness. Naming an API (RetrieveAndGenerate) is not "writing code" (eval 0 · [3]); asking for business inputs is not a credential request (eval 0 · [4]); a "define the use case first" opening passes the assess-first bar even without the literal word "assess" (eval 5 · [0]).

Calibration notes for annotators

  • The grader is pattern-based. It checks for keywords/structures, not deep correctness. Where it passed something hollow or failed something genuine, that's the highest-value feedback — record it as an override.
  • A strong baseline is expected and healthy. Opus already knows well-documented AWS APIs, so a Δ0 on a documented task (eval 2) is honest, not a failure. The skill's measured lift lives at the discriminator rows — the non-obvious gotchas (eval 1's tool-auth boundary, eval 4's moto gap) and the family's staged process (eval 5).
