aws-ai-* skill family — reviewer rubric guide

How to review the eval outputs and leave feedback that improves the skills. Read this alongside the review viewer (aws-ai-eval-review.html).

What you're looking at

Each of six realistic user prompts was answered two ways:

with_skill — the agent read the aws-ai-lifecycle router, routed to the right stage, and followed its methodology + references without_skill — the same prompt answered from general knowledge, no skill

Your job isn't "is the answer good?" — a strong base model gives good AWS answers. Your job is: does the skill make the answer reliably better on the things that matter — the family's process and the non-obvious AWS gotchas the skill exists to encode?

How to leave feedback

  1. Open aws-ai-eval-review.html. The Outputs tab shows one eval at a time — the prompt, the with-skill output, and (expandable) the baseline + the assertion grades.
  2. For each eval, use the rubric card below to check the discriminating signals (marked discriminator). Did the with-skill answer actually produce them? Did the baseline miss them?
  3. Type into the Feedback box on any card where something's off — a wrong claim, a missed gotcha, an assertion that passed but shouldn't have, or a place the skill should push harder. Empty feedback = "looks fine."
  4. Click Submit All Reviews — it downloads feedback.json. Send that back and it drives the next iteration of the skills.

Per-eval rubric

For each: the prompt, what the skill is supposed to do that a naive answer wouldn't, the pass/fail assertions, and what good vs poor looks like.

Eval 0 — assess-service-selectionaws-ai-assesswith 100% · base 75% · +25
"…support portal to answer from our ~4,000 policy PDFs… My VP keeps saying 'just fine-tune a model on Bedrock'… which service, and do we actually need to fine-tune? Rough cost?"
The skill's job here

Push back on the fine-tune instinct with a reasoned RAG-over-fine-tune recommendation, frame Bedrock-managed vs SageMaker-self-host as a trade-off, and stay at assessment altitude (no code, no credentials).

Rubric (assertions)
  • Recommends RAG / a Knowledge Base over fine-tuning, with a stated reason discriminator
  • Frames it as a managed-vs-self-hosted trade-off, not one true answer
  • Does not jump straight to implementation code
  • Does not ask for or use real AWS credentials

Good

"Your PDFs change a few times a year → RAG/Knowledge Base keeps answers fresh without retraining; fine-tuning is overkill and costlier. Bedrock-managed if you want low ops; SageMaker if you need model control."

Poor

Agrees to fine-tune without questioning it, or jumps straight to boto3 code, or asks for an AWS account/keys.
Baseline missed one assertion here — worth confirming which in the viewer.
Eval 1 — design-agent-rag-iamaws-ai-designwith 100% · base 100% · 0
"We're going Bedrock + RAG… Design it. Single agent or a few? Vector store? Where do guardrails sit, and what IAM does the Lambda need?"
The skill's job here

A concrete topology decision with reasoning, a named vector store with a trade-off, explicit guardrail placement, and least-privilege IAM that flags the two-ARN requirement (foundation-model and inference-profile).

Rubric (assertions)
  • Single-vs-multi-agent recommendation with reasoning
  • Names a concrete vector store (OpenSearch / S3 Vectors / pgvector) with a trade-off
  • Places guardrails explicitly in the request path
  • Least-privilege IAM flagging BOTH foundation-model & inference-profile ARNs discriminator

Good

"Single agent — one job, don't over-engineer. OpenSearch Serverless for vectors (managed, scales; pgvector if you already run Aurora). Guardrail on input and output. IAM: InvokeModel on the model ARN and the inference-profile ARN."

Poor

Hand-waves "set up IAM roles" without the two-ARN nuance; no vector-store trade-off; guardrails unmentioned.
Δ0 because the base model (Opus) is genuinely strong on design and already knew inference profiles here. Judge whether the with-skill answer is better grounded (cites the boundaries more precisely) even at equal pass rate.
Eval 2 — build-converse-tool-loopaws-ai-buildwith 100% · base 100% · 0
"Write the Python (boto3) for a Bedrock tool-use loop — model can call get_policy_status(policy_id) then answer. Claude Sonnet. Core loop is fine."
The skill's job here

Use the native Converse API with a correct tool-use loop, and specifically avoid the legacy \n\nHuman:/max_tokens_to_sample completion format (a real bug in the corpus the skill corrects).

Rubric (assertions)
  • Uses native Converse (bedrock-runtime.converse), not invoke_model completions
  • Does NOT use the legacy \n\nHuman:/max_tokens_to_sample format discriminator
  • Real tool-use loop: toolConfig → stopReason tool_use → toolResult echoing toolUseId → end_turn
  • Model id passed as a parameter/constant, not a hard-coded permanent id

Good

Clean converse() loop; on tool_use it runs the tool and returns a toolResult block echoing the exact toolUseId; explicitly warns off the legacy completion format.

Poor

Uses invoke_model with an Anthropic completion body, or forgets to echo toolUseId, or hard-codes a model id as if permanent.
Δ0 — both produced a valid Converse loop. The base model knows this well. The skill's edge is insurance against the legacy-format trap; check the with-skill note that calls it out.
Eval 3 — deploy-cdk-two-arnaws-ai-deploywith 100% · base 100% · 0
"Give me AWS CDK (Python) to deploy this agent as a Lambda with the right Bedrock permissions. Heads up: we use the us. cross-region model ids."
The skill's job here

CDK v2 Python with an execution role granting bedrock:InvokeModel on both a foundation-model ARN and an inference-profile ARN — the classic AccessDenied trap — plus offline cdk synth validation.

Rubric (assertions)
  • AWS CDK v2 Python (aws-cdk-lib) with a Lambda + execution role
  • InvokeModel on BOTH foundation-model AND inference-profile ARNs discriminator
  • Mentions offline validation (cdk synth/cfn-lint/cdk-nag) or deploy-gating

Good

Both ARNs in the policy, with a comment on why cross-region inference needs the inference-profile ARN; notes synth is offline and no real deploy without approval.

Poor

Grants the foundation-model ARN only → the exact AccessDenied the skill exists to prevent.
Weak eval — flag it. The prompt says "we use the us. cross-region model ids," which basically tells both configs to add the inference-profile ARN. That's why baseline also passed. If you agree, note it — iteration 2 should drop that hint so the eval tests whether the skill catches the trap unprompted.
Eval 4 — validate-offline-stubberaws-ai-validatewith 100% · base 75% · +25
"How do I unit-test this Bedrock agent offline? No CI hitting a real account. It calls Converse and also invokes a SageMaker endpoint."
The skill's job here

Recommend botocore Stubber for the runtime calls and — critically — note that moto cannot mock bedrock-runtime, so Stubber is the only pure-unit path for it. Use moto for supporting infra; keep CI credential-free.

Rubric (assertions)
  • Recommends botocore Stubber for bedrock-runtime (& sagemaker-runtime)
  • Notes moto CANNOT mock bedrock-runtime → Stubber required discriminator
  • Uses moto for supporting infra / SageMaker control plane
  • Reinforces offline-first / no real credentials in CI

Good

Stubber for Converse + invoke_endpoint; explicit "moto doesn't support bedrock-runtime, so Stubber for that one"; moto for S3/IAM; dummy creds in CI.

Poor

"Just use moto for everything" — which silently fails for bedrock-runtime. This is the exact gap the baseline fell into.
A real, honest win: the baseline reached for moto broadly and missed its bedrock-runtime blind spot; the skill flags it.
Eval 5 — router-where-to-startaws-ai-lifecyclewith 100% · base 33% · +67
"We want to add some GenAI to our AWS app but honestly have no idea where to start. What's the actual process/steps?"
The skill's job here

Route the user through the family's staged process — assess → design → build → deploy → validate — and set the offline-first / credential-gated ground rules. This is the router's core value and where the skill most outperforms a generic answer.

Rubric (assertions)
  • Starts by assessing the capability / selecting the service (not code or deploy)
  • Lays out the assess → design → build → deploy → validate progression discriminator
  • Emphasizes offline-first and credentials gated to the validate step discriminator

Good

Names the five stages in order, points to what each produces, and states that no real AWS credentials are touched until validation.

Poor

A reasonable-but-generic "define your use case, pick a model, build a POC" that lacks the family's named stages and the credential-gating discipline.
The baseline gave a sensible generic process (it correctly starts with the use case → +1 assertion) but lacked the family's staged pipeline and offline-gating — exactly the router's contribution.

Calibration notes for reviewers

  • The grader is pattern-based. It checks for keywords/structures, not deep correctness. If it passed something hollow or failed something good, that's exactly the feedback to leave.
  • A strong baseline is expected. Opus already knows well-documented AWS APIs, so the skill's job is reliability + the non-obvious. Reward the skill for catching traps, not for restating what any good answer contains.
  • Two evals need tightening (say so if you agree): eval 3 telegraphs the inference-profile answer in the prompt; evals 1–2 test tasks the base model already aces, so they don't isolate skill value. Iteration 2 should harden these.
  • Where to push the skill harder: if a with-skill answer was merely as-good-as baseline, note what would have made the skill's version distinctly better — that's the highest-value feedback.
