Chapter 4: Advanced Agent Architecture Patterns
4

Whenever a software team needs to solve a complex problem, they don't dedicate a single person to do everything, whether it's architecture, coding, testing, or deployment. That would create chaos. Rather, there are architects, developers, testers, each doing what they're good at. Similarly, a hospital has doctors, nurses, specialists, and administrators working together. The same principle applies to AI agents.

In the previous chapters, you learned how to build single agents with tools and how they interact with other systems. For the majority of use-cases, a single agent should be able to accomplish most of the tasks. But what if a single agent isn't enough and if your problem is too complex for one agent to handle alone?

In this chapter, we'll move from single agents to multiple agents. We'll start by understanding why one agent isn't always enough, then explore patterns for coordinating multiple agents—from a simple supervisor delegating tasks to workers, to swarms of agents handing off work to each other, to structured graphs that route decisions through defined paths. Along the way, you'll build working examples and learn when each pattern makes sense (and when it doesn't).

The multi-agent solution

Imagine you're running a busy restaurant. You could have one person doing everything—taking orders, cooking, serving, and cleaning. But that would be slow and inefficient. Instead, you have specialized roles: a host, servers, chefs, and dishwashers. Each person focuses on what they do best, and together they create a smooth dining experience.

Multi-agent systems work the same way. Instead of building one super-complex agent that tries to do everything, you create multiple specialized agents that work together. Each agent has a specific job, and they coordinate to solve complex problems faster and more effectively. Under the hood, a coordinator agent receives the user's request, breaks it into subtasks, and delegates each one to the right specialist. The specialists do their work and report back, and the coordinator stitches the results into a single response.

Multi-agent systems solve these problems by breaking down complex tasks into smaller, manageable pieces and assigning them to specialized agents.

What are multi-agent patterns?

A multi-agent pattern is a structured way of organizing multiple AI agents to work together toward a common goal. Think of an orchestra where you have different sections like strings, brass, woodwinds, and percussion. Each section plays their part, but they all work together under a conductor to create beautiful music.

Just like orchestras can be organized in different ways (a small chamber ensemble, a large symphony, or a jazz band with improvisation), there are different patterns for organizing agents. Each pattern solves specific types of problems, and choosing the right one makes your system more efficient and easier to build.

These four aspects form the foundation of every multi-agent pattern that we'll explore in this chapter. First, we'll start with the simplest and most common pattern, then explore variations that handle more complex scenarios.

Your first multi-agent pattern: the supervisor-worker

In the supervisor-worker pattern, one agent acts as the coordinator. It receives the request, decides which specialist agents to call, delegates the work, and combines their results into a single response. The workers focus on their specific tasks and report back to the supervisor. Let's see this in the form of an example. Let's say, you're building a market research assistant. An investor asks: Should I invest in electric vehicle companies?

Your first version uses one agent. It scans recent news, analyzes stock performance, checks social media sentiment, reads analyst reports, compares competitors. It takes about five minutes per query. Works fine for a few queries a day. Then your boss says the system needs to handle hundreds of queries per hour. Five minutes per query won't work.

You split the work across three agents running in parallel. NewsAgent scans recent EV news. FinancialAgent analyzes stock performance. SentimentAgent checks social media sentiment. These tasks are independent. Since they can all run concurrently, it should ideally be three times faster.

You deploy it, and it works! Though the speed is great, you now have a different problem. The investor gets three separate responses:

NewsAgent: Tesla announced a new factory in Texas. Rivian had production delays. Ford is investing $50B in EV infrastructure.
FinancialAgent: EV sector up 15% this quarter. Tesla P/E ratio is 45. Rivian burning $1B per quarter.
SentimentAgent: Twitter sentiment mixed. Reddit bullish on Tesla. Concerns about charging infrastructure.
The investor stares at this wall of unconnected facts and asks: So... should I invest or not?

You can notice that nobody synthesized the information or made a recommendation. The three agents did their jobs perfectly, but nobody coordinated them into a coherent answer. You need a supervisor agent here, who takes these three perspectives and weaves them into a clear recommendation.

With the supervisor-worker pattern, the supervisor agent coordinates the worker agents. Worker agents do specialized tasks and report back. Worker agents never talk to each other. All communication goes through the supervisor.

Let's re-consider the investment prompt but this time with the supervisor-worker pattern. So, the supervisor gets the question and thinks: This person needs news context, financial analysis, and market sentiment. I have three workers who handle exactly those things.

The supervisor calls all three workers at once:

NewsAgent: What's happening in the EV industry this month?
FinancialAgent: What's the financial health of major EV companies?
SentimentAgent: What's the market sentiment around EVs?

Debugging becomes straightforward. If there's anything wrong with financial data, check FinancialAgent. If the news is outdated, check NewsAgent. The supervisor handles synthesis, not domain logic, so bugs stay isolated.

Adding new capabilities is easy. So, if you need regulatory analysis, you can create a RegulatoryAgent and tell the supervisor about it. Existing workers don't change. Let us see how a supervisor agent looks like in practice:

from strands import Agent
# Create worker agents with specific expertise
news_agent = Agent(
    name="news_agent",
    system_prompt="Research recent news about companies and industries. Provide factual, up-to-date information from reliable sources.",
    tools=[news_search_tool]  # Tool for accessing news APIs
)

financial_agent = Agent(
    name="financial_agent",
    system_prompt="Analyze financial metrics, stock performance, and company valuations. Provide data-driven insights.",
    tools=[financial_api_tool]  # Tool for accessing financial data
)
sentiment_agent = Agent(
    name="sentiment_agent",
    system_prompt="Analyze market sentiment from social media, forums, and investor discussions. Identify trends and concerns.",
    tools=[sentiment_analysis_tool]  # Tool for sentiment analysis
)
# Create supervisor that coordinates the workers
supervisor = Agent(
    name="research_supervisor",
    system_prompt="""You are a market research coordinator. When asked about investment opportunities:

    1. Analyze the question to determine what information is needed
    2. Delegate to specialist agents:
       - news_agent: For recent developments and industry news
       - financial_agent: For financial metrics and performance data
       - sentiment_agent: For market sentiment and investor opinions
    3. Synthesize their responses into a coherent investment recommendation

    Always provide balanced analysis considering all perspectives.""",
    tools=[
        news_agent.as_tool(),
        financial_agent.as_tool(),
        sentiment_agent.as_tool()
    ]
)
# Use the supervisor
question = "Should I invest in electric vehicle companies?"
response = supervisor(question)
print(response)

The trade-offs of the supervisor-worker pattern

One of the major trade-offs with this pattern is that the supervisor becomes a bottleneck. Every decision flows through one agent. In production, you can address this through horizontal scaling (run multiple supervisor instances), caching (repeated queries return instantly), and prompt caching. For high-volume systems, you could use load balancing and async processing.

Another trade-off is the supervisor, which can be a single point of failure. If it crashes, the system stops. You need health checks, automatic restarts, and checkpoint management to ensure that the supervisor resumes from its last known state in case of failure. For critical systems, it's better to run redundant supervisors with a failover mechanism.

Workers can't collaborate directly. If SentimentAgent discovers something FinancialAgent should know, it goes through the supervisor. For simple workflows, this works fine. However, for complex negotiations, you need different patterns called collaborative communication, which we will discuss later in the chapter.

Most multi-agent systems don't need complex negotiations. Rather, they need clear accountability, simple communication, and easy debugging. That's why the supervisor-worker pattern is the most common pattern in production.

Make agents reusable: agent as a tool

The supervisor-worker pattern works well, but every time you need a specialist, you build it from scratch for that specific supervisor. What if you could build an agent once and reuse it across different systems? That's the Agent as Tool pattern. You wrap an agent with a description of what it does, and any other agent can discover and call it like a regular tool.

Research from Anthropic on building effective agents (https://www.anthropic.com/research/building-effective-agents) showed that treating components as modular, reusable tools allows systems to scale without rigid dependencies.

When another agent receives a task, it reads the available tool descriptions and picks the right one. If you recall the tools that we learned in Chapter 2, Building Agents with Tools, you can relate that it's the same concept, but here the tools are agents.

Let's say you are building a tutoring assistant. Students ask questions about different subjects, and you have specialist agents for math, writing, and science. Instead of writing logic that says if the question contains 'equation', call MathAgent, you wrap each specialist as a tool and let the main agent figure out which one to use.

In the following code snippet, notice how each specialist agent is registered as a tool, and the teacher agent picks the right one based on the student's question.

from strands import Agent
# Create specialist agents
math_tutor = Agent(
    name="math_tutor",
    description="Solves mathematical equations and explains math concepts step by step",
    system_prompt="You are a math tutor. Solve math problems and explain your solutions clearly, step by step."
)
writing_coach = Agent(
    name="writing_coach",
    description="Helps with writing, grammar, and essay structure",
    system_prompt="You are a writing coach. Help with writing, grammar, and essay structure. Provide constructive feedback."
)
science_helper = Agent(
    name="science_helper",
    description="Explains scientific concepts and principles in simple terms",
    system_prompt="You are a science tutor. Explain scientific concepts clearly using simple language and real-world examples."
)
# Teacher agent uses specialists as tools
teacher = Agent(
    system_prompt="""You are a teacher who helps students by delegating to specialist tutors.
    Never solve problems yourself. Always delegate to the appropriate specialist:
    - math_tutor: for math problems and equations
    - writing_coach: for writing, grammar, and essays
    - science_helper: for science questions

    After receiving the specialist's response, present it to the student in a friendly way.""",
    tools=[math_tutor, writing_coach, science_helper]
)
# Student asks a question
response = teacher("Can you help me solve this quadratic equation: x^2 + 5x + 6 = 0?")
print(response)

How data flows through multi-agent systems

You've seen the supervisor-worker pattern and Agents as Tools. Now let's zoom out and understand how data actually moves through these systems. We'll use a real example, asking, What's the best laptop for video editing under $2000?

Step 1: The request arrives

Your question hits the system as raw text. Nothing's happened yet.

Step 2: The router makes decisions

The router reads your question and thinks: Okay, this person needs product recommendations, price comparisons, and technical specs. I know exactly which agents can help.

The router might decide:

Send to the Specs Agent (knows technical requirements for video editing)
Send to the Price Agent (can search current prices across retailers)
Send to the Review Agent (can analyze customer feedback)
The router doesn't just blindly forward your question. It might rephrase it for each agent. The Specs Agent gets What CPU and GPU specs are needed for 4K video editing? while the Price Agent gets Find laptops under $2000 with these specs.

Step 3: Agents do their thing

Now three agents are working simultaneously. The SpecsAgent is calculating requirements, the PriceAgent is searching retailer databases, and the ReviewAgent is analyzing thousands of customer reviews. They're all working at the same time.

Each agent has its own memory of the conversation. If you've asked about video editing software in a previous message, the SpecsAgent remembers that context.

Step 4: Agents talk to each other (sometimes)

Let's say the Price Agent finds a laptop for $1,800, but the Specs Agent realizes it doesn't have enough RAM for 4K editing. The Price Agent might ask: Hey Specs Agent, if we increase the budget to $2,100, can we get something that works?

This back-and-forth happens automatically. Agents negotiate and refine their answers based on what others are finding.

Step 5: Combining the results

A supervisor agent collects everything:

SpecsAgent: You need at least 32GB RAM, RTX 4060, and an i7 processor.
PriceAgent: Found 3 laptops matching specs: $1,899, $1,999, $2,049.
ReviewAgent: The $1,999 option has 4.5 stars with great feedback on rendering speed.
Step 6: You get your answer

The aggregator synthesizes it into one answer: Based on your needs, I recommend the Dell XPS 15 at $1,999. It has the specs you need for 4K editing, fits your budget, and users specifically praise its video rendering performance.

The final response feels like it came from one agent, but behind the scenes, three specialist agents collaborated to give you the best answer.

Know about video editing requirements

That's a lot for one agent. It would be slower, more expensive to run, and more likely to miss something. With multiple agents, each one is an expert in its domain, and they work in parallel.

What we just described seems simple, but there's a lot happening under the hood. How do agents share information? How do you decide if they work in sequence, in parallel, or collaboratively? Let's look at that next.

Understanding communication techniques

You know what makes up a multi-agent system. Now you can dive into the most critical piece: how agents talk to each other.

Agents working in isolation aren't really a system. They're just individual programs running separately. Communication is what turns them into something useful: sharing information and coordinating their work. But not all communication looks the same.

Agents can communicate in three main ways. Each one solves different problems and fits different situations.

Sequential communication

Picture you are writing a research paper. You can't write the conclusion before doing the research. You can't edit what hasn't been written yet. Some things just have to happen in order.

Sequential communication works this way: one agent finishes its work and hands off the results to the next agent.

Figure 4.7: Sequential communication
Figure 4.7: Sequential communication

The Research Agent may spend 10 minutes gathering information from various sources. Once it's done, it passes everything to the Writing Agent, which then may spend 15 minutes creating a draft. That draft goes to the Editing Agent, which then may spend 5 minutes polishing the content. The total time it took was 30 (10 + 15 + 5) mins.

Each agent waits for the previous one to finish. The Writing Agent literally cannot start until it has the research. The Editing Agent needs a complete draft to work with.

Sequential communication makes sense when you're stuck with dependencies. If step B needs step A's output, a sequential approach is the way to go. The trade-off is time. Three agents taking 10 minutes each means 30 minutes total with no overlap. If the Writing Agent fails after the Research Agent already spent 10 minutes, that time is wasted. Everything downstream stops and you have to restart the pipeline. On the upside, sequential execution means only one agent calls the LLM at a time, which helps if your account has API rate limits.

Parallel communication

Now imagine planning a conference. One person books the venue, another arranges catering, and a third handles marketing. These tasks don't depend on each other. They can all happen at the same time. Parallel communication lets multiple agents work simultaneously on different parts of the problem. When they all finish, you combine their results.

Figure 4.8: Parallel Communication
Figure 4.8: Parallel Communication

The preceding diagram shows how a user query is sent to three agents at the same time. Each agent works independently, and once all three finish, their results are collected and combined into a single response. Let's say you're analyzing a market before launching a product. You need competitor pricing, customer feedback, and market trends—three different types of analysis.

One agent scrapes a competitor's website and builds a pricing matrix. It takes 5 minutes.
Another agent reads thousands of customer reviews from similar products, identifying patterns in complaints and praise. This also takes 5 minutes.
A third agent analyzes search trends, social media mentions, and industry reports. Another 5 minutes.
If you ran these one after another, you'd wait 15 minutes. Run them in parallel and you wait just 5 minutes (the time it takes for the slowest agent to finish).

Parallel communication works best when tasks are independent, when Agent 1 doesn't need Agent 2's results to do its work. Another situation where parallel communication is useful is when you want higher accuracy, with multiple agents checking the same thing from different angles.

Suppose you're building a content moderation system. You run three agents in parallel, each independently checking if a post violates community guidelines. Agent 1 says safe, Agent 2 says safe, Agent 3 says unsafe. Two out of three vote safe, so you approve the post.

Agents make mistakes. But they don't all make the same mistakes. If three independent agents look at the same content and two agree, you can trust more than one agent's opinion. If all three flag something, you're very confident it needs review.

This voting approach has real backing. Research on enterprise AI systems shows that running multiple agents in parallel and having them vote on results can dramatically reduce error rates compared to a single agent. The paper, The Six Sigma Agent (https://arxiv.org/html/2601.22290v1) discusses how consensus voting with just five agents can reduce errors from 5% down to 0.11%. Independent agents don't make the same mistakes, so voting catches errors that would slip through with a single agent.

You can set up voting different ways depending on what you need. Content moderation might use simple majority. Medical diagnosis might require all agents to agree. Legal document review might give the specialist agent's vote more weight.

Agents must be independent though. If they all use the same data source or reasoning approach, they'll make the same mistakes. You need diversity: different models, different data sources, and different approaches.

Collaborative communication

Think about designing a building. The architect proposes a design, but the structural engineer points out it won't support the weight. The architect adjusts the design, and then the interior designer suggests changes for better flow. Everyone discusses it back and forth until they find a solution that works for all constraints.

Collaborative communication means agents talk to each other, share insights, negotiate trade-offs, and refine their work together, not just working in parallel or sequence.

Let's look at a scenario where three agents collaborate on a code review. The Developer Agent has written a function that processes user data, the Security Agent checks for vulnerabilities, and the Performance Agent ensures the code runs fast enough. Watch how they negotiate trade-offs:

Developer Agent: I've written a function that processes user data quickly.
Security Agent: This is vulnerable to SQL injection. You need to sanitize inputs.
Developer Agent: If I add sanitization, performance drops by 40%.
Performance Agent: 40% slower is unacceptable. We have strict latency requirements.
Security Agent: Then use parameterized queries. They're secure and fast.
Developer Agent: Good idea. Let me refactor.
Performance Agent: Wait—you're loading the entire dataset into memory. Stream it instead.
Developer Agent: Done. All three concerns addressed.
[All agents review the updated code]
Security Agent: Secure now.
Performance Agent: Meets latency requirements.
Developer Agent: Code is ready.
This back-and-forth doesn't happen in sequential or parallel patterns. Sequential passes information in one direction. Parallel communication has agents working independently without talking to each other. Collaborative is a real conversation where agents negotiate until they find a solution that satisfies all the different agents' requirements, for instance, in the preceding code review example, balancing security, performance, and maintainability.

If you ask whether this actually works better than a single agent, the answer is yes. Research on multi-agent systems shows that agents discussing and refining together outperform single agents on complex reasoning tasks. The paper Beyond the Strongest LLM: Multi-Turn Multi-Agent Orchestration vs. Single LLMs on Benchmarks(https://arxiv.org/html/2509.23537v1) found that iterative discussion catches errors and explores alternatives that one agent would miss.

Collaborative communication has a trade-off though. Multiple rounds of discussion mean multiple rounds of LLM calls. A single agent might respond in 10 seconds. Three agents collaborating might take 30-40 seconds. Troubleshooting is also more complex. When three agents go back and forth multiple times, figuring out which round of conversation introduced a bad decision takes more effort than debugging a simple sequential pipeline. It's also slower and costlier, but you get better decisions on complex problems where trade-offs matter.

Collaborative communication works best when agents need to balance trade-offs that don't have a single right answer. Security vs. performance, cost vs. quality, speed vs. accuracy. These are decisions where one agent's recommendation affects another's. Instead of picking one perspective, you let agents negotiate until they find a solution that addresses all three concerns. The code review example above is a good illustration: the final code was secure, fast, and correct because all three agents pushed back on each other until the trade-offs were resolved.

You've learned how agents communicate. Sequential, parallel, and collaborative are the building blocks. Now we'll see how to organize entire systems using these building blocks.

The patterns coming next (Graph, Swarm, and Workflow) show you different ways to structure multi-agent systems. Each one uses the communication patterns you just learned but applies them to solve specific types of problems.

Common orchestration patterns

You've learned the supervisor-worker pattern and now you understand how agents communicate. Supervisor-worker is the most common pattern used by organizations, but it's not the only one. Let's explore two common patterns that solve different types of problems: Swarm and Graph Pattern.

Swarm patterns

Similar to collaborative communication we learned earlier in this chapter, where agents discuss and negotiate until they find a solution to a user query, the Swarm pattern takes the same approach and builds a system around it. The challenge with collaborative communication was coordination: Who talks to whom, when, and how do you prevent agents from talking in circles? Swarm solves this through handoffs, where agents pass control to each other explicitly.

Imagine you're part of a team designing a new level for a video game, let's say, a stealth mission in an abandoned space station. The level designer creates the initial layout (floor plan) and blackout (rough 3D prototype). During playtesting, the game designer discovers players get lost because there aren't enough visual cues. Back to the level designer, they add landmarks and lighting to guide players, but then the narrative designer realizes the new bright lighting contradicts the story, and this is supposed to be an abandoned facility with a creepy atmosphere, not a well-lit area. The level designer adjusts to use dim emergency lights and environmental storytelling instead.

Now the difficulty balancer playtests and finds the level is too easy with clearer navigation. Back to the level designer to add more challenging enemy placements without removing the visual cues. The process loops and branches based on what each specialist discovers during their review. You can't predict the path up front.

In a Swarm system, you'd have four agents: level_designer, game_designer, narrative_designer, and difficulty_balancer. Each agent operates independently with its own expertise. They don't share a supervisor or follow a fixed sequence. Instead, when one agent finishes its part, it decides which agent should go next and hands off the task with context about what's been done so far.

from strands import Agent
from strands.multiagent import Swarm
level_designer = Agent(
    name="level_designer",
    model="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    system_prompt="""You are a Level Designer in a game design swarm.
Your role in the swarm is to create level layouts, environments, and visual elements.
Focus ONLY on layout and visual design. Do NOT write narrative or balance difficulty.
After completing your layout, hand off to other agents for review.
When receiving feedback from other agents, revise your design accordingly."""
)
game_designer = Agent(
    name="game_designer",
    model="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    system_prompt="""You are a Game Designer in a game design swarm.
Your role in the swarm is to playtest designs for fun, usability, and player confusion.
Focus ONLY on gameplay feel and player experience. Do NOT design layouts or write narrative.
When you find issues, hand off to the appropriate agent.
Build upon the work of other agents while adding your playtesting perspective."""
)
narrative_designer = Agent(
    name="narrative_designer",
    model="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    system_prompt="""You are a Narrative Designer in a game design swarm.
Your role in the swarm is to create story elements, character backstories, and atmospheric details.
Focus ONLY on narrative. Do NOT redesign layouts or adjust difficulty.
After adding narrative elements, hand off to another agent for their perspective.
When receiving designs from other agents, enrich them with story context."""
)
difficulty_balancer = Agent(
    name="difficulty_balancer",
    model="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    system_prompt="""You are a Difficulty Balancer in a game design swarm.
Your role in the swarm is to evaluate and tune difficulty progression, enemy placement, and pacing.
Focus ONLY on balance. Do NOT redesign layouts or write narrative.
When you find layout or narrative issues, hand off to the appropriate agent.
After balancing, hand off to game_designer for a final playtest review."""
)
swarm = Swarm(
    [level_designer, game_designer, narrative_designer, difficulty_balancer],
    entry_point=level_designer,
    max_handoffs=20,
    max_iterations=20,
    repetitive_handoff_detection_window=8,
    repetitive_handoff_min_unique_agents=3
)
result = swarm("""Design a stealth mission level in an abandoned space station.
The level needs to support multiple playstyles (aggressive stealth, patient stealth, and ghost runs).
Include at least 3 distinct zones with different difficulty levels,
narrative elements that explain why the station was abandoned,
and ensure the difficulty curve is appropriate for mid-game players.""")
When you look at the code sample, the entry_point parameter specifies which agent starts first, the level_designer agent in this case. The max_handoffs and max_iterations limit how many times agents can pass control and how many total iterations can occur. Without these limits, agents could loop indefinitely.

One common problem in swarms is the ping-pong behavior, where two agents keep bouncing the same task back and forth without making progress.

The repetitive_handoff_detection_window and repetitive_handoff_min_unique_agents parameters prevent this.

In the preceding code, the detection window is set to 8 and minimum unique agents is 3. This means the system looks at the last 8 handoffs, and if fewer than 3 different agents appear in that window, it stops the swarm. So, if level_designer and narrative_designer keep passing back and forth for 8 turns without involving any other agent , the system recognizes the loop and forces a conclusion.

Let's say, game_designer agent finishes playtesting and finds that enemy patrol patterns are too predictable. Now this is a difficulty issue, not a playtesting issue. The game_designer agent needs to hand this off to someone who can tune the challenge.

The Swarm provides the game_designer with a formatted context that includes:

The original task
Previous agents who worked on this (for example, level_designer → game_designer)
What did each previous agent contribute?
A list of available agents with their descriptions
The game_designer reads through the available agents:

level_designer: Creates level layouts, environments, and visual elements
narrative_designer: Creates story elements, character backstories, and atmospheric details
difficulty_balancer: Evaluates and tunes difficulty progression, enemy placement, and pacing
The patrol problem matches the difficulty_balancer's description. The game_designer then makes the handoff:

handoff_to_agent(
    agent_name="difficulty_balancer",
    message="Patrol patterns too predictable - need more variation"
)
Now difficulty_balancer is in control. It receives the same formatted context showing the full context of what the game_designer found.

This is how the handoff mechanism works. Each agent sees who's available and what they do, then decides who should handle the current issue. The LLM makes this routing decision by matching the problem to the agent descriptions.

The sequence isn't predetermined. In some cases, the work of level_designer passes through all reviewers without issues. In other cases, agents hand off back and forth multiple times as they discover new problems. You define the agents and what they're good at, then they figure out who should handle each issue as it comes up.

Swarm works well for collaborative work where you can't predict the path upfront. If you need a fixed sequence where certain checks always happen in a specific order, Swarm isn't the right choice. Use the Graph pattern instead, which we'll cover next.

Graph pattern

Graph pattern is built on Directed Graph, where data flows along defined paths from one node to the next. In Graph Pattern, you will see two approaches – Directed Acyclic Graphs (DAG) and cyclic graph. Think of DAGs as flowcharts where arrows only point forward and never loop back. For example, order processing: risk check, then fraud detection, then shipping. Once an order clears fraud detection, it never goes back to risk check. In a cyclic graph, data can loop back to earlier nodes. For example, a code review system where a developer writes code, a reviewer flags issues, and it goes back to the developer for fixes. This loop repeats until the reviewer approves.

You might be thinking, this sounds similar to the Swarm pattern we learned previously, but there's a key difference: in a swarm, agents decide the path on their own. In a graph, you define the paths upfront. We are going to see how we can define these paths. Here we are going to focus more on DAGs because they are most often used in production workflows.

Before we dive into an example, let's understand the building blocks.

Nodes are the building blocks of the graph. Each node represents something that processes data. In Strands, a node can be:

A single agent (like a fraud detection agent)
A swarm of agents working together
Another graph (graphs can be nested)
Custom business logic (deterministic functions)
Edges are the connections between nodes. They define how information flows from one node to another. An edge says when node A finishes, pass its output to node B. Edges can have conditions attached, for example, only follow this edge if the order value exceeds $1,000.

Dependencies describe the relationships between nodes. If node B depends on node A, then node A must complete before node B can start. The graph automatically manages these dependencies and executes nodes in the correct order.

Now let's look at an example. Let's say you're running an e-commerce platform. Orders come in all day. Some are $50 purchases from regular customers. Some are $5,000 orders from brand new accounts. Some have shipping addresses that don't match billing addresses. You can't process them all the same way.

You could use supervisor-worker pattern. The supervisor looks at each order and decides where to route it. It works fine, but what if your payment processor asks, How do you ensure high‑value orders always get fraud review? With supervisor-worker, the routing happens inside the LLM's reasoning. You can log it, but the decision logic isn't explicit in your code.

Graph pattern makes the routing explicit. You draw out the structure: risk analyzer runs first, high-value orders go to manual review, suspicious patterns go to advanced fraud detection, clean low-risk orders go straight to inventory check. The decision tree is visible in your code and anyone can look at it and see exactly what happens for each order type. When an order comes in, the risk analyzer categorizes it into one of three paths:

High-value orders over $1,000 go through manual review before proceeding.
Suspicious orders with red flags like mismatched addresses go through advanced fraud detection.
Low-risk orders from trusted customers skip all fraud checks and go directly to inventory.
After manual review, fraud detection, or direct routing, all three paths converge at inventory check. If items are in stock, the order moves to shipping where labels are generated and the package goes out. If items are out of stock, the order moves to refund processing where the customer is notified and their payment is returned. Every order reaches one of these two final states.

The "directed" part means arrows point one way. Information flows from risk analyzer to fraud check, and never backward. The acyclic part means no loops. So, you can't have risk analyzer followed by suspicious order, then fraud check, then inventory, and finally back to risk analyzer. That would create an infinite loop where orders never complete. The graph structure guarantees every order will eventually reach an end state, either shipped or refunded.

This pattern is useful for compliance and auditability. If your payment processor asks about your fraud prevention workflow, you point to the graph structure. The logic is explicitly defined in code and not hidden in LLM reasoning. An order for $1,500 from a new customer always follows the same path through the graph, and there is no variation based on how an LLM interprets the situation that day.

You might be thinking, where the LLM fits in since the graph structure is deterministic. The graph defines the flow, but each node is an agent that uses an LLM to process its task. The risk analyzer uses natural language understanding to assess the order, the fraud detection agent reasons about suspicious patterns, and the inventory agent interprets stock data. You define the routing and the LLMs handle the reasoning at each step.

Here's an example of a graph-based workflow for processing orders using specialized agents:

from strands import Agent
from strands.multiagent import GraphBuilder
# Create specialized agents
risk_analyzer = Agent(name="risk_analyzer", system_prompt="...")
manual_review_agent = Agent(name="manual_review_agent", system_prompt="...")
fraud_detection_agent = Agent(name="fraud_detection_agent", system_prompt="...")
inventory_agent = Agent(name="inventory_agent", system_prompt="...")
shipping_agent = Agent(name="shipping_agent", system_prompt="...")
refund_agent = Agent(name="refund_agent", system_prompt="...")

# Build the graph
builder = GraphBuilder()
builder.add_node(risk_analyzer, "risk_analysis")
builder.add_node(manual_review_agent, "manual_review")
builder.add_node(fraud_detection_agent, "fraud_check")
builder.add_node(inventory_agent, "inventory_check")
builder.add_node(shipping_agent, "shipping")
builder.add_node(refund_agent, "refund")
# Add conditional edges (conditions check the output from previous nodes)
# Conditional functions like is_high_value check state.results for specific patterns
builder.add_edge("risk_analysis", "manual_review", condition=is_high_value)
builder.add_edge("risk_analysis", "fraud_check", condition=is_suspicious)
builder.add_edge("risk_analysis", "inventory_check", condition=is_low_risk)
builder.add_edge("manual_review", "inventory_check")
builder.add_edge("fraud_check", "inventory_check")
builder.add_edge("inventory_check", "shipping", condition=is_in_stock)
builder.add_edge("inventory_check", "refund", condition=is_out_of_stock)
builder.set_entry_point("risk_analysis")
graph = builder.build()
result = graph("Order #12345: $1,500 laptop from new customer")
Here we have created agents for each processing step, then added them as nodes in the graph. The edges define how information flows between nodes. Some edges have conditions attached that check the previous node's output to decide which path to follow. The conditional functions like is_high_value and is_suspicious examine what the risk analyzer returned and route the order accordingly. The graph structure is fixed, but which path you take through it depends on the data. A $1,500 order goes through manual review, then inventory, then shipping. A $50 order from a trusted customer skips straight to inventory.

You can use Graph patterns when you have established procedures, such as e-commerce order processing, compliance workflows, approval chains, content moderation, or anywhere you need to prove that certain checks always happen in a specific order.

Now that you've learned orchestration patterns. You know how to build supervisor-worker systems, swarms, and graphs. But here's what nobody talks about enough: most problems don't need multiple agents.

When multi-agent is not the answer

We've seen this pattern too many times: someone learns about multi-agent systems and immediately rebuilds their working single-agent application with five agents coordinating through a graph. The demo looks impressive, and then they deploy it.

However, debugging becomes a nightmare. If you want to figure out which agent failed, or whether it was the input to agent three or the output from agent two, the answer is difficult to get. The logs show five different execution paths and you're trying to trace which one ran. Your single agent used to respond in 3 seconds. Now the multi-agent version takes 12 seconds because of coordination overhead. And the error rate went up because you have five points of failure instead of one.

A single agent with good tools beats a poorly designed multi-agent system. Before you architect something complex, try giving an agent the right tools. Try answering simple questions such as: Can it call APIs? Query databases? Run code? Access documentation? Most problems fit in one agent's context window if you structure the tools well.

The patterns in this chapter solve real problems, but they're not default architectures. You'll know you need multiple agents when you hit actual limitations. Your context window fills up because you're processing thousands of documents and the agent loses track. You need true parallelization because waiting for three sequential 30-second API calls is too slow, and you need specialized expertise that genuinely doesn't fit in one prompt. These situations exist and they're just rarer than you think.

Start with one agent, give it tools, and test it. Only add more agents when one agent clearly can't handle it. Three agents that work reliably beat ten agents that don't.

Summary

You've learned how to build multi-agent systems that actually work in production. You started with the fundamental question of when multiple agents are needed instead of one. Then, you walked through communication techniques that define how agents share information. To recap, sequential communication handles dependencies where one agent needs another's output, parallel communication speeds things up when agents can work independently, and collaborative communication lets agents discuss and negotiate when you need to balance competing concerns. These techniques are your building blocks.

You also explored orchestration patterns that structure entire systems. Supervisor-worker gives you centralized control with one agent coordinating specialized workers. Swarm lets agents hand off control to each other when the path isn't predetermined, whereas Graph provides explicit workflow control with deterministic, auditable paths. Most production systems combine these patterns. Your supervisor might coordinate parallel agents and your graph nodes might be swarms. The key is matching the pattern to your constraints.
