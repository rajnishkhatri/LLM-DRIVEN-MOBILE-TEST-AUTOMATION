Four moves, four outages

You add machines, split and copy data, remember answers, or grow a new system around a live one. Each of those moves fails in a different way.

Audience Engineering & architecture Reading time ~14 min Status Explainer — catalog group B
How to read the colours: Verified mechanic / default Judgment / trade-off / when-not Operator or product decision Uncertain in the source

Load grows. Someone says scale it. The tempting picture is one knob: add replicas, watch a dashboard go green. Capacity is four different jobs — add machines, split and copy data, remember so the origin does not redo the work, or replace a live system without a freeze — and each job fails in a different way.

These Concepts do not share a control loop. An autoscaler resizes compute. A partition key decides where a record lives. A replica family decides what a commit means. A cache decides what the origin may forget. A seam decides which implementation still owns a slice. Treating a hot key as a replica shortage, or a dual-write as a routing problem, is how “scale-out” becomes an outage.

Capacity is not one knob. You add machines, split and copy data, cache, or replace a live system — and each move fails in a different way.

If you remember only that, you can retell the group. Everything below is the reasoning: the verified mechanics, the trade-offs the Concepts name, and the operator decisions they refuse to pretend are defaults.

01

01Add machines — a delayed loop

The first move is the one people mean by “scale.” Scale-up changes the capacity of one unit — VM size, Pod requests, instance class. Process identity, in-memory state, and the local disk stay put. It is rarely automated: Azure’s guidance is that a vertical change is often a redeploy and an outage. Kubernetes VPA is the exception, and by default it recreates Pods. Price/performance of a high-end machine is worse than two mid ones; NUMA, locks, GC, and single-thread ceilings bind before the invoice does.

Scale-out adds identical units behind a balancer or a competing-consumer queue. That is the default cloud autoscaler target. It also buys a distributed system: session affinity, membership, and — for stateful data — the B2 chapter. Spreading work across instances you already have is load balancing (C5), not this move. Horizontally scaling a database or a queue “usually involves data partitioning, which is generally not automated.” That sentence is Azure’s, and it is the cut: this chapter resizes compute; it does not resize shards.

Verified mechanic

Little’s law, with consistent units: L = λW. λ is long-run effective arrival rate, W is mean sojourn (queue + service), L is the concurrency the pool must hold. Netflix states the operational form: Limit = Average RPS × Average Latency. The law does not say that raising λ leaves W unchanged. Near saturation, queueing grows, so L grows faster than λ — the performance cliff.

A design drill in the Concept, not a vendor SLO: λ = 200 /s, W = 100 ms → L = 20 in-flight. Size pools and Cloud Run slots from that identity. One replica at utilization 0.80 is already on the steep part of an M/M/1 curve; extra servers collapse queueing delay, not service time. Do not run this arithmetic on a shard-local hotspot and then add replicas that cannot see the hot key — that is B2.

Verified 2026 defaults that bite: HPA syncs every 15 s; omitted metrics default to 80% average CPU (tighter than Cloud Run’s 60%); scale-up stabilization is 0 s, scale-down 300 s. VPA omitted updateMode is Recreate. KEDA polls every 30 s at zero, then hands 1→N to HPA. Cluster Autoscaler can leave those new Pods Pending for minutes. Cloud Run min instances default 0, max 100 per revision; on-demand from zero pends then 429. HPA and VPA on the same CPU/memory metric fight: one wants more Pods, the other wants bigger Pods.

Watch desiredReplicas vs Ready, the metric vs target, reconstructed λ × W vs pool size, admission rejects, and downstream saturation. A scaler that can take the fleet is a bulkhead (C8) you forgot to put on compute. While the loop lags, shedding (C10) is the answer — Azure says it might be better to throttle.

When not

Do not autoscale when load is flat or known-periodic and a bad scaler costs more than idle. Do not autoscale when the bottleneck is data — one hot key, one primary, one queue partition. Do not autoscale when the bottleneck is in-process (unbounded pool, missing timeout): more replicas multiply the damage. Do not expect an answer faster than provision plus warmup. DaemonSets have no scale subresource. Design for the next 10×, not an imaginary 1000×. There is no generic magic scaling sauce.

02

02Key, then copy, then move

The data plane is one chapter with three jobs that slides collapse into “shard it.” First a record finds a shard. Then a replica family decides what a commit means. Then the key-to-node map moves without taking the cluster. Failover, routing, and rebalance couple those jobs: a node commonly leads some shards and follows others. “The primary is down” is usually “the leaders of shards {S17, S44, S91} lived on the dead node.”

Key — one record, one shard

Shard when data or write throughput no longer fits on one node. Read throughput alone is replica scale. Pick the key for the query you cannot afford to scatter, then write-shard the keys that burn a partition. Key-range is cheap for scans and hot on sequential keys. Hash spreads keys (never hash % N in a growing cluster) and still leaves a celebrity on one shard. Composite is the usual compromise; a monotonic sort key plus a local secondary index pins heat and size.

Verified default

DynamoDB documents 3,000 read units/s and 1,000 write units/s per physical partition. A 20 KB item costs 20 WCU; that partition then accepts 50 writes/s to the key even after adaptive isolation. A design drill at 4,000 writes/s to one logical entity needs 80 random suffixes. Table-level capacity looking “fine” while KeyRangeThroughputExceeded fires is the usual lie. Kafka’s broker default num.partitions = 1 is dev-safe and prod-wrong; more partitions are for consumer parallelism, and they do not split a key already in one log. Cassandra’s current num_tokens = 16 — do not cargo-cult 256 onto a new cluster (neighbour explosion). MongoDB default range 128 MB; CockroachDB splits at 512 MiB and merges below 128 MiB.

A secondary index does not map to one shard. A write that updates two shards is a saga or a distributed transaction (B5), not a partitioning trick. Prefer vertical scale plus read replicas while one machine still holds the data and the write rate. Isolating callers from a bad dependency is a bulkhead, a different unit. Align the key with a cell (E13) if you need a user-slice blast radius rather than a random set of hash ranges.

Copy — name what COMMIT means

Once the record has a shard, the replica family is a durability choice, not a brand name. Streaming (Postgres 17) is async until synchronous_standby_names is set — a client-visible write can vanish on failover. Production “sync” is usually one named standby, the rest async; sync-to-all is the stall already named. Cap the replication slot or unlimited WAL (max_slot_wal_keep_size = -1) fills the disk. Consensus (Raft / Multi-Paxos / Kafka ISR with acks=all and min-ISR 2) commits after a majority persists. Kafka broker defaults — RF 1, min-ISR 1 — acknowledge a write on one disk; the documented production pairing is RF 3 / min-ISR 2 / acks=all, and two brokers down then stops writes. Dynamo (2007, leaderless) and DynamoDB (2012+, Multi-Paxos per partition) are different systems.

A second writer buys local writes through a region or device partition and pays conflicts: uniqueness and “cannot go negative” are not enforceable. Sync multi-leader is single-leader in disguise. The interesting cases are geo, offline devices, and collaboration. DynamoDB global tables are still one leader per partition plus async cross-region — not two writers on the same item in one region. Leaderless has nothing to fail over: wait for w of n. w + r > n makes an up-to-date value likely; it is not linearizability (sloppy quorum, restore-from-backup, clock-skew LWW, a “failed” write that landed somewhere). Cassandra hints last 3 h; gc_grace is 10 days — repair must beat grace or deletes resurrect. Dynamo’s (3, 2, 2) was a shopping-cart bet, not a ledger.

Operator decision

Fully asynchronous replication is a product decision, not an accident of defaults. Name it in the SLO, or name a sync/majority path for the rows that cannot take it. Enabling Kafka unclean election restores writes and drops messages that only lived on the dead ISR — record it; it is not a Tuesday default. Eventual consistency has no bound; session stickiness is the operational substitute.

Move — the map, not more Pods

Rebalancing is expensive. Automation plus false death cascades: one slow node looks dead, ranges move, the rest look dead, more moves. If detection can be wrong, require a commit step. Pre-split for named calendar events. MongoDB balances data size, not QPS (default migrate at a ≥ 384 MB gap). A 100 MB celebrity chunk should not migrate. Cassandra will not drop a silent node from gossip. Disable the balancer during an incident.

Routing must know key → shard → node: any-node forward, a routing tier, or a smart client. C5 may sit in front of coordinators; it must not spray keys at storage. The map wants consensus. Gossip is cheaper and admits two owners. At cutover, in-flight requests to the old owner are not buffered unless the product says so. A stale smart-client ring extends the window (Dynamo’s paper: 10 s refresh — a window, not a default to copy).

03

03Two caches, two keys

Remembering work is the third capacity move, and it is two products that share a miss identity. The application cache (B3) sits next to an origin — database, service, or computed view. The HTTP edge (B8) sits on the public path. The caller, the key space, and the invalidation fleet are different. Do not treat Redis invalidation and Cache-Control as substitutes.

Aside (lazy loading) is the default application pattern because a cache outage degrades to a slower origin — if the origin can take the miss load. That is SRE’s latency cache. A capacity cache cannot: lose a 90% hit rate and you multiply origin load by 10×. Write-through buys read-after-write at write RTT and RAM. Write-behind buys write throughput at the price of a durable-queue problem; a crash loses acknowledged writes. Azure’s order: write the store, then delete the key. Delete-first lets a concurrent reader re-cache the old row.

Stampede after expiry, eviction, flush, or deploy is the same shape. Controls: per-key lock, leases (Facebook’s published 10 s/key token rate on that fleet), XFetch (β = 1), refresh-ahead. OSS Redis defaults to noeviction; Azure and ElastiCache default volatile-lru, which will not evict if you never set TTLs. “Query the origin if the cache is down” is how a partial outage becomes site-wide — pair with a breaker (C1).

At the edge the key is every dimension you vary on. Extra dimensions cut hit rate; an omitted one the origin uses is a correctness bug. Drop tracker query params and signed-URL tokens; validate before lookup. s-maxage is not “CDN max-age” — on Cloudflare it silently disables stale-while-revalidate. A shield is fan-in of misses, not a second CDN. Flush the shield and every POP refills at once; request collapsing and the shield are the stampede controls here.

When not

Do not cache sensitive data in a shared application cache, write-heavy churn whose sync cost exceeds the win, or session state that implies sticky affinity. Do not put write-behind on data you cannot afford to lose. Do not CDN-cache per-user HTML, Set-Cookie / Authorization bodies, or mutating POST. If the origin is already a latency cache — it can take full client QPS — a capacity cache is optional complexity. Small internal services in one region often want B3 next to the origin, not an edge fleet.

04

04Replace while live — write once

The fourth move is not more capacity of the old system. It is leaving a live system without a big-bang date, and emitting facts without writing the database and the broker as two independent commits. Strangler (B4), saga (B5), and outbox/CDC (B7) sit next to the gateway (C6), the inbox (C9), the channel (A2), and the event-driven style (E4). Those siblings own façade placement, exactly-once effects, how a message travels, and whether the architecture is event-driven. This chapter owns the shared villain: dual-write.

A strangler inserts a seam — usually an HTTP façade (C6 owns that physical place). Clients keep one URL. Official sequences start at 0% new / 100% legacy, dark-launch to parity, intercept reads, then writes, then flip SoR after consistency checks. A 50/50 of all URLs is a misconfiguration unless both sides implement every URL. Shadow replays writes. Rollback is a route flip until you drop legacy objects. An ACL translates leftover callers; it is not the façade. Azure’s last phase deletes the seam.

The outbox writes the business row and an outbox row in one local transaction. A relay that is not on the request path publishes after commit. Delivery is at-least-once; every consumer needs an inbox (C9). Two relays: polling, or log-tail CDC. CDC of the business table avoids a forgotten outbox insert and couples consumers to storage. A designed external event (Morling) is the other bet. Cross-service atomicity of several stores is a saga, each step using an outbox — do not restack saga recovery here, and do not retell A2’s channel kinds or E4’s style fight.

A saga is local commits plus semantic undos: either T1…Tn or compensate backward. Locks drop at each commit — that is the isolation hole. The execution log is atomicity. Compensatable steps, then a pivot (card capture), then retryable steps. Transient failure retries; business failure compensates; timeout-unknown on a capture is neither — reuse a C9 key, then a human. Retry and timeout knobs stay on C2 and C7.

When not

Strangler is brownfield. Greenfield designs the destination style and still makes today’s system strangleable. A tiny system is cheaper to rewrite. Saga is the wrong tool when one database already owns the rows, when intermediate reads are intolerable, or when retries alone suffice. Outbox is the wrong tool when there is no other consumer, when you wanted the broker to be the system of record (that is event sourcing, E12), or when you need a warehouse mirror of tables rather than a domain event.

05

05A helper next to the replica

Sidecar (B6) is not a fifth way to add capacity and not a runtime style. A sidecar is a second process scheduled with the application instance and dying with it — on Kubernetes, a second container in the same Pod: shared network namespace, optional shared volumes, independent image, not independently scaled. That is placement. It does not turn a monolith into microservices. It does not create a cell. The breaker, retry, timeout, and concurrency limit that often run inside a mesh proxy stay on those cards.

Verified injector numbers are scheduling hints, not a workload profile. Istio chart defaults: 100m / 128Mi request, 2000m / 1024Mi limit. Set all four resource annotations or a partial apply wipes the rest and can leave CPU unlimited. Native sidecars (restartPolicy: Always on init) are GA in Kubernetes 1.33 and fix Job completion and startup order. A down injector is not a no-op: new Pods come up unmeshed. Shared fate is the opposite of a bulkhead — proxy OOM isolates the app, or a live app behind a dead proxy black-holes stolen traffic.

When not

Prefer a library when you own one language and latency is critical. Prefer a node proxy or ambient ztunnel when per-replica Envoy cost dominates and L4 is enough. Prefer a separate Deployment when the helper must scale independently. Prefer the gateway for north-south composition. Prefer hexagonal or microkernel when the “adapter” you want is a domain port or a plugin the app already loads.

07What the Concepts refused to invent

These items are explicitly unfetched, unreconciled, or labelled not-an-SLA in the Group B Concepts. They stay fenced so nobody fills them in from a blog.

◆ Uncertain · replica / client defaults

Kafka 4.x producer acks default was not re-verified per language — the broker min.insync.replicas = 1 is verified. MongoDB replica-set election timeout and Cockroach follower-read staleness were not fetched. Cassandra 5 driver/session consistency-level defaults were not re-verified; treat historical “default ONE” as cqlsh, not universal. Set the level in the session.

◆ Uncertain · clocks and thresholds

DynamoDB global-table conflict clock (HLC vs wall vs per-item version) was not pinned this pass. MySQL Group Replication / EDB multi-primary knobs were not fetched. Citus / Vitess / Yugabyte tablet and default-shard thresholds were not fetched — empty cells are not defaults. No controlled measurement of a rebalance-induced cascade beyond the qualitative warning; do not invent a numeric cascade threshold.

◆ Uncertain · placement resources

Envoy the product has no sidecar CPU/memory default; blogs that say “100m” are repeating Istio. Dapr resource defaults were not fetched. The Istio native-sidecar opt-out annotation string was not reconciled — look up the live reference. Istio’s ambient vs sidecar latency figures are Istio-stated with no benchmark method on the page — not a universal SLA. Envoy RequestMirrorPolicy omitted-fraction default is not stated; set the fraction explicitly.

◆ Uncertain · telemetry

No stable OpenTelemetry application-cache semantic convention as of the Concept’s fetch date. Redis spans today are database spans, not cache spans. No CDN-specific OTel convention was found. No official saga convention — join keys in that card are a design rule, not a vendor schema.

Add machines, or split and copy, or remember, or replace while live. Name the move. Then name the outage that move actually produces — before the dashboard goes green.
