From function to tool

Before you build agents, let's see how to take a simple python function and turn it into something the Agent can use. Let's say you're building an agent to help manage your development workflow. You already have a Python function that checks if your staging server is running:

import requests
def check_server_status(server_url):
    """Check if a server is responding."""
    try:
        response = requests.get(server_url, timeout=5)
        return f"Server is up. Status code: {response.status_code}"
    except requests.exceptions.RequestException:
        return "Server is down or unreachable"
# You use it like this:
status = check_server_status("https://staging.myapp.com")
print(status)  # "Server is up. Status code: 200"
This function works when you call it directly. Now you want your agent to use it. You ask the agent, Is the staging server running?

The agent responds:

I don't have the ability to check server status. You can use curl or ping to check if your server is responding.
Right now, your agent doesn't know that you have a function in a Python file somewhere that performs this task. The agent can't magically discover the check_server_status function and use it.

This is where function calling (also called tool use) comes in. To make this function available to your agent, add three things: the @tool decorator, type hints, and a proper docstring. The @tool decorator tells Strands to make this function available to agents. Type hints tell the agent what data types to expect. The docstring describes what the function does so the agent knows when to use it:

from strands import tool
import requests
@tool  # Decorator
def check_server_status(server_url: str) -> str:  # Type hints
    """Check if a server is responding by making an HTTP request.
    Args:
        server_url: The URL of the server to check  # Docstring
    Returns:
        A message indicating whether the server is up or down
    """
    try:
        response = requests.get(server_url, timeout=5)
        return f"Server is up. Status code: {response.status_code}"
    except requests.exceptions.RequestException:
        return "Server is down or unreachable"
The function makes an HTTP GET request to the server URL with a 5-second timeout. If the server responds, it returns the status code (like 200 for success). If the request fails (server is down, network error, or timeout), it catches the exception and returns an error message.

Now give this function to the agent:

from strands import Agent
agent = Agent(tools=[check_server_status])
response = agent("Is the staging server running?")
The agent can now call this function. When someone asks about server status, the agent calls check_server_status with the right URL and gets the actual result back.

This pattern works for any function. Add @tool, give it to your Agent, and the agent can now execute it.

When one tool isn't enough

So, you just looked at how you can go from a function to a tool. But let's say you have multiple tools and you want to use with your agent. Suppose you are building a sales assistant, where you ask the agent to pull last quarter's sales data and email a summary to the team.

That's not one task, but three:

Query the database for sales data.
Analyze the numbers.
Send an email.
You can create three specialized tools, with the following code:

from strands import Agent, tool
@tool
def get_sales_data(quarter: str) -> dict:
    """Retrieve sales data for a specific quarter."""
    return {"revenue": 1250000, "deals": 47, "quarter": quarter}
@tool
def analyze_sales(revenue: int, deals: int, quarter: str) -> str:
    """Calculate key metrics from sales data."""
    avg_deal = revenue / deals
    return f"Q{quarter}: ${revenue:,} revenue, {deals} deals, ${avg_deal:,.0f} avg deal size"
@tool
def send_email(to: str, subject: str, body: str) -> str:
    """Send an email message."""
    return f"Email sent to {to}"
agent = Agent(tools=[get_sales_data, analyze_sales, send_email])
Each tool handles one specific job. The database tool only queries data. The analysis tool only crunches numbers. The email tool only sends messages. This way, you can reuse them in different combinations. Need to analyze data from a different source? Use the same analysis tool. Need to email something else? Use the same email tool. The agent will figure out which tools to use and in what order.

Build focused, single-purpose tools. Avoid the temptation to create one mega-tool that does everything. It becomes harder to maintain, harder for the agent to reason about, and impossible to reuse in other contexts.

Now when you ask the original question:

response = agent("Pull last quarter's sales data and email a summary to the team")
The agent:

Recognizes it needs sales data and calls get_sales_data("Q4")
Gets the data back, then extracts the values and calls analyze_sales(revenue=1250000, deals=47, quarter="Q4")
Gets the summary and calls send_email("team@company.com", "Q4 Sales", summary)
You didn't program that sequence and nor did you write if user asks for sales summary, then do steps 1, 2, 3. The agent figured it out by analyzing the request, selecting the right tools, and executing them in the right order.

Building your first tool-enabled agent

Let's create something you can actually use, an agent that helps you calculate tips at restaurants. You know the situation, when you're at dinner, the bill arrives, and you need to figure out the tip and split it among friends. Let's build an agent that does this for you:

from strands import Agent, tool
# Step 1: Create a tool (just a Python function with @tool)
@tool
def calculate_tip(bill_amount: float, tip_percentage: float, num_people: int = 1) -> dict:
    """Calculate tip and split the bill among people.

    Args:
        bill_amount: Total bill amount in dollars
        tip_percentage: Tip percentage (e.g., 15, 18, 20)
        num_people: Number of people splitting the bill (default: 1)
    """
    tip = bill_amount * (tip_percentage / 100)
    total = bill_amount + tip
    per_person = total / num_people
    return {
        "bill": bill_amount,
        "tip": round(tip, 2),
        "total": round(total, 2),
        "per_person": round(per_person, 2)
    }
# Step 2: Create an agent and give it the tool
agent = Agent(
    model="us.anthropic.claude-sonnet-4-20250514-v1:0",
    tools=[calculate_tip]
)
# Step 3: Ask the agent a question
response = agent("The bill is $85. What's a 20% tip, and how much does each person pay if we're splitting it 4 ways?")
print(response.message['content'][0]['text'])

The agent figured all of that out. We just described what our tool does (through the function name, parameters, and docstring), and the agent handled the rest.

Give it to an agent (add it to the tools list)

Whether you're building a tool that calculates tips or one that checks server status, you follow the same approach. The only difference is what happens inside your tool's implementation.

The agent just needs to understand three things about your tool: what it does, what information it needs, and what it gives back. We communicate all of that through your function's name, parameters, and docstring. The agent reads those, figures out when your tool is useful, and calls it automatically. When you start a new software project, do you write your own HTTP library? Your own JSON parser? Of course not. You use packages that others built. Same goes for agent tools. Why spend three days building a web scraper when someone already solved that problem?

The Strands ecosystem gives you a head start. Instead of spending days building a file reader or AWS integration, grab pre-built tools and start building. This matters because the agents you'll create in later chapters use these same tools, just combined in more interesting combinations.

Building custom tools

When community tools don't fit your needs, you build custom tools. Maybe you're integrating with an internal API that only your company uses. Maybe you need to query a proprietary database with specific business logic. Or perhaps you're building something entirely new that no existing tool covers.

Pre-built tools can't do these things. That's when you build your own. Earlier in the chapter, we built a very simple custom Python tool using the @tool decorator. But let us now take a different real-world example.

Let's say you run an online store. Customers ask, Is product X in stock all the time? You need a tool that checks your inventory database:

from strands import tool
@tool
def check_inventory(product_id: str) -> str:
    """Check if a product is in stock.

    Args:
        product_id: The product ID to check (e.g., "PROD-123")
    """
    # This is where you'd query your actual database
    # For now, let's simulate it
    inventory = {
        "PROD-123": 15,
        "PROD-456": 0,
        "PROD-789": 8
    }
    quantity = inventory.get(product_id, 0)
    if quantity > 0:
        return f"Product {product_id} is in stock. We have {quantity} units available."
    else:
        return f"Product {product_id} is currently out of stock."
We've created a function called check_inventory that takes a product ID and returns stock information. The @tool decorator makes this function available to agents. Without it, this would just be regular Python code.

The docstring explains what the tool does. When a user asks, Is PROD‑123 in stock?, the agent reads this description and recognizes that check_inventory handles this request. The Args: section tells the agent what parameter to extract from the user's question.

Inside the function, we've simulated a database with a dictionary. In production environment, you'd replace this with actual database queries or API calls to your inventory system. The agent calls the function with a product ID and uses the returned message in its response. Once defined, you can ask about inventory any way that feels natural:

from strands import Agent
agent = Agent(tools=[check_inventory])
# All of these work:
agent("Is PROD-123 in stock?")
agent("Do we have PROD-456 available?")
agent("Check inventory for PROD-789")
agent("Can I order PROD-123 right now?")
Each question is phrased differently, but the agent recognizes them all as inventory checks. In traditional chatbot development, you would write regex patterns or intent classifiers to handle these variations. You would map in stock, available, and can I order to the same intent. You would extract the product ID from different sentence structures.

Here, we skipped all that. You wrote a function with a clear description, and the agent figured out when to call it. The language model handles the intent recognition and parameter extraction.

When simple tools aren't enough

You've been building tools with the @tool decorator. Your agent has five tools: check stock, update stock, get supplier info, track shipments, and generate reports. Then one day you deploy your inventory agent to production. Within an hour, your database administrator sends you a Slack message: Why is your agent opening 50 database connections per minute?

You check the logs and find each tool opens its own database connection. When the agent processes a single request, it might call three or four of these tools. That's three or four separate connections for one user request. Multiply that by dozens of concurrent users, and suddenly your database server is drowning in connections.

The @tool decorator works perfectly for simple cases. But as your agents grow more sophisticated, you'll hit situations where you need more control. Let's look at three scenarios where the simple approach shows its limits and what to do about them.

The database connection problem

Back to that Slack message from your database administrator. Let's look at what your code is doing

from strands import tool
@tool
def check_stock(product_id: str) -> str:
    """Check product stock."""
    db = connect_to_database()
    result = db.query("SELECT quantity FROM inventory WHERE id = %s", (product_id,))
    db.close()
    return result
@tool
def update_stock(product_id: str, quantity: int) -> str:
    """Update product stock."""
    db = connect_to_database()
    db.execute("UPDATE inventory SET quantity = %s WHERE id = %s", (quantity, product_id))
    db.close()
    return f"Updated {product_id} to {quantity} units"
It works, but there's a problem. Every time the agent calls a tool, your database server logs show a new connection being opened and closed. Five tools mean five separate connections per request cycle. When you have dozens of users hitting the agent simultaneously, those connections add up fast.

Opening database connections is expensive. Each connection takes time to establish (typically 50-100 milliseconds), uses memory on the database server, and most databases have hard limits on concurrent connections. MySQL defaults to 151 connections. PostgreSQL defaults to 100. Hit that limit and your agent starts failing with too many connections error.

Here's what you would need to do: connect once when the agent starts, then share that connection across all your tools. But the decorator approach doesn't give us a way to do that. Each function is independent, with no way to share state between them.

The solution is to group related tools inside a class:

from strands import tool
class InventoryTools:
    def __init__(self):
        self.db = connect_to_database()  # Replace with your actual database connection
    @tool
    def check_stock(self, product_id: str) -> str:
        """Check product stock."""
        return self.db.query(f"SELECT quantity FROM inventory WHERE id='{product_id}'")
    @tool
    def update_stock(self, product_id: str, quantity: int) -> str:
        """Update product stock."""
        self.db.execute(f"UPDATE inventory SET quantity={quantity} WHERE id='{product_id}'")
        return f"Updated {product_id} to {quantity} units"
Now you create one instance of the class and pass its methods to your agent:

inventory = InventoryTools()  # Database connection happens here
agent = Agent(tools=[inventory.check_stock, inventory.update_stock])
All your tools share the same database connection through self.db. So, we'll have one connection and five tools, making the implementation both faster and cleaner.

This pattern works for any shared resource such as, API clients that maintain connection pools, file handles for reading large datasets, cache connections to Redis or Memcached or authentication tokens that need to be refreshed periodically.

Slow warehouse checks

Now two days later, your product manager messages you: Users are complaining the agent is too slow. It takes 8 seconds to check if you can fulfill an order. That's way too long.

You look at the code. When a customer asks Can you ship 100 units of PROD‑123?, your agent needs to check inventory across three warehouses. Each warehouse has its own API, so you built a check_warehouse_inventory tool that takes a warehouse parameter. The agent calls it three times, one after another:

warehouse_a = check_warehouse_inventory("PROD-123", "warehouse_a")  # 2 seconds
warehouse_b = check_warehouse_inventory("PROD-123", "warehouse_b")  # 2 seconds
warehouse_c = check_warehouse_inventory("PROD-123", "warehouse_c")  # 2 seconds
total = combine_inventory(warehouse_a, warehouse_b, warehouse_c)    # 2 seconds
# Total: 8 seconds
The total time it took is 8 seconds. Your users are staring at a loading spinner for eight seconds. You check your analytics and see users abandoning their carts before the agent even responds.

However, these three warehouse API calls don't depend on each other. Warehouse B doesn't need to wait for Warehouse A's response. They're completely independent operations and could all happen at the same time.

When you mark a function as async, Python's event loop can pause it at await points while waiting for I/O operations (like API responses) and switch to other async work on the same thread. Multiple async functions can run concurrently, all making progress together through cooperative multitasking.

Here's how you can fix the warehouse check tool:

import asyncio
from strands import Agent, tool
@tool
async def check_warehouse_inventory(product_id: str, warehouse: str) -> int:
    """Check inventory at a specific warehouse."""
    async with httpx.AsyncClient() as client:
        response = await client.get(
            f"https://api.warehouse-{warehouse}.com/inventory/{product_id}"
        )
        return response.json()["quantity"]
async def main():
    agent = Agent(tools=[check_warehouse_inventory])
    response = await agent.invoke_async(
        "Can we ship 100 units of PROD-123? Check all warehouses."
    )
    print(response.message['content'][0]['text'])
asyncio.run(main())
When the agent needs to check all three warehouses, Strands automatically runs them in parallel. All three API calls happen simultaneously. Time it takes is 2 seconds instead of 6 seconds for the warehouse checks, plus 2 seconds to combine the results. So total time is 4 seconds instead of 8.

The async and await keywords tell Python this function can pause and resume. When check_warehouse_inventory hits the await on the API call, Python doesn't sit there waiting. It switches to another warehouse check that's ready to run. All three calls progress together, like those three restaurant orders being prepared simultaneously.

Not every tool benefits from async execution. If a tool runs almost instantly (say, under 100 milliseconds) or performs pure calculations without external calls, async adds unnecessary complexity without measurable gains. It's usually best to start with regular tools and add async support when you need speed.

Choosing your approach

Start with the decorator. It's simple and handles most cases. Build your tool, test it, deploy it, and see what happens. If you run into database connection problems, group your tools in a class to share resources. If external API calls are slow, make them async so they run concurrently. Let real problems guide you, not theoretical ones.

One more thing, if you need to enforce strict validation rules on tool inputs (like specific formats or allowed values), you can define explicit schemas using TOOL_SPEC. We won't cover that here since it's for advanced use-cases, but if you would like to go deeper into it, you can go through the documentation:https://strandsagents.com/latest/documentation/docs/user-guide/concepts/tools/custom-tools/.

In addition, the GitHub repository (https://github.com/strands-agents/samples/tree/main/python/01-learn/02-tools-and-mcp) contains detailed examples of both approaches with complete, runnable code.

Now that you know how to build custom tools, if you want to experiment quickly without writing all the setup code, there's an even faster way to get started.

Quick start with Strands Agent Builder

By now, you've learned quite a bit about building agents with tools. You've seen how to create custom tools with the @tool decorator, use pre-built tools from the Strands ecosystem, connect to MCP servers for external capabilities, and even gotten a glimpse into building your own MCP servers.

But you might be thinking: This is powerful, but setting up all the code, imports, and configurations takes time. When I'm learning or want to test an idea quickly, is there a faster way to experiment?

Absolutely. Let's look at Agent Builder, which is a command tool designed specifically for rapid prototyping and learning.

Agent Builder is a command-line tool that lets you build agents by describing what you want in plain English. Instead of writing code, imports, and configurations, you just say what you want and Agent Builder creates it. Think of it as training wheels for building agents; you get to experiment and learn without worrying about setup.

Let's see Agent Builder in action. Install it and build your first agent:

# Install Agent Builder
pipx install strands-agents-builder

# Start interactive mode
strands
Once it starts, you'll see a prompt. Try asking:

Build a tool that converts Celsius to Fahrenheit.
Agent Builder will:

Create the conversion tool
Test it with example values (for example, What's 100°C in Fahrenheit?)
Show you the result: 100°C is 212°F
Let you try more conversions
You just built a tool by describing what you want. No code, no imports, no setup.

Agent Builder operates in two modes:

Interactive mode: Run strands and have a conversation with the builder. Ask it to create tools, test agents, or explain concepts.
Command mode: Give it specific instructions directly:
strands "Build a tool that monitors API rate limits across all services and alerts at 80% capacity"
Agent Builder comes with powerful integrated tools that let you build sophisticated agents immediately:

Data processing agents: Use the calculator, Python REPL, and file editor tools to analyze data
Web-connected agents: Use HTTP request and Slack tools to interact with APIs and services
AWS-integrated agents: Use the use_aws tool to manage cloud resources
Multi-agent systems: Use the swarm and workflow tools to coordinate multiple agents
Creative agents: Use image generation and video creation tools powered by Amazon Bedrock
When you use Agent Builder, here's what's happening under the hood:

Agent Builder registers its built-in tools with the Strands framework
It sets up a model (Claude Sonnet 4, at the time of writing) with optimized settings for tool use
Your requests go to the model, which decides which tools to call
The framework executes tools and returns results to the model
The model synthesizes tool outputs into natural language responses
This is the same pattern you'll use when building agents manually. Agent Builder just handles the setup for you.

Agent Builder runs interactively and doesn't automatically save generated tool code to files. If you want to persist tools across sessions, use the ‑‑kb flag with an Amazon Bedrock Knowledge Base ID, which lets you store and retrieve tools between sessions. Alternatively, you can copy the generated code from the session output into your own Python files.

If you want to dive deeper, the Agent Builder GitHub repository (https://github.com/strands-agents/agent-builder) includes full documentation and setup instructions.

Agent Builder is perfect for learning and experimentation, but as you build production applications, you'll want the full control and customization that come with writing your own agents using the patterns we've covered in this chapter.

Building agents on LangChain

We've spent this chapter building agents with Strands. If you've searched for how to build AI agents, you've probably come across LangChain. It's been around longer and has a large community, so it's worth mentioning.

Both frameworks do the same core thing: turn Python functions into tools and let agents use them. The difference is in how they approach it. Strands uses a model-driven approach where you write minimal code and let the LLM figure out the workflow. LangChain gives you more explicit control over how agents execute tasks, which means more setup code but also more customization options.

For this chapter, we're using Strands because it's simpler to learn and integrates naturally with AWS services like Bedrock, Lambda, and S3. If you're working in a different environment or need the flexibility that comes with LangChain's larger ecosystem, check out their documentation at https://docs.langchain.com/oss/python/langchain/agents.
