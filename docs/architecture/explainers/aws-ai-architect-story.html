Part I · One call

IOne call

Every architecture in this story reduces to one move: a stateless request crosses a deterministic boundary, a model reasons about it, and a response comes back through the same boundary. Get this single call right and the rest of the page is repetition. Get it wrong and no framework will save you.

Start with what the call is. The API stores nothing between requests: your application keeps the full message list and resends the entire history every turn, roles strictly alternating. And a Claude model will refuse a bare model id on demand throughput — you route through an inference profile, a routing name with a region prefix: us., eu., jp., apac., au., or global., with 4.6+/5-generation ids dateless (global.anthropic.claude-opus-5). aws-claude bundle, "Bedrock Converse API" Concept · AWS Bedrock cross-region inference guide, as of 2026-08-27

Around that one call sit three choices worth slowing down for: which door the call goes through, which model answers it, and how hard the model is allowed to think.

The door. Bedrock serves Claude through two endpoints, and platform services hang on only one of them. bedrock-runtime carries Converse/ConverseStream, InvokeModel, an Anthropic-native Messages path, and two OpenAI-compatible APIs — and it is where Guardrails, Knowledge Bases, Agents, and Flows attach. The bedrock-mantle endpoint serves Claude through the first-party Messages API with standard SSE and its own separate, burndown-free quota pools — and nothing platform-side attaches to it. Anthropic labels the Converse integration "legacy (Opus 4.6 and earlier)"; Converse still works with every current Claude model as the AWS-native multi-model abstraction, but the attach-point asymmetry is what makes the endpoint a real architecture decision rather than a config value. AWS Bedrock userguide, "APIs" · Anthropic "Claude in Amazon Bedrock" docs, as of 2026-08-27

The model. Claude on Bedrock is a four-rung ladder with published list prices per million tokens in and out: Haiku 4.5 at $1/$5, Sonnet 5 at $2/$10, Opus 5 at $5/$25, Fable 5 at $10/$50 unverified — check the current pricing page. Ids are dateless and pinned, context is one million tokens at standard pricing on 4.6+/5-generation models, and max output is 128K. Two traps for cost models: the 4.7+ tokenizer emits roughly 30% more tokens for the same text, and geographic routing adds 10% over global on Sonnet 4.5 and later. AWS Bedrock model cards · Anthropic pricing page, as of 2026-08-27 — per-MTok figures are Anthropic list prices; the Bedrock pricing page is JS-rendered and was not directly confirmable

The thinking. Current Claude models think adaptively — the model decides whether to reason before answering and how much — and you steer that with one knob, output_config.effort, from low to max. There is no budget to tune and no switch to flip: hand-set thinking budgets are a retired control (they are rejected with an HTTP 400 on 4.7+ models), and on Fable 5 thinking cannot be disabled at all. Which effort level to pin is an evaluation question, and Part VII returns to it. Anthropic adaptive-thinking and effort docs, as of 2026-08-27

Two more facts complete the one-call picture. Quota math has a shape worth memorizing: on bedrock-runtime, one output token burns ten quota tokens for Opus 5/Sonnet 5, max_tokens is deducted from your tokens-per-minute allowance at request start, and cache reads burn nothing — so an oversized max_tokens throttles concurrency even though billing stays honest. And one habit to unlearn if you knew Claude a generation ago: seeding the assistant turn ("prefill") is rejected outright today — Part II shows the pattern that took its place. AWS Bedrock quotas and token-burndown guide, as of 2026-08-27

Finally, Fable 5 changes the response contract itself: safety classifiers can end a generation with stop_reason: "refusal" on a perfectly healthy HTTP 200, sampling is pinned (temperature fixed at 1.0), and the account must opt into provider data sharing before the model is available at all. Refusal handling is a designed response path, not an error branch — and the data-sharing requirement couples model choice to retention policy, a coupling the decision map prices out. AWS Bedrock model card for Claude Fable 5, as of 2026-08-27

Envelope beat · before the next escalation

Before any loop exists, the envelope owns: the IAM identity making the call, the endpoint and routing profile it rides, quota and burndown headroom, refusal as a designed response path, and holding model + effort constant inside any cached conversation. None of these are model decisions. All of them are architecture.

Part II · The loop

IIThe loop

Give the single call a set of tool schemas and something remarkable happens: the model stops answering and starts asking. Everything else in this story — servers, agents, platforms — is this one loop at increasing altitude.

The contract is small enough to hold in your head. You send messages plus tool definitions; the model replies with stop_reason set to tool_use and one or more tool_use blocks naming a tool and its arguments; your application executes the real call and returns a tool_result block; the model reads the result and either asks again or finishes with end_turn. That stop_reason field is the hinge of the whole architecture — it is the loop condition inside every framework this page will name. aws-claude bundle, "Tool use on Bedrock" Concept · Anthropic tool-use overview, as of 2026-08-27

Two details of the contract carry more weight than they look. First, a failed tool goes back to the model as a result with status: error, not as a raised exception — the model reads the error text and retries with corrected arguments. Second, the division of labor is absolute: the model only ever proposes a call; your code decides whether and how it runs. That split is where every governance mechanism in Parts VI and VIII will attach.

One thing you no longer have to engineer: when the calls are independent, current models issue them in parallel by default — no wrapper tool required.

Structured output rides the loop

Sooner or later every integration needs the model to return data, not prose. The reliable way to get it is already in front of you: define a tool whose input schema is the output contract, force it with toolChoice, and read the arguments the model fills in. The schema does the formatting; the loop's own contract does the delivery. Two companions round it out — a schema stated in the system prompt with a validate-and-retry step, and, where available, the platform's structured-output mode. Check availability before assuming that last one: structured outputs are not yet on Bedrock for Opus 5/Sonnet 5, a feature-parity gap against the first-party API worth an explicit note in any design that assumes it. Anthropic Opus 5 / Sonnet 5 migration guides · AWS Bedrock model cards, as of 2026-08-27

If you learned a different trick — seeding the assistant turn with an opening delimiter and stopping on the closing one — retire it: prefilling the assistant message returns HTTP 400 on Sonnet 4.6+, Opus 4.7+, and the whole Claude 5 generation. The tool-schema extractor wins for a structural reason, not a fashionable one: a pattern that lives inside the loop's contract outlives any pattern that lives beside it. That asymmetry is this page's thesis in miniature.

Envelope beat · before the next escalation

The loop's envelope owns tool execution end to end: schema validation before anything runs, try/except folded into status: error results, retry ceilings, and the allowlist of what the model may call at all. The model proposes; the envelope executes and validates. Hold that line — every later Part raises the stakes on it.

Part III · The loop with servers

IIIThe loop with servers

The loop never asked who wrote the tools. MCP answers that question: authoring and execution move onto a server that wraps the outside service, and your client rents the capability. The loop itself does not change — only the ownership does.

One sentence does most of the design work here. Tools are model-controlled — capabilities the model chooses to invoke. Resources are application-controlled — data your app injects into context. Prompts are user-controlled — canned workflows a person starts. Whatever you are about to build for an agent, this three-way split tells you which of the three it is, and that decides who gets to trigger it. aws-claude bundle, "Model Context Protocol" Concept · modelcontextprotocol.io server concepts, as of 2026-08-27

A rule that is often misstated: per-tool-call user approval is host policy, not an MCP protocol mandate. The spec puts approval exactly where the control split implies — the host decides how much friction model-controlled tools get.

The protocol itself is worth dating precisely, because its current revision (2026-07-28) settled the wire contract an enterprise server should target. MCP is stateless: no handshake, no session header — anything a server must remember across calls rides in server-minted handles passed back as tool arguments. Streamable HTTP is the transport. When a server needs something from the client mid-request, it uses Multi Round-Trip Requests rather than opening its own channel. Auth is OAuth 2.1 with Client ID Metadata Documents. Three older client features — Roots, Sampling, and Logging — are formally deprecated on a twelve-month clock; a server built today does not build on them, and if yours still relies on the old stateful handshake, session ids are gone. MCP specification 2026-07-28 changelog and release post, as of 2026-08-27

Governance matches the spec's ambition: MCP lives under LF Projects, LLC — vendor-neutral, changes through a formal SEP process, deprecations on a published lifecycle. For an architect this is the difference between betting on a vendor's SDK and betting on an infrastructure standard. modelcontextprotocol.io community governance pages, as of 2026-08-27

Envelope beat · before the next escalation

Once tools live on servers, the envelope owns the seam: server identity and OAuth 2.1 auth, allowlisting at whatever gateway fronts the servers, and the discipline of treating every tool result as untrusted input to the next model turn. A server is a supply chain now — vet it like one.

Part IV · The loop left running

IVThe loop left running

An agent is not a new architecture. It is the tool loop from Part II with the exit condition moved: instead of stopping after one answer, it runs until the goal is met or the budget is gone. Agent = loop + state. Everything agents add — memory, frameworks, platforms — is machinery for the state half.

That definition is not this page's coinage — it is how Strands documents its agent loop: reason, select a tool, execute, accumulate context, recurse until a terminal stop reason. aws-claude bundle, "Agents and computer use" Concept · Strands agent-loop docs, as of 2026-08-27

Strands is the code-first frame for that loop on AWS: an agent is a model, a list of tools, and a prompt; @tool turns a typed, documented Python function into a schema; the loop is the SDK's job. It hit 1.0 in mid-2025, is production/stable in the 1.5x series, and — the detail that matters for the next two Parts — it powers AWS's own managed Harness under the hood. Learning Strands is learning the substrate. Strands Agents SDK docs and PyPI, as of 2026-08-27

State splits on one line: short-term memory is the session — events in order, the context window, the rolling buffer; long-term memory is what survives the session — extracted preferences, facts, and summaries. AgentCore Memory ships that split as a service, with actor- and session-scoped namespaces and asynchronous extraction strategies. And context management inside the window is productized too — server-side compaction, context editing, a client-side memory tool, or a fresh-context restart that rediscovers state from the filesystem. Choose among them deliberately; hand-rolled summarization is the one option with nothing left to recommend it. aws-ai bundle, "Agent Memory" chapter · AgentCore Memory docs · Anthropic context-engineering post, as of 2026-08-27

Envelope beat · before the next escalation

A running loop needs the envelope to own its state: session and actor isolation, memory scoped per user, iteration and budget ceilings, and durable state a fresh session can rediscover. The loop reasons; the envelope remembers — and decides who is allowed to remember what.

Part V · Many loops

VMany loops

The moment one agent works, someone proposes five. The right answer is restraint: multi-agent is an escalation you earn with evidence — context exhaustion, true parallelism, or genuinely disjoint expertise — not a maturity milestone.

Start simple, escalate on evidence. A single agent with well-designed tools beats a poorly designed multi-agent system, and a rebuild exercise in the source notes made the cost concrete: the same task, five agents instead of one, four times the latency. There is a twist: the restraint has to be prompted in — current frontier models over-delegate to subagents by default and need damping, not encouragement. aws-ai bundle, "Advanced Agent Architecture Patterns" chapter · Anthropic prompting best practices, as of 2026-08-27

When the evidence does arrive, the shipped vocabulary is five Strands primitives — agents-as-tools, handoffs, swarm, graph, and workflow — plus A2A for agents that cross framework or organization boundaries. One naming note: a "supervisor" is not a separate primitive; it is what agents-as-tools builds. The real design axis is who decides the path: a supervisor agent decides (agents-as-tools), the agents themselves decide (swarm), or you decide, in code (graph). Auditable workflows belong on the graph — the model reasons inside nodes but never chooses the route. Strands multi-agent pattern docs · aws-ai bundle, "Advanced Agent Architecture Patterns" chapter, as of 2026-08-27

Once loops talk to each other, the protocol question stops being singular — four layers cover the seams. MCP connects an agent to its tools. A2A v1.0 — Linux Foundation governed, with signed agent cards — connects agents to each other across vendors and organizations. AG-UI connects an agent to its frontend. x402/MPP (still in preview) handle agent payments. And AgentCore Gateway fronts the stack as a managed choke point: ingress and egress auth, semantic tool search, even model routing — one place where policy can see every call. AgentCore developer guide · Linux Foundation A2A announcements, as of 2026-08-27

Envelope beat · before the next escalation

With many loops, the envelope owns the topology: the DAG whenever compliance needs an auditable route, handoff and iteration ceilings when it does not, and cross-agent trust — signed agent cards, per-agent identity, one gateway where policy sees every call before it happens.

Part VI · The loop as infrastructure

VIThe loop as infrastructure

Follow the loop far enough and it stops being your code. AgentCore is the tool loop as a managed platform — the envelope of every previous Part, sold as services. Part IV's definition of an agent is now, literally, an AWS product.

The platform decomposes the way this page has been decomposing all along. The loop runs on Runtime — per-session microVMs, sessions to 8 hours, billed on active CPU only — or on Runtime Instances (managed EC2, 14-day sessions, GPU families) when it outgrows that. Harness is the loop itself as configuration: model + tools + instructions, no deployment, powered by Strands underneath and able to export back to Strands code when you outgrow config. Around them: Gateway (tools), Identity (a KMS-encrypted token vault instead of secrets in context), Memory, Policy, Evaluations, Observability — each adoptable independently, framework- and model-agnostic by design. AgentCore developer guide and GA announcements, as of 2026-08-27

One naming trap waits in older material. AWS's earlier managed-agents product — console-configured "Bedrock Agents", with action groups and prompt overrides — is now Amazon Bedrock Agents Classic: closed to new customers since 2026-07-30, model catalog frozen, existing agents still running with no end-of-life date. New designs start on AgentCore, and AWS's own migration path lands on Harness (action groups become Gateway-wrapped MCP tools) or code-defined agents on Runtime. If a system you inherit still sits on Classic, migrating is a scheduled architecture decision, not hygiene — the frozen model catalog is the clock. AWS Bedrock Agents Classic maintenance-mode documentation, as of 2026-08-27

Governance on the platform splits along the line Part II drew. Guardrails govern what the agent says — content filters, denied topics, PII, grounding checks, org-enforced and non-bypassable since the Organizations policy type landed, with Automated Reasoning checks for formally verifiable claims. Cedar-based Policy governs what the agent does — default-deny authorization evaluated on every tool call at the Gateway, outside the reasoning loop, immune to prompt persuasion. The distinction is not advice; the platform enforces it as two separate services. aws-ai bundle, "Evaluation, Observability, and AI Governance" chapter · AWS Security Blog on Cedar in AgentCore, as of 2026-08-27

Observability is OTel-shaped and CloudWatch-landed: gen_ai semantic-convention spans, GenAI observability dashboards, session → trace → span as one substrate for debugging, evaluation, and audit alike. One governance gap ships in the default configuration: model invocation logging is off, per account, per Region — the prompt/completion audit trail exists only if you turn it on. CloudWatch GenAI observability GA notes · AWS Bedrock invocation-logging guide, as of 2026-08-27

Envelope beat · before the next escalation

Here the envelope stops being your code and becomes the platform: microVM isolation per session, a token vault instead of credentials in context, default-deny Cedar at the gateway. One duty the platform will not take from you: invocation logging is off by default — turn it on, in every account, and make the audit trail exist.

Part VII · The eval decides

VIIThe eval decides

Every Part so far ended with the envelope owning something. This Part is about how the envelope knows. The rule is short enough to memorize: no capability knob gets turned on taste — the eval decides.

An eval is a pipeline: dataset → run → grade → average, with three grader families — code, model, human. The working vocabulary: a task is an input plus an environment plus success criteria; a trial is one run — you run several, because outputs vary; a grader is code (fast, brittle), an LLM judge (flexible, calibrated against humans, given an "unknown" escape hatch), or a human (the gold standard the judges are calibrated to). aws-claude bundle, "Prompt evaluation pipeline" Concept · Anthropic "Demystifying evals for AI agents", as of 2026-08-27

The metric that separates demos from production is one exponent. pass@k asks whether at least one of k trials succeeds — right when one success is enough. pass^k asks whether all k succeed — right for agents that must behave every time. The arithmetic is brutal: 75% per-trial reliability is roughly 42% pass^3. Consistency, not capability, is the production bar.

On AWS this doctrine now runs as a two-tier harness. Build-time: Strands Evals in CI — cases with expected outputs and expected tool trajectories; deterministic graders (tool selection, parameters, trajectory order) hard-fail the build at zero tolerance; LLM-judge layers gate on thresholds, measured with pass^k. Production: AgentCore Evaluations continuously samples 1–5% of live sessions against the same evaluator set, and its scores land in the same CloudWatch GenAI observability dashboards as latency and cost — quality alarms next to operational alarms, one pane. Bedrock Evaluations completes the roster with managed LLM-judge jobs that can grade even non-Bedrock outputs. AWS ML Blog, "Evaluating AI agents: a production blueprint with Strands and AgentCore" · AgentCore Evaluations GA notes, as of 2026-08-27

The cleanest example of the doctrine is the thinking knob from Part I. Thinking on current models is adaptive — always available, never toggled — so what the eval selects is an effort level: sweep low through max against the suite, pick the cheapest level that clears the bar, and pin it. Then leave it pinned — changing effort mid-conversation invalidates the prompt cache. Anthropic effort and adaptive-thinking docs, as of 2026-08-27

Envelope beat · the last one

Evals are the envelope's gates: deterministic graders that hard-fail a build, judge thresholds that hold an average, a sampled production tier that never sleeps, and every production failure fed back into the golden set. The model proposes a behavior; the eval decides whether it ships. It is the one claim on this page most worth keeping true.
